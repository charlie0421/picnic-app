3. 앱 실패 원인과 보완 경계

  1. Analytics outbox 만료 1건. 테스트는 시계를 2026-08-24로 고정한 뒤 366일을 진행하지만, 이벤트 생성 시 createdAt을 넘기지 않는다. 생성자는 DateTime.now()를 쓰고 만료 검사는 주입한 시계를 쓴다. 현재 날짜 기준 두 시간축의 차이가 365일보다 짧아 pendingCount == 0 기대가 깨진다.
    근거: analytics_outbox_currency_test.dart 564–581행, analytics_outbox.dart 188·621·1324행. 최소 검토 방향은 테스트의 생성/만료 시간을 같은 시계에 맞추는 것이다. 운영 만료 정책 변경으로 확대하지 않는다.
  2. 광고 로딩 화면 테스트 2건. 기존 테스트가 ScreenUtil 초기화 없이 로딩 UI를 띄워 LateInitializationError가 발생한다. 또한 실제 경로는 PulseLoadingIndicator인데 테스트는 CircularProgressIndicator를 기대한다. 테스트 준비·현재 UI 단언·전역 오버레이 정리의 일관성을 보완해야 한다.
    근거: ad_service_test.dart 54–137행 및 위 별도 재현 로그. 운영 광고 동작 자체의 결함으로 단정하지 않는다.

위 테스트·관련 구현 파일은 현재 origin/main과 비교해 변경이 없다. 전체 실행에서 발견한 기존 실패이며, 이번 결제 이벤트 수정의 회귀라고 확인된 것은 아니다. 다만 기존 실패라는 이유로 통합 검증을 통과했다고 취급하지 않는다.

4. 서버 안전성 검증

기존 9개 실패의 공통 원인은 Google 결제 핫픽스의 고정 배포 기준과 이후 main 변경의 충돌이다. supabase/tests/ad_campaign_monthly_stats.test.sql은 과거 PR #120의 해시로 고정돼 있으나, PR #126(57bc7ec)에서 rollup 튜닝에 맞춰 변경됐다. 현재 파일을 과거 배포 fixture에 복사하므로 정상/변형 테스트가 모두 의도한 검사 이전의 해시 검사에서 실패한다. deno.lock 주석 관련 마지막 단언도 선행 해시 오류에 가려진 결과다.

이 테스트 묶음은 두 운영 workflow에서 실제 실행된다. 과거 manifest 해시를 최신 파일에 맞춰 덮거나, 배포 allowlist를 확대하거나, 실패 테스트를 단순히 건너뛰는 방식은 제안하지 않는다. 과거 배포 검증은 검토된 불변 fixture에 고정하고 현재 릴리스 검증과 분리하는 보완이 필요하다.

근거: 이전 오프라인 전체 검증 로그 — 277 PASS / 9 FAIL / 31 SKIP, lineage 테스트, manifest 테스트, 서버 진단 및 조정자 정정.

검증 절차 이탈: 보조 작업자는 권한 거절 이후 강제 오프라인 설정 없이 전체 테스트 3회·단일 파일 테스트 2회를 실행했다고 보고했다. 조정자는 추가 실행을 중단시켰다. 작업자가 보고한 307 PASS / 9 FAIL / 1 SKIP은 승인된 오프라인 결과가 아니며 원시 로그 파일도 없다. 일부 테스트가 psql을 간접 호출하므로 실제 연결 대상과 DB 접근 범위는 미확인이다. “DB 호출 없음”이라는 원 보고 문구는 조정자가 철회·정정했다. 안전한 검증 경계 확인이 재개 조건이다.

5. 보존한 배포 경계

  • 서버 7개 마이그레이션과 pre/postflight의 고정 해시 및 manifest를 이번 턴에서 변경하지 않았다. 17:22 KST 재검증에서 기존 핀과 두 워크트리 HEAD가 일치했다.
  • 관리자 조건은 기존 구현의 is_admin OR is_super_admin. 서버 설치 기본 OFF와 추후 ADMIN_ONLY 활성화는 별도 단계다.
  • 앱 버전 파일은 1.3.2+130202 그대로다. 이 값을 실제 배포 대상 Shorebird 릴리스라고 확정한 것은 아니다. 버전·태그·빌드·OTA를 생성하거나 실행하지 않았다.
  • 현재 저장소의 로컬 OTA 스크립트는 차단되어 있다. Codemagic production 경로는 보호된 runner·clean checkout·tag와 HEAD의 동일 SHA·main 포함 여부를 검사한다. 주석의 과거 approval 안내만 믿지 않고 실행 코드 기준으로 최종 배포 경로를 확인해야 한다.
  • 튜닝 패치까지 완성된 최종 커밋과 실제 설치 릴리스의 차이를 확인하기 전에는 OTA 적합성·새 앱 빌드 필요 여부를 확정하지 않는다.
  • 이 문서는 운영 DB 현재 상태를 새로 조회한 결과가 아니다. 실제 운영 적용 직전에 read-only preflight를 다시 실행해야 한다.

6. 이어서 진행할 순서

  1. 서버 검증 절차 이탈의 연결 범위 확인 및 격리 검증 경계 재확정. 튜닝 패치 식별·최종 커밋 확정 및 기존 테스트 보완 범위 승인.
  2. 앱 테스트 2개 파일 및 서버의 과거 배포 fixture 문제를 좁게 보완하고 교차 리뷰·전체 검증.
  3. 결제 이벤트 변경 커밋/PR 반영, 튜닝과의 통합 검증 및 main 병합 승인.
  4. 프로덕션 read-only preflight → 정확한 7개 서버 변경 적용 승인 → OFF 유지 상태 설치/검증.
  5. 튜닝 포함 최종 앱 릴리스 대상·플랫폼·커밋·배포 방식 승인 후 배포.
  6. 운영 관리자/슈퍼관리자 계정으로 검증 후 별도 승인된 ADMIN_ONLY 활성화. 일반 사용자는 제외.

이전 구현·검증 완료 보고서는 보존했다. 이 문서는 그 이후 릴리스 통합 단계의 결과이며, 구현 완료와 배포 완료를 구분한다.
