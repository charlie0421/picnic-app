판정과 한계

확인한 프로세스 환경과 테스트 코드를 함께 보면 기본 로컬 DB에 접속했을 가능성이 높다. 다만 실행 당시 자식 shell의 환경 snapshot과 원본 서버 연결 로그가 없어 접속 대상을 완전히 확정하거나 운영 DB 접근이 전혀 없었다고 증명할 수는 없다. 현재 프로세스 환경은 과거 자식 프로세스 환경과 동일하다는 보장이 없다.

추가 실행된 Google Pending 테스트는 코드상 명시적인 transaction 안에서 fixture DDL/권한/이력 행을 변경한 뒤 ROLLBACK하거나, ON_ERROR_STOP 종료로 transaction을 중단하는 구조다. readonly 테스트도 fixture 생성 단계에는 쓰기를 수행하므로 전체 실행을 “읽기 전용”이라고 부르면 안 된다. 코드상 롤백 구조와 실제 서버의 사후 상태 검증은 다르며, 원본 DB 교체로 이번에는 후자를 입증하지 못했다. V2의 commit 수행 테스트는 별도 PROMOTION_V2_REHEARSAL_DB_URL이 필요하고 해당 실행 결과에서 1건 skip이었다.

이번 테스트의 실행 경계

  1. 조정자만 테스트를 실행하며 구현 작업자는 source-only 작업으로 제한했다.
  2. 서버 Node 테스트 자식 프로세스는 macOS sandbox-exec의 (version 1)(allow default)(deny network*)로 네트워크 접근을 차단한다. 사전 실제 소켓 생성 probe에서 EPERM이 아니면 테스트 실행을 거부한다.
  3. 환경변수는 PATH/HOME/LANG/LC_ALL을 원래 값 그대로 전달하고, 최종 실행의 TMPDIR은 이번 실행이 만든 전용 fixture 폴더로 지정한다. 테스트용 CI 설정 및 WALLET_LOCAL_DB_URL=127.0.0.1:1, PROMOTION_V2_REHEARSAL_DB_URL 빈 값, PGHOSTADDR=127.0.0.1을 명시한다. 인증·라우팅 환경변수는 상속하지 않는다.
  4. 이 경계로 두 파일 RED 재현: 14 PASS / 9 FAIL / 0 SKIP. 기존 stats SQL digest 불일치를 그대로 재현했다. 실행 거부를 우회한 검증은 없다.

모의 HTTP 테스트의 별도 검증 경계

전체 23파일에 OS deny-network를 적용하면 기존 GitHub 환경 보호 테스트 1개 파일의 모의 서버 listen이 EPERM으로 거부되어 16건이 실패한다. 이를 소스 결함으로 집계하거나 호스트 loopback 허용으로 해결하지 않았다. 이 1개 파일은 별도 Docker --network none --read-only --cap-drop ALL --security-opt no-new-privileges --user 1000:1000에서 실행했다. 기존 캐시된 공개 이미지의 Node 바이너리만 entrypoint로 사용했고, 테스트와 검증기 2개 파일만 read-only mount했다. 호스트 포트·Docker socket·자격증명·DB 파일은 노출하지 않았다. 컨테이너 내부 인터페이스가 loopback뿐임을 확인한 뒤 16 PASS / 0 FAIL. 이 실행이 생성한 임시 컨테이너는 --rm으로 자동 정리됐다. 기존 DB 컨테이너와 데이터는 변경하지 않았다.

나머지 22개 safety 파일은 기존 OS deny-network를 그대로 유지하여 최종 276 PASS / 31 DB SKIP / 0 FAIL. 두 실행을 합하면 23개 파일 전체 292 PASS / 31 SKIP / 0 FAIL이다. 실제 DB 실행을 포함한 전체 검증이라고 주장하지 않는다.
