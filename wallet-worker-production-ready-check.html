2. 실행한 SQL의 한계

preflight는 transaction_read_only=off를 검사하므로 일반 BEGIN + SET LOCAL statement_timeout=15s / lock_timeout=3s + 원본 gate + 완료 SELECT + ROLLBACK으로 실행했다. 이 gate는 메타데이터 읽기 및 트랜잭션 로컬 설정만 수행한다. migration·CREATE/ALTER/GRANT·flag 변경·worker 함수 호출은 하지 않았다. 전후 별도 조회는 BEGIN READ ONLY로 실행했다. 즉 운영에서 committing bundle이나 rollback rehearsal을 실행한 것이 아니다.

5. 쓰기 중단 창과 재개 조건

독립 읽기 전용 보조 조사(Sol/high)와 root의 runbook/builder 대조 결과, 필요한 동결 범위는 배포·권한·플래그 등 운영 설정 변경이다. 일반 사용자 결제나 expiry/reconciliation cron을 전면 중단하라는 요구가 아니다. 다른 migration/DDL, 함수·ACL·owner·role membership, route registry, cutover evidence, audit coverage, worker roster/deployed_version/CHECK, runtime flag 변경을 짧은 적용 구간 동안 중단하는 운영자 확인이 필요하다. 조사 작업자는 코드·DB·파일을 변경하지 않았다.

runbook §3·§4.3·§4.4의 운영자 확인은 미확인 상태다. 다른 세션의 DB migration/권한/flag/배포 관련 설정 변경을 멈출 수 있는 실행 창과 새 복구 지점이 필요하다. 단일 시점의 DB 접속 목록이나 관련 flags OFF만으로 “쓰는 사람이 없다”를 증명하지 않는다. cron·결제·전체 서비스는 임의로 중단하지 않았다.

이번 단일 번들의 잠금은 같은 번들의 advisory lock, migration history table, runtime_flags를 대상으로 하며 시스템 전체 writer를 차단하는 잠금이 아니다. emergency flag-OFF도 짧게 대기할 수 있어 실행 창 동의가 필요하다. 범위가 불명확한 동결을 임의 실행하지 않는다.

재개 순서: 새 백업/복구 지점 방법과 데이터 보관 승인 → 복구 지점 확보·확인 → 다른 운영 변경 중단 창 확인 → preflight 재확인 → 승인된 단일 패치 적용 → 독립 postflight·보존 검증. ADMIN_ONLY 활성화·앱 배포·다른 migration은 포함하지 않는다.

사용자의 현재 진행 승인은 단일 서버 패치 작업을 이어가는 범위로 기록한다. 그 승인이 새 백업의 데이터 보관 방법이나 다른 세션의 변경 중단 완료 사실을 자동으로 증명하지는 않는다. 추가 확인을 요청하고 실제 적용 직전에서 중단했다.
