Task 39.9: 투표 신청 데이터 로딩 성능 검증 설계

대상: VoteItemRequestService의 검색 결과 enrichment 배치 처리
제약: 실제 DB·네트워크·RLS를 변경하거나 호출하지 않는다.

1. 현재 구조

  • UI 검색 페이지 크기는 20명이며, 결과를 먼저 표시한 뒤 신청 정보를 백그라운드에서 enrichment한다.
  • enrichment는 최대 50명씩 나누며 로그인 사용자는 배치당 3개, 비로그인 사용자는 2개 쿼리를 병렬 시작한다.
  • 50명 초과 배치는 순차 처리하므로 100명은 로그인 기준 최대 6개 쿼리가 필요하다.
  • 응답 행 필터링에 이름 List.contains를 반복해 데이터 증가 시 선형 lookup 비용이 중첩된다.

2. 선택한 접근

영역설계
배치 계획기존 pure helper의 splitIntoBatches를 운영 서비스가 직접 사용한다. 기본 batch size는 50을 유지한다.
구조 검증0·1·50·51·100·120명에 대한 배치 개수, 최대 크기, 누락·중복 부재를 결정적으로 검증한다.
쿼리 상한ceil(artistCount / 50) × (로그인 3 / 비로그인 2)를 helper로 계산하고 경계값을 테스트한다.
lookup배치 내 아티스트 이름을 Set<String>으로 수집해 응답 행 membership lookup을 평균 O(1)로 변경한다.
시간 측정CI pass/fail에 Stopwatch 절대 시간을 사용하지 않는다. mock 시간은 Supabase·기기 성능을 대표하지 못한다.

3. 변경 경계

  • vote_item_request_service_helper.dart: batch size 상수와 구조적 쿼리 수 계산 함수
  • vote_item_request_service.dart: helper 기반 배치 분할과 Set lookup 사용
  • vote_item_request_service_helper_test.dart: 경계·상한·데이터 보존 테스트

4. 하지 않는 것

  • 서버 RPC, view, index, RLS, migration 변경
  • 배치 병렬 실행으로 DB 부하를 늘리는 변경
  • 실제 latency, payload byte, p95를 mock 결과로 주장
  • 현재 호출되지 않는 legacy N+1 경로의 별도 리팩터링

5. 후속 운영 측정

실제 최적화가 필요하면 staging에서 검색과 enrichment를 분리 측정하고, 반환 row·byte, cold/warm p50·p95, 전체 투표 row 증가에 따른 변화, DB EXPLAIN과 index를 확인한다. 문제가 확인될 때만 artist_id 필터 또는 서버 집계 RPC를 별도 설계한다.

6. 완료 조건

  • 운영 서비스가 검증된 batch helper를 사용한다.
  • 0·50·51·100 경계에서 배치와 쿼리 상한 테스트가 통과한다.
  • lookup 입력이 Set으로 구성되고 동작 결과가 유지된다.
  • 관련 서비스·helper 테스트와 정적 분석이 통과한다.
  • 실제 DB와 원격 설정에는 변경이 없다.
