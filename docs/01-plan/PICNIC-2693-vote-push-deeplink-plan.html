투표 현황 푸시 클릭 시 초기화면 이동

목표: 투표 현황 알림을 탭하면 해당 투표 상세를 열고, 앱 시작·복귀·포그라운드 수신 과정에서 목적지를 잃지 않게 한다.

아키텍처: 실제 발송 payload 계약을 먼저 확인한다. 원격/로컬 알림의 입구에서 목적지를 한 번 추출하고, 콜백이 아직 없는 구간은 PushTokenService 내부 pending queue 가 보존한다. 초안 폐기 Branch 경로의 준비 상태·대기열을 재사용하는 안은 회귀 위험 대비 이득이 없어 채택하지 않았다.

기술: Flutter / Riverpod / Firebase Messaging / flutter_local_notifications / Branch / Supabase.

명세: Jira PICNIC-2693 원문 — “투표 현황 푸시 수신했을때 클릭하면 해당 투표의 상세로 이동하게 해야함. 현재는 초기화면으로 이동함.”

1. 결론과 확정 범위

원인은 확정됐다. 서버는 정상이며 결함은 전부 앱에 있다. 발송처 picnic-supabase/supabase/functions/notify-vote-progress/index.ts:164–168이 { type:'vote_progress', vote_id:String(id), action_url:'https://applink.picnic.fan/vote/detail/<id>' }를 보내고, send-push/index.ts:121–125의 buildFcmData가 이를 그대로 FCM message.data에 넣는다. 프로덕션 Edge Function notify-vote-progress는 ACTIVE version 53으로 실제 배포돼 있고, DeepLinkHandler는 이 canonical URL을 ['vote','detail','<id>']로 이미 지원한다. 따라서 서버 수정은 불필요하고, 아래 세 가지 앱 결함이 목적지를 잃게 만든다.
  1. 탭 실행을 프레임에만 맡겨 지연될 수 있다. 원격 탭은 push_token_service.dart:122 → app_initializer.dart:664로 post-frame 콜백을 중첩한다. 이 함수는 새 프레임을 요청하지 않으므로 화면이 정지해 있으면 후속 콜백이 사용자 조작까지 대기할 수 있다. 로컬 탭도 app_initializer.dart:673에서 같은 위험이 있다.
  2. 초기화 이전 resume이 최초 원격 탭을 소비한다. (주원인) app.dart:469가 포그라운드 복귀마다 무조건 PushTokenService.resume()을 호출하고, resume()은 콜백 설치 없이 coordinator를 생성한다. _installSubscriptions():148이 1회성 getInitialMessage()를 소비하면 _handleNotificationTap은 콜백이 없어 로그만 남기고 탭을 버린다. 이후 initialize()가 콜백을 설치해도 복구 경로가 없다. 앱 종료 상태에서 푸시를 탭했을 때 resume이 background task의 initialize보다 먼저 도달하면 재현된다.
  3. 기존 로컬 알림을 눌러 종료 상태에서 실행하면 launch payload 복구가 없다. getNotificationAppLaunchDetails() 호출이 앱 코드 전체에 없다. 원격 FCM의 getInitialMessage()가 이 로컬 알림을 대신 복구한다고 가정할 수 없다.
  4. 정정 — 로컬 정규식은 결함이 아니다. push_token_service.dart:469의 RegExp(r'https?://[^\s}]+')은 raw string이므로 \s는 문자 s가 아니라 공백 문자 클래스로 정상 동작한다. 초기 조사에서 이스케이프를 잘못 읽은 것이며 결함 목록에서 제외한다. 다만 service가 동일 로직을 push_token_helper.dart:141과 중복 구현하고 있어 helper 호출로 일원화한다(동작 변경 없음, 중복 제거 목적).

배포 판단: 이 문서의 기본 앱 수정은 Dart만 변경하므로 기존 바이너리와 호환되는 OTA 후보다. iOS/Android 네이티브 수정은 현재 근거로 필요하지 않다. 실제 iOS 탭 이벤트가 Dart에 도달하지 않는 별도 네이티브 문제가 확인되면 신규 빌드로 전환한다. 서버 payload 는 정상으로 확인됐으므로 서버 배포는 필요 없다(2절).

문서 상태: 최초 작성 시점에는 분석·계획 문서였고, 이후 구현·교차 리뷰를 거쳐 확정 설계에 맞게 갱신했다. 초안과 달라진 항목에는 미채택 또는 “초안과 다름” 표시를 붙였으므로, 표시가 붙은 서술은 구현 근거로 쓰지 말 것. 앱 Dart 코드와 테스트만 변경했고 네이티브·버전(1.3.4+130403)·의존성·서버는 변경하지 않았으며 commit/push/배포는 수행하지 않았다.

payload 계약 확인 완료

아래는 최초에 “제안”으로 적었던 형태이며, 이후 발송처 확인 결과 실제 계약과 일치했다.

{
  "message": {
    "notification": { "title": "투표 현황", "body": "대상 투표의 현황" },
    "data": {
      "action_url": "https://applink.picnic.fan/vote/detail/123"
    }
  }
}
달성형 투표: action_url = https://applink.picnic.fan/vote/detail/123?type=achieve

notification.title/body는 표시 내용, message.data.action_url은 앱 이동 목적지다. notification 본문·DB의 최상위 action_url·APNs의 일반 url·Branch 단축 URL은 이 계약과 같지 않다. 123은 예시 ID다.

배포본 확인 방법

  1. 동일 제보의 발송 시각, 대상 OS, 앱 버전, messageId, 앱 상태를 확보한다. 발송기 로그의 FCM 요청과 단말 RemoteMessage.data를 대조한다. 사용자 ID·토큰·본문 전체는 공유 로그에 남기지 않는다.
  2. 실제 Supabase 프로젝트의 Edge Functions 목록·배포 소스·스케줄, 별도 picnic-supabase/관리자 발송 레포를 읽기 전용으로 확인한다. 로컬 baseline을 배포 소스로 대신 사용하지 않는다.
  3. 최근 관련 push_messages.data와 user_notifications/broadcast_notifications의 type·action_url·data 키를 비교한다. DB row와 FCM 요청을 함께 봐야 변환 과정의 누락을 찾을 수 있다.
  4. 반환 데이터에는 action_url, url/link/route, type, vote_id, 달성형 구분 키가 있는지 기록한다. 단축 URL이라면 Branch 원래 목적지도 확인한다.
-- 운영 담당자가 선택한 프로젝트에서 읽기 전용 확인. 토큰/수신자 목록은 조회하지 않는다.
SELECT id, created_at, data
FROM public.push_messages
WHERE title ILIKE '%투표%'
ORDER BY created_at DESC LIMIT 20;

SELECT id, created_at, type, action_url, data
FROM public.broadcast_notifications

ORDER BY created_at DESC LIMIT 20;

위 SQL은 실행하지 않았다. 다국어 제목·별도 발송 저장소를 쓰면 제목 검색만으로 누락 여부를 판정하지 말고 발송 시각·messageId로 조회한다. 운영 DB 접근 및 발송 로그는 이번 워커에 제공되지 않았다.

// 성공한 read 만 래치하고, 동시 호출은 single-flight 로 합친다 (:64-96).
static Future<void> _consumeLaunchNotification() {
  if (_launchPayloadConsumed) return Future<void>.value();
  final inFlight = _launchNotificationRead;
  if (inFlight != null) return inFlight;

  late final Future<void> attempt;
  attempt = () async {
    try {
      final details = await (_debugLaunchPayloadReader ?? _readLaunchPayload)();
      _launchPayloadConsumed = true;          // 실패하면 래치하지 않아 다음에 재시도된다
      final actionUrl = PushTokenHelper.resolveLaunchActionUrl(
        didNotificationLaunchApp: details.didNotificationLaunchApp,
        payload: details.payload,
      );
      if (actionUrl == null) return;
      _deliverActionUrl(actionUrl);           // 실행 중 탭과 같은 처리 경로
    } catch (e, s) {
      logger.e('[FCM] Could not read notification launch details; will retry',
          error: e, stackTrace: s);
    } finally {
      if (identical(_launchNotificationRead, attempt)) _launchNotificationRead = null;
    }
  }();
  _launchNotificationRead = attempt;
  return attempt;
}

owner 보호: 초안의 _ownerGeneration 재검사 대신 _deliverActionUrl 이 콜백 유무를 보고 분기한다. dispose 가 콜백과 pending queue 를 함께 비우므로(dispose()), 죽은 owner 로 목적지가 흘러가지 않는다.

세부 계약(구현 기준): payload 에 action_url 이 없으면 null 이며 다른 필드의 URL 을 대신 고르지 않는다. 추출 실패는 예외를 밖으로 던지지 않는다. 이미 생성된 legacy 알림은 형식을 바꾸지 않았으므로 그대로 읽힌다. launch 처리 완료는 성공한 read 뒤에만 기록해 동일 launch 를 중복 전달하지 않으면서 실패는 재시도된다. 권한 요청과 토큰 등록을 기다리느라 launch 조회를 지연시키지 않는다.

범위 선택: 정규식은 결함이 아니므로 JSON 형식 전환은 이번 범위에서 제외했다(중복 제거를 위한 helper 호출 일원화만 수행). 종료 후 로컬 탭 복구는 수용 범위에 포함했다.

  • 적용 · 초안과 다름 초안은 투표 경로의 내부 post-frame 을 유지하려 했으나 제거했다. 같은 포털이면 setPortal 자체를 생략하므로 기다릴 rebuild 가 없고, 다른 포털이면 setPortal 직후 같은 턴에 push 한다 — 동기 state 를 읽으므로 stale stack 문제가 없다. 그 결과 홈 화면이 한 프레임 노출되는 깜빡임도 사라졌다. 고정 delay 는 넣지 않았다. (_pushFullScreenPage 의 post/qna post-frame 은 Navigator push 용이라 그대로 둔다.)
  • 변경 없음 투표의 usePushKeepScreen 은 기본값(false) 그대로다. 필요한 회귀가 나오지 않았고, 화면 표시가 stack 기반이라 이 플래그는 제보 해결과 무관했다. notice 의 keepScreen=true 도 그대로 유지된다.
  • 미채택 · 불필요 legacy /vote/ID·custom scheme·단축 링크 호환 분기는 추가하지 않았다. 발송처가 canonical URL 만 보내는 것이 확인됐고(ACTIVE version 53), 푸시는 Branch 흐름을 거치지 않아 단축 해석이 필요 없다. getLongUrl 도 계속 푸시에서 호출되지 않는다.

결과: 서버가 이미 canonical URL 을 보내므로 새 네트워크 요청이나 단축 해석 의존성을 앱에 추가하지 않았다. vote_id fallback helper 도 구현하지 않았다 — action_url 이 항상 유효하게 도착하므로 쓸 자리가 없고, 없는 계약을 추측해 목적지를 만들지 않는다는 원칙은 그대로다.

실기기 수용 기준

  • Android/iOS 각각 백그라운드 원격 탭, 종료 원격 탭, 포그라운드 로컬 탭, 로컬 알림 생성 후 종료 탭을 검증한다. iOS 원격 배너와 로컬 배너는 messageId/notification ID와 callback 종류로 구분한다.
  • 일반 투표·달성형 투표 각각 올바른 ID와 화면 유형을 표시한다. 로그인 세션 복구 지연·네트워크 복구·다른 포털에서 탭해도 목표가 사라지지 않는다.

  • 진단은 received(source/id), destination-resolved, queued, ready, dispatched, page-pushed 단계로 남긴다. full payload/토큰 대신 필요한 키 목록·정규화된 경로·오류 이유만 남긴다.

  • 브라우저 검증 미완료: Orca tab list는 runtime_unavailable, 독립 Playwright Chrome 실행은 sandbox 내 SIGABRT로 실패했다. 파일 렌더링 자체의 오류를 확인한 것은 아니다. 코디네이터에게 브라우저 로딩 검증을 요청했으며, 데스크톱/모바일 가로 overflow 검사는 아직 수행하지 못했다.
  • 변경 범위: 이 문서 외에 앱 Dart 코드(push_token_service, push_token_helper, app_initializer, deep_link_handler, 신규 deep_link_navigation_plan)와 테스트가 함께 바뀌었다. 네이티브·pubspec·버전·서버는 무변경이다. commit/push 는 수행하지 않으며 coordinator 가 문서 추적 여부를 함께 처리한다.
