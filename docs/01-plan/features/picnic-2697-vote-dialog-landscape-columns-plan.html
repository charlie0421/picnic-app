2. 전환 조건 설계

2.1 내용의 압박과 실제 제약으로만 선택

아래는 제안 의사 코드다. single은 현재 1단 폭·여백 정책을 적용해 계산한 가상 기준이고, columns는 별도 후보 폭으로 측정한 값이다. 어느 쪽을 렌더했는지로 다음 프레임의 판단을 되먹이지 않는다.

// 모두 logical px. empty/neutral은 입력값·활성·로딩 상태에 독립적이다.
final singleWidth = min(routeAvailableWidth, min(defaultLargePopupWidth(), 560));

장식 전체 길이 또는 ScrollPosition.maxScrollExtent를 트리거로 쓰지 않는다. 정책을 펼쳤다는 이유만으로 넉넉한 창도 2단으로 바뀌기 때문이다. 압박은 1단의 후보 식별·잔액·기존 로고 자리를 유지할 수 없는 상황으로 정의한다. 키보드에서 기존에 숨기는 로고는 preferredTailLogoHeight=0이다. M의 single.preferredIdentityAndBalanceHeight는 기존 _decorationComfortHeight를 중립 상태에서 호출한 값이다. 로고 이동·선호 초상화 압박을 보수적으로 포착하는 신호로만 사용하며 “실제로 장식 스크롤이 전혀 없다”는 증거로 쓰지 않는다. 새로운 좌열 실측은 columns.minimumIdentityAndBalanceHeight에 적용해 잘못된 2단 진입을 막는다. 1단 렌더 정책 자체는 변경하지 않는다.

폭 후보를 얻는 외부 LayoutBuilder는 AlertDialog의 IntrinsicWidth 밖에 두고, 그 부모가 이미 적용한 SafeArea는 다시 차감하지 않는다. 미적용 dialog inset 및 viewInsets의 수평분만 한 번 차감한 값이 routeAvailableWidth다. 열 선택용 body도 이 외부 제약에서 중립 inset으로 가상 계산하며, 입력 오류로 바뀐 실제 AlertDialog의 내부 높이를 열 선택에 되먹이지 않는다. 최종 렌더 높이는 기존 content LayoutBuilder의 실제 constraints를 따라 안전하게 제한한다.

추가 usefulColumnsFit는 “폭만 넓으니 2단”으로 더 나쁜 스크롤을 만들지 않기 위한 조건이다. 본문이 0이거나 한 컨트롤조차 담지 못하면 기존 1단 폴백을 유지한다. 무한 폭/높이 제약은 현재 경로로 돌리고 임의 화면비를 넣지 않는다.

전제 검증의 한계와 선택지: 기존 수치로 M의 보수적 압박 신호는 만들 수 있지만, “모든 실제 장식 축소/스크롤”을 정확히 탐지한다는 전제는 성립하지 않는다. JMA의 근사 comfort가 잔액 전체 높이를 과소평가하고 정책/계산 전문의 길이는 측정하지 않기 때문이다. 선택 A(M)는 기존 신호로 대상 표본을 열고 실제 두 열 적합성만 새로 검사해 기존 여유 화면을 보존한다. 선택 B는 1단의 실제 후보·잔액 전체도 새로 측정해 압박 판정을 넓힌다. B는 놓치는 경우를 줄이지만 1194×834 K280·2.0처럼 기존 근사상 여유였던 화면까지 2단이 될 수 있어 아래 “바뀌지 않음” 표를 그대로 적용할 수 없다. M은 중립 상태에서는 여유였다가 오류 문구가 생겨 압박이 커지는 순간에도 열 전환을 하지 않아 추가 2단 기회를 놓칠 수 있다. 반대로 실제 상태를 트리거에 넣으면 입력 한 글자로 열이 바뀔 수 있다. 어느 보존 범위를 제품 계약으로 삼을지는 디자인 확인 대상이다.

2.3 히스테리시스와 입력 중 안정성

  • 현재 상태 그대로 연결하면 입력 중 모드 변경 가능. 일반 _essentialHeight는 _canVote/_hasValue, JMA는 validation/hint에 따라 바뀌고 inset도 바뀐다. voting_dialog_viewport_test.dart:139는 100ms AnimatedPadding을 지난 뒤 검사하므로 중간 프레임은 미검증이다.

6.2 새 위험과 실패 조건

  • 좌열이 우열보다 길 때: IntrinsicHeight나 긴 좌열의 자연 높이로 카드 전체를 키우면 input이 다시 아래로 밀린다. body maxHeight를 먼저 고정하고 좌열 상세만 독립 스크롤한다. 우열 조작부 rect는 좌열 정책 펼침 전후 동일해야 한다.
  • 짧은 초상화 조각: 최소32를 계산해도 실제 잔여 viewport가32보다 작으면 원 일부만 보인다. 2단에서는 identity+잔액 최소 높이 검사를 통과해야 하며 초상화 전체 Rect와 모든 clip 조상을 검사한다. 좌열 최초 offset0에서 원·이름이 겹치지 않게 한다.
  • 원시 .w 확장: JMA의 16.w padding과 일반 잔액의32.w 아이콘·충전 pill은 작은 열에서도 전체 창 폭으로 커진다. 2단 슬롯에는 실제 열 폭 기준의 로컬 패딩/아이콘 치수를 사용한다. 1단에는 기존 치수를 유지한다.
  • 넓은 잔액 child: Wrap 자체가 있더라도 내부 Row에 긴 숫자가 있으면 단일 child가 열보다 커질 수 있다(JMA:1069). 자릿수 범위·줄바꿈/내부 스크롤을 실측하고 최소 열 폭 계산에 포함한다.

  • 읽기·키보드 순서: 두 열 렌더 순서가 스크린리더나 Tab 순서를 끊지 않도록 후보/잔액 → 전체사용 → 입력/clear → 피드백 → 제출 → 상세 순서로 Semantics/FocusTraversal을 검증한다. 정책을 열어도 focus를 이동하지 않는다.
  • 텍스트 확대/아이콘 테마: 200%를 clamp하지 않고 폰트·아이콘 scaling 정책이 실제 측정과 일치해야 한다. IconTheme applyTextScaling 변경 시 icon20 상수 전제가 깨질 수 있다(기존 recheck-response:338).

7.3 갱신 — 2026-09-15 실측과 사용자 결정

이 절의 초판은 닫기 영역을 캡슐 위에 겹치는 변경을 승인하지 않는다고 적었다. 그 판단은 철회한다. 초판은 최대 본문 높이만 비교했고, 아래 두 가지를 반영하지 못했다.

  • 예측 범위가 과했다. 851×393, 844×390, 926×428 의 K280 은 2694 에서 이미 스크롤 폴백 경로이고, 그 구간의 계약은 “오프셋 0 에서 전부 보임” 이 아니라 “오버플로 0 + 스크롤로 입력 도달” 이다. 닫기 48 이 그 판정을 바꾸지 않아 실제로는 실패하지 않았다.

겹치기 구현 시 확인할 것 4 건. “카드 우상단이 비어 있다” 는 전제는 성립하지 않는다.

  1. 충전 버튼이 그 자리로 올라온다(최우선). VotingStarCandyInfo 는 spaceBetween 이고 오른쪽 끝이 48 탭 타깃의 충전 버튼이다(voting_dialog_widgets.dart:514 부근). 장식 밴드 순서가 초상화 → 이름 → 잔액이라 장식이 스크롤되는 짧은 화면에서 잔액 행이 밴드 최상단까지 올라온다. Stack 은 나중 자식이 히트테스트를 이기므로 충전을 누르면 팝업이 닫히고 입력한 금액이 사라진다. 해법: 닫기가 있을 때 장식 밴드에 상단 인셋을 준다. 장식은 양보하는 밴드라 조작부 필수 높이를 건드리지 않는다. 2단의 우열 상단 여백과 같은 값을 쓴다.
  2. 카드 반경은 상수가 아니다. resolveVoteDialogShape 가 min(120.r, bodyHeight/4) 로 클램프한다. 본문이 넉넉하면 반경 120 이라 우상단이 크게 둥글고, 48 박스를 안쪽 모서리에 그대로 놓으면 Clip.antiAlias 에 깎인다. 1 차 적대적 리뷰 4 번 지적이 정확히 이 RRect 모서리 clip 이었고 실측 6.0 / 6.0 / 8.5px 이었다. 실제 해결된 반경을 기준으로 위치를 잡는다.
  3. JMA 배지가 상단에서 넓게 뻗는다. JMA 는 titleWidget 을 쓰지 않고 배지를 content 최상단에 직접 그린다. 280 계열의 좁은 카드에서는 배지 오른쪽 끝이 닫기 자리에 닿을 수 있다.
  4. 스크롤 콘텐츠가 닫기 밑을 지나간다. 이름과 잔액 텍스트가 Clip.antiAlias 안에서 흐르므로, 1 번의 상단 인셋을 두지 않는다면 스크림이나 배경 처리가 필요하다.

voting_complete 는 showCloseButton: false 라 겹침 분기를 타지 않으므로 공유 이미지 캡처 기하는 영향받지 않는다. 하단 숨김 strip 24 를 유지하면 본문 높이가 2694 와 같아지는 것도 계산상 맞다.
