투표 팝업: 화면비보다 실제 가용 공간을 기준으로 입력과 투표 동작 보장

목표: 플렉스 모드, 폴더블, 듀얼 스크린, 휴대폰 가로, 태블릿 분할 창에서 키보드가 없을 때 금액 입력·전체 사용·투표 버튼을 첫 화면, 스크롤 오프셋 0에서 모두 표시한다.

권고 구조: 실제 부모 제약으로 핵심 조작부 높이를 먼저 확보하고, 부족한 공간은 로고·장식 여백·초상화 순으로 줄인 뒤 헤더와 부가정보를 스크롤 영역으로 보낸다. 일반·PIC·파트너·JMA가 같은 레이아웃 정책을 사용하되 검증·차감·사용량 계산은 기존 다이얼로그가 소유한다.

기술: Flutter / Dart / LayoutBuilder / MediaQuery / flutter_screenutil 5.9.3. 요구사항 출처: 전달받은 PICNIC-2694 작업 명세와 로컬 코드. Jira 원문·실기기·위젯 실행 결과로 확대 해석하지 않는다.

1.2 공간을 더 줄이는 요인과 실제 상수

  • voting_dialog.dart:233–257: 일반 AlertDialog의 세로 inset은 위·아래 24씩, 합계 48 logical px다. 부모가 이미 뺀 키보드·SafeArea를 다시 빼는 버그는 현재 일반 코드에 없다. 최종 높이는 constraints.maxHeight에서 팝업 자체 장식만 뺀다.
  • picnic_lib/lib/presentation/widgets/ui/large_popup.dart:16–35: 숨긴 닫기 영역도 24를 점유하고 테두리는 양쪽 2.r이므로 추가 높이는 24 + 4.r다. 65–76행의 캡슐은 Clip.antiAlias로 실제로 자른다. 단순 화면 Rect 포함만 검사하면 둥근 모서리 클리핑을 놓칠 수 있다.
  • large_popup.dart:22: 345.w는 물리적으로 고정된 345가 아니다. voting_dialog_widgets.dart:226, 238–239, 387–388: 초상화는 80.w, 일반 로고는 60.w, 파트너 로고는 100.w다. 가로 화면에서 세로 이미지 점유까지 화면 폭 배율로 커진다.
  • picnic_lib/lib/core/utils/app_builder.dart:17–20, 50–53: 기준 393×892, splitScreenMode=true, minTextAdapt=true. 잠긴 ScreenUtil 5.9.3의 lib/src/screen_util.dart:216–245에서 scaleWidth=W/393, scaleHeight=max(H,700)/892, .r=min(scaleWidth,scaleHeight)다. 높이 393이어도 세로 여백은 393/892가 아닌 700/892 배율을 쓴다.
  • picnic_lib/lib/ui/presentation_tokens.dart:64–81: PicnicUi.text는 fontSize=size, height=1.45이며 .sp를 쓰지 않는다. minTextAdapt가 글자 크기를 자동 축소해 해결해주지 않는다. 글자는 MediaQuery의 TextScaler를 따른다.
  • 루트 ScreenUtil 크기와 팝업 부모 크기가 다를 수 있다. 예를 들어 루트 412×1000에서 상단 패널 412×500만 쓰면 실제 예산은 500 높이인데 .h 배율은 1000/892일 수 있다. 기기 자세나 MediaQuery.size만 보지 않고 최종 부모 constraints를 사용해야 한다.

1.3 일반 다이얼로그 높이 공식과 키보드 없는 티어 예시

아래는 루트 논리 크기와 부모 크기가 같고 SafeArea 추가 차감이 0인 독립 테스트 조건이다. W/H는 논리 px, K는 bottom viewInset, t는 선형 텍스트 배율이다. 폰트의 정확한 높이는 measureVotingTextHeight(voting_dialog_widgets.dart:18–32)로 측정해야 한다. 아래 23.2t·26.1t는 16×1.45t·18×1.45t의 한 줄 추정값이다.

sx = W / 393
sy = max(H, 700) / 892
sr = min(sx, sy)
B  = max(0, H - K - 48 - (24 + 4*sr))
C  = 실제 카드 폭 - 4*sr - 48*sx

I = max(48, measuredDigitLine + 16*sy + 2)
S = max(52, measuredVoteLabel + 8*sy)
N = measuredNameRow(C) + 20*sy
P = 80*sx + (K>0 ? 20 : 40)*sy
F = S + (K>0 ? 16*sy : 40*sy + logoHeight)
logoHeight = 60*sx (일반), 100*sx (파트너)

full    : B >= P + N + F + I + 8
compact : B >= P + F + I + 8, full 조건은 불충족
none    : 위 조건 불충족 또는 C <= 0

full의 중간 창 Vh    = B - P - N - F
compact의 중간 창 Vh = B - P - F
입력 시작 y (중간 창 기준) = 잔액 높이 + 전체사용 높이 + (compact ? N : 0)
입력 전체 가시 조건          = y + 실제 입력 높이 <= Vh

실제 입력 컨테이너에는 48 높이의 지우기 버튼도 있다(voting_dialog_widgets.dart:757–759, voting_dialog.dart:695–707). 테두리를 포함하면 일반 입력의 최소 외곽 높이는 약 50, JMA는 약 52다. 티어 계산은 현재 코드의 I 공식을 그대로 사용하고, 가시성 추정은 이 차이를 반영했다. 새 구현은 임의의 8 여유값에 의존하지 않고 실제 자식·테두리·패딩을 함께 측정해야 한다.

1.4 JMA는 같은 원칙의 결함이지만 구현·티어가 다름

git show 757507d49 --stat의 PR #227 변경 파일은 일반 다이얼로그·공유 위젯·일반 presentation test 세 개다. JMA에 _PinnedChrome.full/compact/none가 도입되었다고 쓰면 사실과 다르다.

  • jma_voting_dialog.dart:297–339: 키보드 없을 때 inset 합계 80, 있을 때 40. 예산은 min((H-K)*(K>0 ? .85 : .75), 실제 제약 높이 - hiddenChrome). 고정 티어는 예산 ≥360이면서 textScaler.scale(14) ≤18.2; 그 외는 전체 스크롤이다. t=2는 큰 화면에서도 항상 전체 스크롤이다.
  • jma_voting_dialog.dart:374–415: 고정 경로는 Expanded 중앙 스크롤, 대안은 모든 내용을 같은 순서로 스크롤한다. 일반처럼 실제 헤더·푸터·입력 높이를 모두 측정하지 않는다.
  • jma_voting_dialog.dart:419–429, 792–955, 1628–1642: 입력 앞에 잔액·교환 가능량 패널, 일일 한도, 전체 사용이 놓인다. 일반의 96보다 선행 콘텐츠가 훨씬 크다.
  • jma_voting_dialog.dart:695–745, 493–502, 1601–1661: 키보드가 없으면 초상화 60.w, 로고 60.w를 고정한다. 키보드가 있으면 초상화와 로고를 숨긴다. 일반 다이얼로그의 키보드 초상화 유지 정책과도 다르다.
  • 412×500, K=0은 min(375, 500-80-27.14)=375, 따라서 t=1·1.3은 고정 티어다. t=1의 헤더 약 120.57, 푸터 약 136.01을 빼면 중앙 창은 약 118.42이다. 잔액 패널 한 줄 모델만 약 130.22이고, 입력은 중앙 기준 약 222.73부터 시작해 첫 화면에서 보이지 않는다. 모든 텍스트 실측을 생략한 추정이어도 선행 패널만으로 창을 소모한다.

1.5 기존 테스트가 놓친 조건

voting_dialog_presentation_test.dart:106–157은 프로덕션 ScreenUtil 설정과 DPR=3, 논리 뷰포트, 하나의 viewInsets 주입 지점을 재사용할 수 있다. 그러나 181–214행은 tester.ensureVisible을 먼저 호출하고, 322–342행의 ‘without scrolling’ 검사도 325–326행에서 포커스를 준 뒤 자동 스크롤이 끝난 상태를 검사한다. 482–515행은 포커스 후 내부 스크롤 창 포함을 검증한다. 키보드 없음 + 첫 프레임 offset=0 + 내부 clip에 입력 전체 포함의 조합이 빠져 있다.

2. 뷰포트 매트릭스

기기 이름과 대응 크기는 추정 테스트 표본이다. 실제 제품·OS·화면 확대·작업 표시줄·힌지 설정마다 달라진다. 412×500도 플렉스 상단을 모델링한 값이며 특정 모델의 보증 사양이 아니다. iPad 분할 폭은 구분선 등을 감안한 예시다.

모든 가시성·스크롤 표시는 코드 기반 추정이며 위젯 실행 결과가 아니다. 행별 전체 조합은 K={0,280} × t={1,1.3,2}. ScreenUtil과 부모는 같은 W/H, 추가 SafeArea=0, 짧은 한 줄 이름(그룹 없음), 한국어의 짧은 라벨·잔액, 입력 공백·오류 없음, JMA 정책 접힘을 모델링했다. 글꼴 반올림·긴 라벨·줄바꿈은 결과를 악화시킬 수 있다. 특히 V는 이 단순 모델에서의 전체 표시이며 실제 기기 표시의 보증이 아니다.

각 셀은 ‘티어 / 스크롤 / 입력 / 투표 버튼’. F=일반 full, C=일반 compact, N=일반 none. JF=JMA 고정, JN=JMA 전체 스크롤. S=콘텐츠 넘침으로 스크롤 범위 양수, –=추정상 스크롤 범위 0(위젯 자체는 존재). V=전체 표시, P=일부만 표시, X=미표시 또는 전체 표시 실패. 모두 포커스·ensureVisible 이전, offset=0 기준이다. JMA JN의 투표 X는 아래로 밀리거나 일부 잘림도 포함한다.

3. 설계

3.1 조작부 우선, 장식·설명은 남은 공간 사용

  1. 먼저 실제 사용 가능 영역을 확정: route/SafeArea/키보드 처리 뒤의 LayoutBuilder 제약을 사용한다. 상위 AlertDialog가 제거한 inset을 재차 차감하지 않는다. IntrinsicWidth 질의를 차단하는 유한 SizedBox(width: ...)도 유지한다.
  2. 입력·전체 사용·제출의 실제 높이를 먼저 측정: 글자 배율, 실제 내부 폭, 줄바꿈, 입력 border/clear 버튼, 활성 제출 아이콘까지 반영한다. 터치 영역은 최소 48, 일반 제출은 기존 최소 52를 유지한다. TextScaler를 제한하거나 FittedBox로 글자를 축소하지 않는다.
  3. 충분한 높이: 현재 순서와 초상화·이름·잔액·안내·로고의 모습을 유지한다. 전체 콘텐츠가 들어가는 경우 중앙 영역은 스크롤 범위 0이다. PICNIC-2688의 375×812·K336·1×처럼 여유가 있는 키보드 화면도 기존 초상화·버블을 모두 보인다.
  4. 첫 축소: 장식 로고와 부가 혜택/정책을 우선 스크롤 가능한 부가 영역으로 옮기고, 장식 여백을 줄인다. 짧은 화면에만 로고를 숨길 수 있으나 브랜드·정책 정보는 부가 영역으로 접근할 수 있게 남긴다. 단순히 K>0일 때만 축소하지 않는다.
  5. 다음 축소: 초상화 최대 크기를 로컬 카드 폭·가용 높이로 제한한다. 일반 기준 80, JMA 기준 60 logical px를 상한 제안값으로 사용하고 부족할 때 32까지 줄인다. 글자·입력·터치 크기는 줄이지 않는다. 이름은 전체 텍스트를 남기고 줄바꿈을 허용한다. 짧은 모드에서는 카드 모서리 반경도 24 logical px로 제한하는 것을 제안한다. 기존 120.r 반경을 유지한 채 조작부를 위아래 끝까지 붙이면 bounding Rect가 들어가도 실제 페인트가 둥근 모서리에 잘릴 수 있다.
  6. 여전히 부족: 헤더(초상화·이름 포함), 잔액 상세, 로고, 혜택, JMA 설명·정책을 하나의 독립 스크롤 영역으로 옮긴다. 입력·전체 사용·제출은 이 스크롤 밖에 고정한다. 짧은 상태에서는 입력 → 전체 사용 → 제출 순서의 조작부가 먼저 공간을 확보한다. 후보의 짧은 식별 문구는 공간이 허용하면 조작부와 함께 표시하고 전체 이름은 부가 영역·Semantics에서 보존한다. 280×280·200%처럼 핵심 조작부만 들어가는 경계에서는 후보 이름을 입력·제출의 Semantics label에 연결하고 별도 고정 이름 행을 강제하지 않는다.
  7. 물리적 하한: 유한한 임의의 모든 높이에 세 48px 컨트롤을 보장할 수는 없다. K=0의 인수 표본(최소 280×480 및 추가 280×280)은 반드시 동시 표시한다. 그보다 작은 자유 크기 창이나 큰 키보드로 핵심 높이 자체가 남은 공간보다 크면 조작부 우선 순서로 전체 스크롤 폴백을 사용한다. 클리핑·음수 높이·RenderFlex overflow를 허용하지 않는다.

3.2 가로형 폭 확장·2단 배치 결정

이번 수정은 전체 팝업 2단 배치를 채택하지 않는다. 현재도 가로 851에서 카드가 약 747로 이미 넓다. 2단 자체는 이미지·로고 크기와 초기 우선순위 오류를 해결하지 않고, 좁은 Fold 커버·태블릿 1/3·200% 글자에서 또 다른 분기를 만든다. 먼저 1열 조작부를 보장하는 공통 구조로 해결한다.

투표 팝업에만 논리 폭 상한 560을 도입하는 것을 권고한다. 초기 폭은 min(345.w, 560, routeAvailableWidth), 세로 방향과 키보드 유무가 아닌 실제 폭으로 결정한다. 560은 설계 제안값이며 기존 상수가 아니다. LargePopupWidget(width: resolvedWidth)와 외부 SizedBox에 같은 값을 전달한다. 내부 패딩·초상화는 전역 .w 확대를 따르지 않도록 로컬 폭에서 상한을 정한다. 제출 버튼도 기존 172.w를 그대로 크게 만들지 말고 실제 영역에 맞춰 상한/최소 터치를 지킨다.

이후 별도 UX 검증으로 2단을 도입하려면 최소 좌측 정보 폭 + 간격 + 200% 우측 입력 폭이 실제 제약에 들어갈 때만 선택한다. orientation == landscape나 화면비 상수는 선택 근거로 사용하지 않는다. 지금 계획의 통과 조건에 2단은 필요하지 않다.

3.4 OTA 범위

구현은 Dart 레이아웃·테스트 변경으로 제한하고 새 플러그인, 네이티브 Activity/Info.plist/Manifest, 이미지·폰트 자산, pubspec 의존성 변경 없이 설계한다. 이 조건은 Shorebird OTA 검토가 가능한 범위라는 뜻이며 실제 OTA 호환·배포 성공을 확인한 것은 아니다. 버전·빌드·OTA 실행 단계에 들어갈 때는 지정 Flutter release 정책을 먼저 읽어야 한다. 이 계획 작업은 버전 결정이나 배포를 수행하지 않는다.

5.2 ‘보임’의 검증을 외곽·내부 clip·히트 테스트로 분리

  1. 새 다이얼로그를 열고 필요한 한정 프레임만 pump한다. 반복 애니메이션 때문에 무제한 pumpAndSettle을 사용하지 않는다. 키보드 없는 첫 표시 검사 전에 showKeyboard/ensureVisible/drag는 금지한다.
  2. 각 Scrollable의 offset은 0±0.01. amount는 TextFormField 글자 Rect가 아닌 테두리 포함 컨테이너 Rect를 잡는다. useAll은 GestureDetector의 터치 영역, submit은 표시 컨테이너를 잡는다.
  3. 세 Rect 모두 카드 경계 내부, SafeArea·키보드 제외 실제 부모 경계 내부다. 입력에 스크롤 조상이 있으면 가장 가까운 Scrollable의 viewport Rect에도 전체 포함되어야 한다. 허용 오차는 0.5 logical px.
  4. 카드의 둥근 클립(120.r)도 검사한다. 카드 RRect를 구성해 컨트롤의 실제 주요 페인트 영역이 안쪽인지 확인하거나 네 모서리 안쪽 1px·중앙의 hit test 결과로 클립과 겹침을 검증한다. 단순 findsOneWidget나 화면 안의 bounding box만으로 합격시키지 않는다.
  5. 세 컨트롤 Rect가 서로 겹치지 않고 중심에서 hitTestable이어야 한다. 비활성 제출도 시각적으로 보이되 실제 투표 호출이 일어나지 않아야 한다. 전체 사용/지우기 탭 후 값과 포커스 동작을 검증하고 제출은 mock에만 연결한다.

6.2 기타 위험과 대응

위험대응
후보를 모르는 상태에서 투표 조작만 강조공간이 허용하면 짧은 식별 문구를 고정 조작부 주변에 유지하고 전체 이름·초상화는 부가 영역에 둔다. 극단적으로 낮은 창은 입력·제출 Semantics label에 후보 이름을 연결하고 초상화/전체 이름은 스크롤로 접근한다. 긴 이름 전체를 무리하게 고정해 핵심을 밀지 않는다.
