투표 팝업 닫기 버튼·키보드 잔존
원인 분석 및 구현 계획

Goal: 입력 중 안전하게 닫을 수 있는 우상단 X를 복원하고, 일반·JMA 투표 팝업의 종료 시 입력 포커스를 정리한다.

Architecture: 종료 포커스 정리는 각 투표 다이얼로그가 소유한다. 공통 LargePopup에는 기존 기본 모양을 유지하는 선택형 우상단 닫기 배치와 활성 상태·콜백을 추가하고, 두 투표 다이얼로그가 정확한 48px 닫기 높이를 예산에 반영한다.

Tech Stack: Flutter 3.41.4 / Dart 3.11.1, Riverpod, ScreenUtil, Flutter widget tests. Spec: 코디네이터의 task_34b83414047d 요구사항 (a)~(d), Jira PICNIC-2695.

작업자는 이 HTML만 작성했다. 앱 코드·테스트·Git 이력은 수정하지 않았으며, Flutter 테스트 실행과 iOS 기기 재현은 구현 단계의 검증으로 남긴다. 구현 작업자는 Superpowers의 TDD 및 실행 계획 절차를 사용한다. 이 문서는 구현 승인이 아니다.

2. Flutter / iOS 연결 종료 메커니즘

로컬 SDK 경로의 디렉터리명은 3.35.2지만, 캐시 메타데이터와 실제 소스 커밋은 Flutter 3.41.4 / ff37bef603469fb030f2b72995ab929ccfc227f0이다. 아래는 이 체크아웃을 직접 읽은 근거이다.

  1. FocusNode.unfocus는 즉시 키보드를 숨기는 플랫폼 호출이 아니다. scope로 포커스 이동을 예약하고 포커스 갱신은 microtask에서 적용된다. 기본 disposition은 해당 scope의 이전 focusedChild 기록을 비운다(SDK/widgets/focus_manager.dart:916, SDK/widgets/focus_manager.dart:1920).
  2. EditableText가 포커스를 잃으면 입력 연결을 닫는다. _handleFocusChanged → _openOrCloseInputConnectionIfNeeded에서 !_hasFocus일 때 close한다. 포커스가 유지되고 기존 연결이 있는 동안에는 이 분기로 닫히지 않는다(SDK/widgets/editable_text.dart:4752, SDK/widgets/editable_text.dart:3982).
  3. close와 hide는 다른 단계다. TextInputConnection.close는 자신이 현재 attached 연결일 때 clearClient를 수행한다. _clearClient는 현재 연결을 null로 만들고 숨김 microtask를 예약한다. 그 사이 다른 입력이 attach하면 _currentConnection != null이 되어 hide는 생략된다(SDK/services/text_input.dart:1680, SDK/services/text_input.dart:2142, SDK/services/text_input.dart:2165). 이전 연결이 닫힌 경우와 키보드가 계속 보이는 경우를 동일시하지 않는다.
  4. iOS 네이티브 종료는 first responder 해제가 관여한다. TextInput.hide는 hideTextInput으로 전달되고 _activeView.resignFirstResponder를 호출한다(SDK/FlutterTextInputPlugin.mm:2564, SDK/FlutterTextInputPlugin.mm:2835). clearTextInputClient는 클라이언트 번호·뷰·접근성 상태를 정리하고 autofill 상태에 따라 뷰 제거를 지연할 수도 있다(SDK/FlutterTextInputPlugin.mm:3108). 네이티브 잔존을 확인하려면 TextInput.hide 수신 여부와 이후 새 연결을 구분해야 한다.
  5. pop 시점과 dispose 시점은 다르다. TransitionRoute.didPop은 역방향 애니메이션을 시작한다(SDK/widgets/routes.dart:377). pop 성공 알림은 그 직후 발생한다(SDK/widgets/navigator.dart:3323). 일반 라우트 포커스 관리도 자동으로 복원/해제한다(SDK/widgets/routes.dart:1166, SDK/widgets/routes.dart:1222).
  6. dispose 누락 또는 부모가 먼저 FocusNode를 파괴한다는 설명은 근거가 없다. 트리 unmount는 자식부터 수행하고, EditableText.dispose는 연결을 명시적으로 닫는다(SDK/widgets/framework.dart:2103, SDK/widgets/editable_text.dart:3443). 그 뒤 각 투표 State.dispose가 소유 FocusNode와 controller를 해제한다(voting_dialog.dart:188, jma_voting_dialog.dart:265). FocusNode.dispose 자체도 detach/unfocus한다(SDK/widgets/focus_manager.dart:1116).
원인 가설의 신뢰도: 종료 경로의 포커스 정리 누락은 높음. 그 누락이 iOS에서 전환 중 입력 연결/first responder 정리를 늦춘다는 설명은 합리적 가설이다. “dispose가 입력 연결을 영원히 닫지 않는다” 또는 “iOS 엔진 결함”이라는 결론은 현재 근거로는 성립하지 않는다. 뒤 페이지의 편집 필드가 다시 포커스를 얻는 경우도 별도 반례이다.

공식 API 교차 확인: PopScope의 성공 알림과 iOS 제스처 차이, TextInputConnection.close의 다른 클라이언트 연결 조건, FocusNode.unfocus의 포커스 이동 의미.

(b) X 복원, 투표 잠금, 높이 예산

1. 실제 UI 관례와 권고

팝업현재 관례판단
LargePopup 기본Column에서 카드 다음에 닫기 strip이 배치되고, 오른쪽 ‘닫기’ 텍스트 + cancel SVG를 표시한다(large_popup.dart:81, large_popup.dart:142). Pic 카메라 저장 팝업은 이 기본값을 쓴다(pic_camera_view_page.dart:460).showCloseButton=true의 최소 변경은 하단 ‘닫기 + X’다. 사용자가 말한 우상단 X와는 위치가 다르다.
전체 화면 다이얼로그Icons.close + 지역화된 닫기 접근성 이름을 사용한다(fullscreen_dialog.dart:89).아이콘만으로 닫기를 나타내는 관례도 존재한다. 투표는 우상단에 기존 cancel SVG 모양을 재사용하되 48×48 타깃과 닫기 label을 제공한다.
투표 완료 / 공유 이미지showCloseButton=false, 저장 중에는 빈 closeButton placeholder를 전달한다(voting_complete.dart:80, voting_complete.dart:387).숨김 24px strip과 캡처 이미지를 그대로 둔다. 공통 기본 배치를 전역으로 상단 이동하지 않는다.

채택안: LargePopup에 선택형 상단 닫기 모드를 추가하고 일반·JMA에만 사용한다. showCloseButton: true는 유지하며 closeButtonEnabled: !_isVoting로 비활성화한다. 상단 strip은 캡슐 외부 위쪽 48px에 둬 둥근 카드/아티스트 이미지와 겹치지 않게 한다. 기존 기본 하단 행과 숨김 strip 동작은 보존한다. 제품 결정으로 하단 행을 택하면 위치 변경은 생략할 수 있으나, 콜백·잠금·실제 닫기 높이 예산은 여전히 필요하다.

2. closeButton 커스텀만으로 해결되지 않는 이유

closeButton는 현재 외부 GestureDetector의 자식만 바꾼다. 바깥 strip은 그대로 하단이고 onTap은 showCloseButton이면 직접 Navigator.pop한다(large_popup.dart:107). 비활성 IconButton을 자식으로 넣어도 바깥 탭 처리를 막는 계약이 생기지 않는다. 상단 배치와 닫기 콜백/활성 여부를 공통 위젯의 외부 인터랙션에 적용해야 한다.

권고안은 상단 모드의 기본 자식을 기존 cancel SVG 24px로 제공하므로 투표 측에 closeButton: 커스텀은 필요 없다. 기존 슬롯은 호환성 때문에 유지한다. 상단 모드에 커스텀 자식을 허용한다면 48px 슬롯 안에서 시각 요소만 교체하고, 중첩된 Navigator.pop 핸들러를 두지 않는다.

3. 닫기 안전 계약

  • 사용자 dismiss: mounted & 현재 라우트 & !_isVoting일 때만 소유 포커스 정리 후 maybePop. 이 최신 상태 체크는 재빌드 전 저장된 콜백을 실행해도 유효해야 한다.
  • 진행 중: X의 onTap=null, Semantics.enabled=false, 비활성 시각 상태. 최소 타깃/strip 48px 유지. PopScope(canPop: !_isVoting)가 백과 배리어 maybePop도 보호한다.
  • 성공/실패 확정: 투표 완료 제어 흐름의 직접 pop은 그대로 남긴다. 이를 사용자용 _requestClose로 바꾸면 _isVoting=true인 성공 경로가 영원히 닫히지 않는다.
  • JMA: 현재 PopScope가 없으므로 추가한다. _isVoting은 동기 검증을 통과한 뒤 첫 await인 탈퇴 확인 전에 세우고, 차단 반환 때 해제한다. 현 코드는 탈퇴 확인 뒤에만 true로 설정하므로(jma_voting_dialog.dart:1356) 새 X로 그 사이 닫히면 await 뒤 setState가 disposed State에 도달할 수 있다. 일반 투표는 이미 첫 await 전에 가드를 세운다(voting_dialog.dart:730). 탈퇴 판단·투표 계산·네트워크 API를 바꾸지는 않는다.

Navigator.maybePop은 popDisposition을 확인하지만 직접 Navigator.pop은 그 확인을 거치지 않는다(SDK/widgets/navigator.dart:5553, SDK/widgets/navigator.dart:5590). onPopInvokedWithResult는 이미 결정된 pop 결과 통지이며 취소 지점이 아니다(SDK/widgets/pop_scope.dart:106).

잔액 부족 오류가 unfocus보다 먼저 표시됨동의. 일반 751~765줄 및 JMA1337~1356줄의 순서를 확인했다. 수정 범위에 포함하며, 제출 진입의 blur를 validation UI 앞에 옮기고 중첩 오류 팝업 종료 후 입력이 다시 포커스되지 않는 테스트를 추가했다.
오류 팝업의 확인 버튼을 누르면 닫힘해당 초기검증 분기의 onOk는 빈 함수다. SimpleDialog는 onOk를 그대로 실행할 뿐 자동 pop하지 않는다(simple_dialog.dart:168). 따라서 이 회귀 테스트는 오류 팝업을 배리어로 먼저 닫아야 한다. 확인 버튼 동작 변경은 별도 결함이다.
성공/실패 제출 경로는 안전, 탈퇴 확인에는 unfocus 없음성공/terminal 실패에는 선행 unfocus가 있어 위험도가 낮지만 네이티브 결과까지 ‘안전’이라고 입증되지는 않았다. 탈퇴 확인 호출은 일반765줄 unfocus 뒤의767줄, JMA1356줄 뒤1358줄이므로 ‘unfocus 없음’은 부정확하다. dispose가 FocusNode만 해제하므로 누락이라는 주장도 Flutter의 자식 EditableText.dispose 연결 close 근거와 충돌한다.
상단 strip이24→48, 크롬28→5224px 차이는 동의하지만 현재 strip은 하단이다. border는2.r이므로28/52는 scale=1인 경우만 맞는다. 상단 X opt-in, 실제 border helper, 큰 글씨의 기본 행 minHeight와 정확한 높이 차이를 계획에 반영했다.
widget test에서 닫으면 viewInsets가0인지 검사테스트가 주입한 viewInsets는 testTextInput.hide로 자동0이 되지 않는다. 포커스/client/isVisible과 네이티브 화면 geometry를 혼동하면 실패하거나 테스트 자체가0을 넣어 거짓 통과한다. widget test는 소유 FocusNode·text input 로그/연결을 검사하고, 주입된 inset은 별도의 layout fixture로 사용한다.
FocusScope.hasFocus=false를 필수 기대치로 사용scope/root가 primary focus를 소유할 수 있어 잘못된 일반화다. 실제 EditableText 소유 FocusNode.hasFocus=false 및 primaryFocus가 그 입력이 아닌지를 검사한다.
