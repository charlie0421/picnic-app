GA4 택소노미 — 최종 핸드오프

2026-09-06 · GA4 이벤트 택소노미 전 작업의 종료 시점 상태 · 이 문서가 진입점이다. 선행 문서는 §7 문서 지도 참조.

한 줄 요약 — GA4 택소노미는 구현·배포·실측 검증까지 전부 끝났다. 대행사 13문항 종결(8/31), 매출 서버 계약 종결(9/3). 열려 있는 코드 작업은 없다. 남은 것은 제품 결정 1건(Android 강제 업데이트)과 의도적으로 분리한 설계 과제 1건(attestation seal)뿐이다.

2. 이번 사이클에 실제로 일어난 일

GA4 매출을 서버 정본으로 만드는 계약이 2026-09-02 까지 프로덕션에서 한 번도 동작하지 않았다. 플래그를 켰는데도 아무 일이 없었고, 그 사실을 3주 동안 아무도 몰랐다. 경위는 이렇다.

근본 원인 — 게이트가 RPC 반환값과 이름이 달랐다

// wallet-operation-worker/index.ts (수정 전)
const shaped = actualType === "MOBILE_PURCHASE" || actualType === "WEB_PURCHASE"
  ? await withPurchaseAnalytics(client, inboxId, processed)
  : processed;

-- get_wallet_operation_event_type (20260721104000)
select case when operation_type in('MOBILE_PURCHASE','WEB_PURCHASE') then 'PURCHASE' ...

RPC 가 두 값을 'PURCHASE' 하나로 접어서 돌려주므로 게이트가 절대 맞지 않는다. 플래그 ON 이후 정산 63건 전부 actual_type='PURCHASE' 였고, withPurchaseAnalytics 는 한 번도 호출되지 않았다. 응답은 늘 7키였고 앱은 늘 카탈로그 값을 썼다.

가장 중요한 교훈 — "실측"이라 부르려면 응답 경계를 봐야 한다.
#117 은 "Google 정산 17건 중 16건이 통화만"이라는 스냅샷 컬럼을 근거로 "Android 매출이 0 이 됐다"고 결론지었다. 스냅샷은 서버가 아는 것이지 앱이 받은 것이 아니다. 실제 GA4 에는 그 16건 모두 카탈로그 금액이 정상적으로 찍혀 있었다. 같은 문서가 "스냅샷으로 판정하지 말 것"이라고 경고해 놓고 바로 그 함정에 빠졌다.
매출 계측을 판정할 때는 GA4(끝단)와 DB(서버)를 시각·통화 단위로 대조하라. 한쪽만 보면 틀린다.

3. 남은 작업 — 2건, 둘 다 코드 아님

① Android 강제 업데이트 (제품 결정 완료 · 실행 대기)
client_observed_currency 는 130104 부터 나간다. 그 이전 버전에서 들어온 Android 구매는 통화조차 없어 영구히 매출 없는 건이다 — analytics_* 컬럼이 불변 트리거로 잠겨 있어 소급 backfill 이 불가능하다. 2026-09-03 제품 결정: 다음 버전에서 강업. 현재 Android 미달 기기 290대(25.6%). 강업이 나가면 Google 통화 확보율이 100% 에 수렴한다.
② attestation seal 확장 (의도적 분리 · 미착수)
설계 §5.4 편차. MAC 재작성이 필요해 picnic-supabase #109 본문에서 별도 설계·리뷰로 분리했다. 택소노미 범위 밖이며, 착수하려면 #109 본문을 먼저 읽어라.

종결된 것 — 다시 꺼내지 말 것

  • 대행사 13문항 — 8/31 실측 전건 종결(재화명 오염 없음, ja 미출현, 지원 언어 실질 8개).
  • B-4 재고지 — 2026-09-03 불필요로 종결(제품 판단). AdMob 지면은 계측에 포함하고 분석에서 ad_platform 으로 분리한다.
  • B-9 sign_up — 오탐이 아니라 누락이다(커버리지 88.3%). signUpWindow 를 늘리지 말 것 — 격차가 14.8일까지 벌어져 어떤 창도 부족하고, 넓히면 진짜 오탐이 생긴다. 설계 한계다. sign_up 수를 실제 가입 수로 읽지 말 것(정확한 수는 auth.users).
  • Google 출처 A(regionCode → 카탈로그) — 8/25 불필요로 종결. Google Play 검증 응답에는 구·신 API 양쪽 다 가격 필드가 없다. Billing 8.x 로 올려도 서버는 통화를 모른다.
  • ad_click — AdMob 자동수집 예약어다. 우리 것은 ad_cta_click(8/29 배포·수집 확인).
  • 매출 과대계상 — 8/26 Firebase Play 토글로 Android 분 차단, 8/28 검증 완료. iOS 잔여분은 리포트 필터로 대응.
  • 복구 구매 매출의 로컬 기록 방식 — 적대적 리뷰 3회에서 blocker 가 계속 나와 되돌렸다(b5b138bd1). 같은 길을 다시 파지 말 것. 채택된 것은 서버 정산 응답 방식이고 이미 배포됐다.

4. 다음 사람이 반드시 알아야 할 함정

배포 대상은 verify_receipt 가 아니라 verify-receipt-v2

앱 상수가 receiptVerificationFunction = 'verify-receipt-v2' 이고, verify_receipt 슬롯(v186)은 구버전 앱 전용 레거시로 동결돼 있다. 레포의 verify_receipt/index.ts 는 wallet.v1 구현이라 그 슬롯에 배포하면 동결이 풀린다. verify-receipt-v2 가 그 파일을 import 해서 번들한다. 그 슬롯은 건드리지 말 것.

함수 배포 전에는 딸려 갈 변경을 반드시 확인한다

git log <현재_배포본_sha>..origin/main -- supabase/functions

실제로 걸렸다. #117 배포 시 main 에 #115 가 들어와 있었는데 짝 마이그레이션이 프로덕션 미적용이라, 프로덕션 베이스라인 + 해당 변경만으로 번들해 배포했다. 지금은 #115 도 롤아웃됐다(워커 v30).

통화와 금액은 짝으로만 보낸다 (#117)

앱의 우선순위 규칙(analytics_outbox.dart enqueueOrMergePurchase):

currency = server ?? catalog ?? observed;
value    = server != null ? serverValue : (catalog != null ? catalogValue : null);

서버가 통화를 주는 순간 금액도 서버 것만 쓴다. Google 은 serverValue 가 항상 null 이므로 통화만 보내면 앱이 이미 들고 있던 카탈로그 금액까지 버린다. 그래서 서버는 금액이 없으면 통화도 뺀다. 근본 원인은 응답이 출처를 알려주지 않는 것 — 앱이 APPLE_JWS(서버가 실제로 아는 값)와 GOOGLE_CLIENT_STOREFRONT(앱이 방금 보낸 값의 메아리)를 구분할 수 없다.

스냅샷의 app_build=0 은 정상

앱이 요청 본문에 app_build·app_version 을 아예 넣지 않는다 (receipt_format_helper.dart). 서버가 0/"0.0.0" 으로 채운다. 구버전 신호로 오독하지 말 것 — 스냅샷만으로는 앱 버전을 알 수 없다.

프로덕션 쓰기·조회 경로

  • DB 조회·적용은 Supabase MCP(plugin:supabase:supabase) 또는 supabase db query --file <path> --linked. PROD = xtijtefcycoeqludlngc.
  • db query 에는 --project-ref 플래그가 없다. --linked 만 있다. 감시 스크립트에서 stderr 를 버리지 말 것 — 빈 값을 0 으로 읽고 오보한 적이 있다.
  • supabase db push 는 못 쓴다. wallet-production-rollout.yml 도 경로가 아니다(매니페스트 status: blocked).
  • MCP execute_sql 과 CLI db query 둘 다 current_user=postgres 다.

(not set) 오독 주의

사용자 범위 속성은 값이 바뀌면 여러 행에 걸쳐 중복 집계된다. language 의 (not set) 은 사용자 수로 88% 지만 이벤트 수로는 19.8% 다. 초기화 전 구간을 모두가 한 번씩 지나서 생기는 정상 현상이다. 사용자 수로 판단하지 말 것.

5. 되돌리기

매출 키를 즉시 끄려면 SQL 한 줄. 재배포 불필요하고, 앱은 카탈로그 짝으로 자동 복귀한다.

update public.wallet_runtime_flags
   set value_json = 'false'::jsonb, version = version + 1
 where flag_key = 'wallet.purchase_revenue_fields_enabled';

6. 상태 확인 쿼리 (복붙용)

공급자별 통화·금액 확보율

select s.provider,
       count(*) as settlements,
       count(*) filter (where s.analytics_currency is not null) as with_currency,
       count(*) filter (where s.analytics_price_milliunits is not null) as with_value
from public.wallet_provider_event_inbox i
join public.purchase_reward_snapshots s on s.id = i.result_id
where i.created_at >= now() - interval '3 days' and i.status = 'SUCCEEDED'
group by 1 order by 1;

기대: APPLE 은 통화·금액 100%, GOOGLE 은 통화만(금액 0 이 정상).

앱이 실제로 받는 값(응답 경계)

select a.currency, a.value, a.currency_source
from public.wallet_provider_event_inbox i
join lateral public.get_purchase_analytics_for_inbox(i.id) a on true
where i.id = '<inbox_id>';

단, 이것도 서버가 아는 값이다. 앱이 받았는지는 GA4 에서 확인한다(아래).

배포본에 게이트 수정이 살아 있는지

# MCP get_edge_function 으로 소스를 받아
grep -c 'actualType === "PURCHASE"'      # 1 이어야 한다
grep -c 'actualType === "MOBILE_PURCHASE"'  # 0 이어야 한다

다른 세션이 워커를 재배포해도 #118 은 main 에 있으므로 자연히 포함된다. 재배포 후에는 이 두 줄로 확인하라.

GA4 끝단

탐색 → ✅ 실제 매출 (purchase 전용)(속성 picnic-423500 / 441670286, 시간대 GMT+9). 행에 날짜 + 시간(YYYYMMDDHH)·통화를 추가하고 열은 플랫폼. DB 정산 시각(KST)과 시간 단위로 대조한다. 확인 후에는 기간을 지난 28일, 행을 날짜로 되돌려 놓을 것.
