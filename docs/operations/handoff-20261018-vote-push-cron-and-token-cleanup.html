1. 한 일

1-1. 크론을 30분 간격으로 전환 완료

  • 문제. notify-vote-progress 는 시간대 그룹마다 현지 09:30·12:30·18:30·21:00(±15분)에 알림을 보낸다. 크론 4개(jobid 50~53)는 UTC 00:30·03:30·09:30·12:00, 즉 KST 기준 시각에만 돌았다. 그래서 Asia/Seoul 그룹(KR·JP·국가 없음)만 네 번을 모두 받았고, 7개 그룹은 한 번도 받지 못했다.
  • 변경. picnic-supabase PR #233(1a3da1f). 새 크론 jobid 98 notify-vote-progress-every-30m, 일정 0,30 * * * *. 이전 크론 50~53 은 지우지 않고 비활성으로 바꿨다. 컷오버 킷은 supabase/prod-cutover/20261017-vote-progress-cron-every-30m/ 다.
  • 리뷰. Codex 교차 리뷰는 HOLD 였다. 지적은 두 가지였다: 명령 비교가 대소문자를 무시하는 문제, 일부만 활성인 상태에서도 적용이 시작되는 문제. 둘 다 고친 뒤 GO 를 받았다.
  • 적용. 2026-10-18 01:10:13. 적용과 원장 기록(20261017010000)은 한 트랜잭션이다. 적용 전에 rollback 리허설을 했다.

1-2. 일일 DB 점검 루틴 프롬프트 수정 완료

  • 대상은 클라우드 루틴 trig_01Rt3PFebBYi1mVtQk2wA7HK(09:10 KST 리포트)이다.
  • notify-vote-progress 설명을 "jobid 50~53, 하루 4회"에서 "jobid 98, 30분 간격, 하루 48회"로 바꿨다.
  • health 쿼리에 vote_progress_jobs 항목(jobid·active·runs_24h·last_run)을 더했다. 리포트는 다음 경우 WARNING 을 낸다: jobid 50~53 이 10/18 01:10 뒤에 실행됨, jobid 98 이 비활성이거나 없음, 활성 job 이 2개 이상.
  • 함수가 이제 30분마다 돌므로, 리포트 창(18:10~00:10)에도 이 함수의 pg_net 응답 행이 들어온다.
  • 수정한 쿼리는 운영에서 읽기 전용으로 실행해 확인했다. 수정 전·후 프롬프트와 diff 는 로컬 비공개 폴더에 있다(§6).

1-3. send-push 실패 원인 완료

  • 01:30~12:00 의 send-push 요약 로그([send-push] summary, function_logs)를 집계했다. 실패가 있었던 호출은 21건, 실패는 44건이다. 44건 모두 UNREGISTERED 였다. 대부분 Android 였다.
  • UNREGISTERED 는 FCM 이 그 토큰을 다시 받아들이지 않는다는 뜻이다(앱 삭제, 토큰 교체 등). 서버 결함은 아니다.
  • send-push 가 이 토큰을 지우지 않아서, 같은 토큰이 실행마다 다시 실패했다. 예: Seoul 그룹 호출(41건 중 4건 실패)이 03:30·09:30·12:00 에 같은 결과를 냈다.

1-4. 무효 토큰 정리 수정 머지 완료, 배포 전

  • picnic-supabase PR #238, squash baaf2a4.
  • 동작. FCM 이 UNREGISTERED 로 답한 토큰만 정리한다. 발송이 끝난 뒤, 그 토큰 값을 그대로 가진 user_push_tokens 행에서 해당 플랫폼 칸만 null 로 바꾼다. 행은 지우지 않는다.
  • 제한. UPDATE 하나에 토큰 50개. UPDATE 하나는 4초 뒤 중단한다. 정리 전체는 8초 안에서만 새 UPDATE 를 보낸다. 서비스 롤 호출만 정리한다.
  • 로그. 요약 로그에 unregisteredCleared·clearErrors·clearSkipped 를 더했다.
  • 검증. push 테스트 79개 통과. 변이 7개를 테스트가 모두 잡았다. Codex 교차 리뷰(GPT-6.1-Sol high)는 1차 HOLD(정리 요청에 시간 제한 없음, High 1건)였고, 수정 뒤 재검토에서 GO 를 받았다.
  • CI. edge preflight gate 가 소스 지문 불일치로 실패했다. 인벤토리 지문을 c1387649… 로 갱신하고 근거 문서 docs/operations/push-clear-unregistered-2026-10-18.html(picnic-supabase)을 추가했다.
  • 일괄 정리는 하지 않는다. 어떤 토큰이 무효인지는 보내 봐야 안다. 발송할 때 걸리는 토큰부터 지워진다.

2. 다음 작업

A. send-push 운영 배포 승인 필요

send-push 는 일반 supabase functions deploy 로 배포하지 않는다. import map 없이 빌드하면 하위 패키지 4개의 버전이 바뀐다. 10/16 배포와 같은 방식(고정 import map 으로 만든 빌드 파일 + canary 실행 도구)을 쓴다. 자세한 방식은 picnic-supabase docs/operations/push-deploy-canary-2026-10-16.html 에 있다.

실행 도구 scripts/security/edge_canary.py 는 10/16 배포 전용으로 고정돼 있다. 그래서 먼저 도구를 이번 배포에 맞게 바꿔야 한다.

  • ORIGINALS 에 10/15 에 관측한 원본(send-push v56, my_artist v61)이 하드코딩돼 있다. 지금 운영본은 send-push v57, my_artist v62 다. 되돌리기 기준을 v57 로 바꿔야 한다.
  • SOURCE_SHA 가 d4c8986 이다. 새 빌드의 기준은 main baaf2a4 다.
  • ops/edge/send-push/manifest.json 에 실행 도구 sha256, 빌드, 출처 증명이 들어 있다. 도구를 바꾸면 manifest 도 다시 만들어야 한다(scripts/security/edge_canary_manifest.py). scripts/security/test_edge_canary.py 도 같이 맞춰야 한다.
  • 이번 배포는 send-push 만 바꾼다. my_artist(v62)는 그대로 둔다. 새 send-push 도 동시 발송을 유지하므로 my_artist 와 함께 동작한다.

진행 순서(제안):

  1. 현재 운영본 send-push v57 을 내려받아 백업한다. 읽기 전용이다.
  2. baaf2a4 로 고정 import map 빌드를 만든다. 실행 도구, manifest, 테스트를 v57 기준으로 바꾼다. 이 변경은 picnic-supabase PR 로 만들고 교차 리뷰를 받는다.
  3. 리허설 계획(임시 함수 배포, canary 사용자 1명 발송)을 정리해 승인을 받는다.
  4. 승인 뒤 배포한다. 다음 투표 진행 알림 실행에서 요약 로그의 unregisteredCleared 가 0보다 크고, 같은 토큰의 반복 실패가 줄어드는지 본다.
  5. 문제가 있으면 v57 로 되돌린다. 이미 비운 토큰 칸은 앱이 다음에 등록할 때 다시 채운다.

4. 상태를 다시 확인하는 쿼리 (읽기 전용)

-- 크론 상태와 컷오버 뒤 실행 수
select j.jobid, j.jobname, j.schedule, j.active,
       (select count(*) from cron.job_run_details d
         where d.jobid = j.jobid and d.start_time > '2026-10-18 01:10+00') as runs_since_cutover,
       (select count(*) from cron.job_run_details d
         where d.jobid = j.jobid and d.start_time > '2026-10-18 01:10+00' and d.status <> 'succeeded') as failed
  from cron.job j
 where j.command ilike '%notify-vote-progress%'
 order by j.jobid;

-- 최근 6시간의 함수 응답(대상 그룹, 성공·실패 수)
select created, status_code, timed_out, left(content, 200) as body
  from net._http_response
 where content like '%targetTimezones%'
 order by created desc;

send-push 실패 코드는 로그에서 본다(Supabase MCP query_logs, source function_logs, 메시지 [send-push] summary). 요약 로그에는 토큰과 사용자 ID 가 없다.

5. 조사할 때 알아둘 것

  • 운영 postgres 롤은 cron.job 을 UPDATE 할 수 없다. cron.alter_job·cron.schedule·cron.unschedule 을 쓴다.
  • net._http_response 는 약 6시간만 보존한다.
  • notify-vote-progress 실행 시간은 push_messages(data.type='vote_progress')의 첫·마지막 행 시각으로 본다. function_edge_logs 는 회차의 약 25% 가 빠진다.
  • picnic-supabase 에서 supabase/functions/ 아래 런타임 파일을 바꾸면 edge preflight 인벤토리의 소스 지문을 갱신해야 한다. 근거 문서의 #freshness 절도 함께 쓴다.
  • 교차 리뷰 전 사용량 라우트가 blocked(예: Orca 캐시 낡음)이면 작업자를 띄우지 않는다. 10/18 재검토 때 게이트가 셸에서 작업자 실행을 막지 못해 작업이 한 번 잘못 전달됐다. 리뷰어를 즉시 중단했고 그 작업은 실패로 정산했다.
