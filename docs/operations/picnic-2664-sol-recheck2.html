A→B→A async 테스트가 지연 오염을 놓친다는 판별력 지적해소wallet_provider_test.dart:2366-2374가 두 번 queue drain 후에도 99가 나타나지 않음을 다시 확인한다. 즉시 쓰기만 피하고 다음 event turn에 stale 쓰기를 하는 구현은 이제 실패한다.

차단 지적

[major] 실패한 refresh가 정상 정산을 영구적으로 화면에서 잃게 할 수 있다

파일/위치: picnic_lib/lib/presentation/providers/wallet_provider.dart:407-423, 533-546.

재현 조건: owner A에서 정산을 시작하고 같은 owner의 새 Session(토큰 갱신) 이벤트가 전달된 뒤, 정산 응답 S를 setSummary에 넣어 event queue에 예약한다. 같은 turn에 refresh()를 시작하고 repository가 microtask에서 실패하게 한다. refresh의 오류 분기는 아직 화면에 있던 이전 값 P를 AsyncData(keep)로 다시 쓰면서 _reReads를 증가시킨다. 이어 실행된 정산 callback은 카운터 차이만 보고 S를 폐기한다. 최종 화면은 P이고, 실패한 재조회에는 서버의 지급 결과가 포함되지 않았으므로 “폐기해도 이미 재조회 결과에 들어 있다”는 근거가 성립하지 않는다.

영향: 정산 자체는 서버에서 성공했는데 화면에는 이전 잔액이 남는다. 이 경로는 후속 refresh를 예약하지 않으므로 사용자가 다시 당겨 새로고침하거나 다른 재조회 계기가 오지 않으면 지급 잔액이 계속 보이지 않는다. 투표 실패 후 best-effort refresh 및 여러 UI 수동/백그라운드 refresh 호출과 겹칠 수 있다.

최소 수정 방향: “서버 값을 성공적으로 반영한 refresh”와 “오류 후 기존 로컬 값을 유지한 refresh”를 구분한다. 성공 또는 signed-out처럼 authoritative 상태를 실제로 얻은 경우에만 지연 정산을 앞서는 sequence를 올리고, 오류 fallback은 sequence를 올리지 않아 예약된 정상 정산이 적용되게 한다. 같은 세션 교체 조건에서 실패 refresh가 먼저 끝난 뒤 S가 최종값이 되는 회귀 테스트를 추가한다.

순서·카운터 경로 검토

  • 즉시 성공 refresh: 해소. refresh가 70을 쓴 뒤 카운터가 달라져 지연 99를 폐기한다.
  • 느린 refresh: 계약 유지. 지연 정산이 먼저 적용되고, 나중에 완료한 성공 refresh가 최종 상태를 정한다.
  • 실패 refresh: 위 major. 기존 값을 재게시한 행위까지 authoritative re-read로 계산해 정상 정산을 과잉 차단한다.
  • 연속 refresh: 성공한 재조회가 하나라도 정산 뒤 완료되면 정산 폐기는 타당하다. 모두 실패하거나 첫 실패만 정산 callback보다 먼저 끝나면 위 손실이 발생한다.
  • signed-out 조기 반환: :363-366에서 카운터가 증가하며, 동시에 owner가 null이어서 _ownsWrite도 실패한다. 이전 계정 정산을 signed-out 화면에 쓰지 않는 계약과 일치한다.
  • refresh 상태 쓰기 포괄성: signed-out, 오류 fallback, 성공/오류 최종 state 쓰기에는 모두 증가가 있다. superseded read의 조기 반환은 상태를 쓰지 않으므로 누락이 아니다.
  • build/invalidateSelf: 이 카운터는 build 결과 게시를 추적하지 않는다. 현재 production 검색에서 wallet provider를 외부에서 직접 invalidate하는 호출은 없고, 내부 invalidate는 계정 전환 epoch 또는 refresh 신원 가드와 결합되어 있어 새 차단 결함으로 승격할 구체 재현은 찾지 못했다. 향후 외부 invalidate가 추가되면 build 완료와 지연 정산의 순서 보호가 별도로 필요하다.
  • 잦은 백그라운드 재조회: 세션 인스턴스가 그대로인 통상 정산은 동기 적용되어 카운터 가드 대상이 아니다. 과잉 차단은 같은-owner Session 교체로 지연 분기에 들어간 좁은 창에서만 생기지만, 그 창에서 실패 refresh가 겹치면 실제 손실이다.

테스트 판별력과 남은 공백

A→B→A: queue drain 뒤 재단언이 추가되어 직전 판별력 지적은 해소됐다. stale 99를 단순히 한 턴 늦춰 적용하는 구현은 통과할 수 없다.
[minor] logout→A async 변형: 별도 테스트가 여전히 없다. 재현 조건은 auth 이벤트 미전달 상태에서 A→null→새 A Session 후 이전 A 정산 callback이 도착하는 경우다. 최소 수정은 _AsyncAuthGateway로 이 전환을 만들고 즉시 및 두 차례 flush 뒤 stale 잔액 부재를 단언하는 테스트 추가다. 현재 구현의 공통 epoch 경로는 이를 차단하므로 차단 심각도는 아니다.
