이전 지적 재검증

이전 지적판정근거
BehaviorSubject sync:false 이벤트 전달 전 A→B→A 우회해소wallet_provider.dart:446-452가 세션 인스턴스를 토큰에 담고, :500-529가 세션 불일치 시 event-queue Future 뒤 epoch/owner를 재검사한다. B와 새 A 이벤트가 먼저 전달되어 :247-250에서 epoch가 증가하므로 이전 A 토큰은 폐기된다. 실제 BehaviorSubject 기반 추가 테스트와 전체 지정 스위트가 통과했다.
이벤트 전달 전 logout→동일 A 재로그인 우회해소추가 테스트는 이 변형을 직접 다루지 않지만 코드 경로는 동일하다. currentSession은 새 A 인스턴스라 지연 분기로 가고, queued signedOut(null)과 signedIn(A)은 둘 다 최초 build owner A와 달라 epoch를 두 번 올린 뒤 Future가 실행된다. 따라서 _ownsWrite가 실패한다. notifier 재빌드가 먼저 일어나더라도 epoch는 notifier 인스턴스에 남는 keepAlive 설계(:178-197)다.
폐기 로그의 사용자 식별자 노출해소wallet_provider.dart:534는 고정 문자열만 기록한다. 변경 diff 안에 다른 식별자 interpolation은 없다. 단, PR 범위 밖 기존 코드에는 auth_service.dart:112, purchase_service.dart:861, receipt_verification_service.dart:490, tapjoy_platform.dart:51 등 사용자 ID 로그가 남아 있으며 이번 수정이 새로 만든 것은 아니다.

새 지적

[major] 지연된 정산이 더 나중에 시작한 명시적 refresh 결과를 다시 덮을 수 있다

파일/위치: picnic_lib/lib/presentation/providers/wallet_provider.dart:484-485, 522-529, 536-542.

근거: 기존 계약은 “명시적 refresh가 가장 최신”이므로 refresh는 setSummary의 snapshotAt 비교를 거치지 않는다. 하지만 세션 인스턴스가 다른 정상 token refresh 구간에서 setSummary는 이제 Future로 예약된다. 그 직후 시작한 refresh()가 즉시 완료되는 repository 응답이면 async continuation(microtask)이 event-queue Future보다 먼저 state를 갱신하고, 뒤늦은 _applySummary가 snapshot timestamp만 비교해 refresh 결과를 다시 덮는다.

재현 조건: A 정산 토큰 캡처 → 같은 A의 새 Session으로 token refresh 및 이벤트 drain → 정산 응답 S(snapshotAt=2099)을 setSummary에 전달하여 Future 예약 → 같은 turn에 refresh() 시작, repository가 R(snapshotAt=현재)를 즉시 반환 → refresh가 R을 반영 → 예약된 S가 R보다 timestamp가 크다는 이유로 다시 반영. 수정 전에는 S가 동기로 먼저 반영되고 이후 refresh R이 최종값이었다. 결과는 서버 재조회보다 앞선 정산 snapshot이 화면의 최종값이 되어, 코드 주석의 순서 계약을 위반한다.

최소 수정 방향: 지연 쓰기를 예약할 때 write/refresh generation(또는 단조 증가하는 상태-write sequence)을 캡처하고, callback 전에 그 뒤 시작·완료한 refresh가 있으면 폐기한다. 또는 애매한 auth 판정만 비동기로 해결하되 최종 적용을 refresh와 같은 직렬화 순서 안에 넣는다. 즉시 완료 refresh와 느린 refresh 양쪽을 포함한 회귀 테스트를 추가해야 한다.

과잉 차단·경합·순서 검토

  • 같은 계정 토큰 갱신: 수정된 테스트가 event turn 뒤 cotton 40과 repository 호출 1회를 확인하므로 정상 정산을 전부 버리는 구현은 잡는다. 단, 위 refresh 경합은 검증하지 않는다.
  • 콜드스타트 세션 복원 지연: build/read의 세션 대기 및 identity 검사는 이번 커밋에서 변하지 않았다. 세션 없는 상태에서 캡처한 타 계정 쓰기를 새 로그인에 적용하지 않는 기존 보수적 동작도 유지된다.
  • route unmount: applier가 app-level container를 캡처하고 provider가 keepAlive이므로 route 이탈 자체는 notifier를 dispose하지 않는다. 세션 동일 보통 경로는 여전히 동기 적용된다.
  • keepAlive 재빌드: notifier 인스턴스, _authEpoch, _generation은 invalidateSelf 후 유지된다. 계정 변경으로 재빌드되는 한 턴에는 stale 쓰기가 폐기된다. container 자체 dispose면 callback의 ref.mounted 검사로 안전하게 중단된다.
  • 동시에 예약된 여러 정산: Dart event queue 등록 순서를 따르고 최종 적용 시 현재 state와 비교하므로 서로 간 snapshotAt 규칙(오래된 값 폐기, 동일 stamp는 뒤 쓰기 채택)은 유지된다.
  • refresh/build 경합: 느린 refresh는 지연 정산 뒤 완료되어 정산을 덮으므로 기존 계약과 일치한다. 즉시 완료 refresh는 위 major처럼 완료 순서가 역전된다. build/invalidation을 일으키는 실제 계정 전환에서는 epoch가 변해 stale 쓰기가 폐기된다.

테스트 커버리지 판별력

수정된 token refresh 테스트: 커버리지를 약화하지 않았다. 기존 cotton 40 및 repository 1회 단언을 유지하고 실제 비동기 적용을 기다리는 _flush()만 추가했으므로, session identity만 보고 정상 정산을 폐기하는 원 결함을 계속 잡는다.
추가 A→B→A 테스트: 원 구현의 즉시 잘못된 쓰기는 잡지만 완전한 판별력은 없다. applyWallet 직후만 단언하고 event queue를 drain한 뒤 다시 단언하지 않으므로, stale 값을 두 턴 뒤 적용하거나 callback 순서를 잘못 잡은 구현도 이 테스트를 통과할 수 있다. 최소한 await _flush() 후 cotton 10 유지와 새 세션 build 안정화를 재단언해야 한다. logout→A 변형도 별도 async 게이트웨이 테스트가 없다.

범위와 결론

코드·테스트·기존 보고서는 수정하지 않았다. 실기기 Supabase 통합과 임의 재현 테스트 파일 생성은 소유권 제약상 수행하지 않았고, logout→A 및 refresh 경합은 실제 BehaviorSubject/event-loop semantics와 해당 코드 순서를 따라 정적 재현했다. 이전 blocker와 minor는 해소됐지만 새 major 때문에 현재 HEAD 승인은 보류한다.
