2. 내 1차 리뷰의 오류 정정

정정 1차 "기각 항목"의 Riverpod 수명주기 판단이 틀렸습니다

1차 리뷰에서 저는 "ref.refresh(provider.future) 가 notifier 를 폐기·재생성하므로 진행 중이던 refreshVoteTotals 는 vote_detail_provider.dart:143 에서 차단된다 — 양방향 모두 안전" 이라고 적고 이를 반례에서 기각했습니다. 이 판단은 틀렸습니다. 이 레포는 Riverpod 3.2.1 이고:

  • Notifier 인스턴스는 element 당 1회만 생성돼 rebuild 시 재사용됩니다 — riverpod-3.2.1/lib/src/core/provider/notifier_provider.dart:543 classListenable.result ??= …
  • Notifier.ref 는 필드가 아니라 _element.ref 를 매번 읽는 getter 입니다 — 같은 파일 :60, :366-370
  • Ref.mounted 는 !_element._disposed && identical(_element.ref, this) — core/ref.dart:110
  • rebuild 는 element 를 dispose 하지 않고 새 $Ref 만 갈아끼웁니다 — core/element.dart:569

따라서 ref.refresh 후에도 ref.mounted 는 계속 true 이고, 늦게 도착한 폴링 응답은 차단되지 않습니다. 런타임으로 확인했습니다(임시 probe, 실행 후 삭제):

PROBE initial total = 5000
PROBE after refresh total = 9000
PROBE notifier identical after refresh = true
PROBE FINAL total = 5000   ← 늦은 응답이 fresh 9000 을 덮어씀

이 오류 때문에 1차 리뷰는 "수동 새로고침 ↔ 폴링 상호 덮어쓰기" 를 근거 없이 안전하다고 기각했습니다. 실제로는 실재하는 상태 오염 결함이었고, 이번 수정의 epoch 가드가 이를 닫습니다.

철회 1차 F2 의 최소 수정안(await .timeout)은 잘못된 처방이었습니다

1차에서 저는 refreshVoteTotals await 에 .timeout(8초) 를 걸라고 했습니다. Dart 의 Future.timeout 은 원본 작업을 취소하지 않습니다. 따라서 그 안을 적용했다면:

  • 8초마다 _activePollGeneration 이 풀리며 raw HTTP 요청이 계속 누적(서버 무응답 시 무한 증가)
  • 먼저 떠난 요청이 나중에 도착해 순서가 뒤바뀐 totals 쓰기 발생 — 위 정정 항목 때문에 provider 가드도 이를 못 막음

부모가 이 반례를 제기한 것이 옳았습니다. 채택된 (A)안 — 가드는 유지하고 명시적 full refresh 가 epoch 를 올려 낡은 응답을 폐기 — 이 raw 중복 없이 같은 목표를 달성합니다.

  • element dispose 후 늦은 응답 — 구 notifier 의 _element._disposed 가 true 라 ref.mounted 가 false. 새 notifier 의 _fetchGeneration 이 0 으로 시작해도 충돌 없음 안전
