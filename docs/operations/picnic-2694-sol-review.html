W=280, H=280, t=2.0, K=0이면 JMA의 상하 inset 80과 hidden chrome 약 26.9를 뺀 body는 최대 약 173.1px이다. 측정 essential은 약 191.4px이고 allScroll의 actions+submit 하단도 약 178.9px이므로, 초기 스크롤 오프셋 0에서 submit 하단이 약 5.8px 잘린다. 선행 계획의 명시적 280×280 인수 조건과 충돌한다.

2. Non-blocking 관찰

  • VoteDialogBands는 현재 유한한 형제에서는 비-flex actions/submit/tail을 먼저 측정하고 남은 높이를 Flexible.loose decoration에 주므로 의도대로 동작한다. allScroll도 actions → submit → decoration 순서라 조작부는 상단 우선이지만, actions 내부 첫 항목은 입력이 아니라 전체 사용이다. 비-flex 형제가 무한 높이를 요구하면 Flex의 unbounded main-axis layout 단계에서 예외가 나며 공통 위젯 자체의 방어는 없다. 현재 구체 형제는 유한하다.
  • resolveVoteDialogPortraitSide의 결과는 Flexible이 이미 배정한 maxHeight 안에서 decoration 자식 크기만 바꾸므로 현재 구조에서는 Flex 배정으로 되먹임되지 않는다는 주장은 맞다.
  • TextEditingController와 FocusNode는 State에 남아 있고, vote/pic의 K 0→300→0 테스트가 값 123과 focus 보존을 확인해 통과했다. selection/IME composing 및 JMA 전환은 4번의 테스트 공백이다.
  • LargePopupWidget.cardBorderRadius는 nullable 선택 인자이고 미지정 시 기존 120.r 기본값을 유지한다. voting_complete/PIC 등 비투표 호출부 변경은 없고 공유 팝업 관련 38개 테스트도 통과했다.
  • 투표 수량, 전체 사용, JMA 30:1 환산·일일 한도·보너스·검증/네트워크 처리 로직은 diff에서 바뀌지 않았다. 일반 보너스 버블과 JMA 계산·정책 패널의 위치는 바뀌었으며, validation 이동의 실제 회귀는 2번에 분리했다.
  • 변경 범위는 문서 2개, 프로덕션 Dart 5개, Dart 테스트 2개뿐이다. native/plugin/asset/pubspec 변경이 없어 Shorebird OTA의 소스 변경 범위에는 들어간다. 실제 패치 배포 성공을 검증한 것은 아니다.
