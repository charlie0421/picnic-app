B1 · 2단 body 가 라우트의 실제(애니메이션되는) 높이를 무시한다 차단 · 높음

원인 Dialog 는 본문 높이를 AnimatedPadding(padding: viewInsets + insetPadding, duration: 100ms) 로 내준다. 2단 경로는 AlertDialog 바깥 LayoutBuilder 제약에서 viewInsets 를 직접 빼 popupAvailableHeight 를 만들고(377행), 그것을 bodyHeight 로 확정한 뒤 SizedBox(height: …) 로 고정한다(layout.dart:501). 애니메이션이 진행되는 동안 실제 제약 < 고정 높이이므로 LargePopupWidget 의 Column(mainAxisSize: min) 이 넘친다. 1단 경로는 안쪽 LayoutBuilder 의 constraints.maxHeight 를 그대로 읽고 ConstrainedBox(maxHeight:) + Flexible 로 받기 때문에 프레임마다 적응한다 — 그래서 대조군 A 는 깨끗하다. 421-423행의 2단 분기는 constraints 를 한 번도 읽지 않는다.
계획 위반 설계 문서 docs/01-plan/features/picnic-2697-vote-dialog-landscape-columns-plan.html §2.1 은 “최종 렌더 높이는 기존 content LayoutBuilder의 실제 constraints를 따라 안전하게 제한한다”고 명시했다. 미이행. 같은 문서 §2.3 은 “voting_dialog_viewport_test.dart:139는 100ms AnimatedPadding을 지난 뒤 검사하므로 중간 프레임은 미검증이다”라고 이 구멍을 미리 지목해 두었는데, 신규 198건도 inset 을 고정한 채 열기만 하므로 전이 프레임을 전혀 덮지 않는다.
최소 수정 방향 열 선택은 지금의 중립 계산(되먹임 없음)을 그대로 두고, 렌더 높이만 실제 제약으로 clamp 한다. 421-423행 분기에서 final chrome = columnsLayout.showTopClose ? largePopupTopCloseChromeHeight() : largePopupHiddenChromeHeight(); 를 구해 math.min(columnsLayout.bodyHeight, math.max(0, constraints.maxHeight - chrome)) 를 VoteDialogColumns 에 넘기면 된다(레이아웃 값은 layout 객체에 남기고 렌더 높이만 별도 인자로). 회귀 테스트는 viewInsets 를 280→0 으로 바꾼 뒤 16ms 씩 pump 하며 tester.takeException() 이 null 인지 보는 것으로 충분하다(위 재현이 곧 테스트다).

원인 pill 내부 Row 를 Expanded(child: label) 로 바꾸면 비-flex 자리(주축 제약 unbounded)에서는 RenderFlex 가 assert 를 낸다. 그걸 피하려고 _RechargeButton 을 Flexible 로 감쌌는데, 그 순간 pill 이 비-flex(자연폭) 자식 → flex 자식으로 바뀐다. 남은 폭을 Expanded(amount) 와 1:1 로 나눠 pill 은 maxWidth = 절반 을 받고, 내부 Align 은 bounded 폭에서는 shrink-wrap 하지 않고 제약을 꽉 채운다(RenderPositionedBox: shrinkWrapWidth = maxWidth == infinity). 2단 경로에서 Expanded(child: recharge) 를 쓰는 것은 의도된 설계지만, 그 변경이 1단 분기까지 끌고 들어갔다.
영향 ① 민트 “충전” pill 이 디자인 대비 1.8배로 커지고, 라벨은 좌정렬·+ 아이콘은 우측 끝으로 밀린다(중앙 정렬이던 그룹이 깨진다). ② 잔액 Expanded 박스가 약 187 → 128.6 으로 줄어든다. 비-columns 분기의 잔액 Text 에는 maxLines/overflow 가 없어 자릿수가 커지면 이전보다 일찍 넘친다. ③ 승인 결정 4 “1단 560 불변”과, 구현 결과 문서 §8 의 “정상 폭의 card-scaled geometry는 유지하고, 내부 폭이 아이콘+gap보다 작을 때만…” 라는 주장과 상충한다 — 정상 폭에서도 바뀐다.
최소 수정 방향 819-820행의 비-columns 분기를 이전대로 Expanded(child: amount), recharge 로 되돌리고, pill 내부 Row 는 Expanded(label) 대신 Flexible(label) + mainAxisSize: MainAxisSize.min 으로 둔다 (unbounded 에서도 assert 가 나지 않고, bounded 에서는 여전히 라벨이 줄어든다). 600×500 의 2px 오버플로 방어(showGap/아이콘 clamp)는 그대로 유지된다. 회귀 단언으로 1단 pill 폭이 행 폭에 비례하지 않음(예: pill.width < row.width * 0.45 대신 로케일별 자연폭 근처)을 고정할 것.

2. 비차단 관찰

N1 · 충전 pill 테두리 2px 가 최소 폭·높이 측정에서 빠졌다 낮음

파일:라인 voting_dialog_widgets.dart:717-730 (columnMinimumWidth), :747-750 (rechargeLabelWidth)
근거 Border.all(width: 1) 은 BoxDecoration.padding 을 통해 Container 의 effective padding 에 상하좌우 1px 씩 더해진다. 실측: padding: 12 좌우 + 자식 10 → 공식상 34, 실제 36.
영향 (a) 좌열 최소 폭이 2px 과소 → 충전 라벨이 의도보다 2px 일찍 ellipsis. (b) preferredHeight(columns: true) 가 라벨 측정 폭을 2px 넓게 잡아, 라벨이 1줄↔2줄 경계에 있으면 좌열 높이를 최대 한 줄만큼 과소평가 → 잔액 행 하단이 offset 0 에서 잘릴 수 있다. 오버플로는 없다(좌열은 스크롤, 라벨은 Expanded).
비차단 사유 현재 매트릭스(8 뷰포트 × 3 배율 × 4 locale)에서 그 경계를 실제로 치는 조합을 만들지 못했다. 다만 앞의 두 사고와 정확히 같은 계열이므로 함께 고쳐 두는 편이 안전하다.
최소 수정 두 식에 + 2(또는 상수 _rechargePillBorder = 1 을 두고 *2)를 더한다.

N2 · 열 최소 폭 측정이 즉시 평가돼 1단에서도 매 빌드 비용을 낸다 낮음

파일:라인 voting_dialog.dart:395-396
근거 높이 두 개는 Function(double) 콜백이라 지연 평가되지만, leftMinimumWidth:/rightMinimumWidth: 는 인자로 즉시 계산된다. 따라서 keyboardVisible 이나 !singleIsUnderPressure 로 즉시 null 이 되는 세로형 폰에서도 매 빌드마다 5회의 이분 탐색(각 48회 TextPainter.layout)이 돈다.
실측 호스트(Apple Silicon) 기준 5.41 ms / 빌드. 빌드는 입력 포매터의 setState 때문에 타자 한 글자마다 발생하며, 지갑 갱신·inset 애니메이션 프레임에서도 발생한다. 중저가 안드로이드에서는 수 배가 되어 프레임 예산을 넘길 수 있다.
최소 수정 두 폭도 double Function() 으로 지연 평가하거나, (locale, textScaler, 아티스트명) 을 키로 State 에 메모이즈한다.

독립 판단 th/2.0 예외는 구현 결과를 그대로 기대값으로 굳힌 골든이다. 주석으로 근거가 남아 있고 구현이 바뀌면 깨지므로 tautology 는 아니다. viewport 테스트 14줄 수정은 커버리지를 약화시키지 않았다 — 1단 ≤560 단언이 그대로 살아 있고 2단에만 ≤800 이 적용된다. 다만 851×393 에서 무조건 ≤560 이던 단언이 경로 의존이 되어, 그 뷰포트가 실수로 2단이 되는 회귀는 이제 이 테스트가 잡지 못한다 — columns 매트릭스가 그 역할을 대신하므로 수용 가능하다.

3-3. 측정 컨텍스트 일치 여부

  • TextScaler — 측정은 MediaQuery.textScalerOf(context), 렌더는 같은 MediaQuery 하위. Dialog 의 MediaQuery.removeViewInsets 는 scaler 를 건드리지 않는다. 일치
  • Locale / Directionality — Localizations.maybeLocaleOf, Directionality.of 모두 같은 서브트리. 일치
  • 제약 폭 — rightMinimumHeightForWidth(rightWidth) 와 _buildColumnsRight 의 constraints.maxWidth 가 동일하다. SingleChildScrollView 는 세로축만 풀고 가로 tight 를 그대로 전달(_SingleChildViewport._getInnerConstraints). 일치
  • 상태 되먹임 — 열 선택 입력은 라우트 제약 + 중립 측정뿐이고, 선택 결과가 바꾸는 insetPadding 은 선택기가 읽는 LayoutBuilder 아래에 있다. 진동 경로 없음. 없음
  • DefaultTextStyle 병합 — PicnicUi.text() 는 inherit: true 라 렌더 시 AlertDialog 의 contentTextStyle 과 merge 되지만 측정은 raw 스타일을 쓴다. fontSize/family/weight/height/letterSpacing 을 전부 명시하므로 폭에 영향을 주는 속성은 남지 않는다. 기존 2694 측정에도 동일하게 적용된 전제. 영향 없음

결론: 세 번째 불일치는 있다 — 개별 위젯 폭이 아니라 body 높이 예산 자체(B1)에서 났고, 네 번째(N1, 충전 pill 테두리)도 같은 계열로 남아 있다.

7. 판정

수정 필요 — 현재 상태로 머지 불가.
  • B1 은 승인된 설계 문서 §2.1 이 명시적으로 요구한 “실제 constraints 로 최종 렌더 높이를 제한한다”를 이행하지 않아 생긴 결함이며, 실제 기기에서 키보드를 내리거나 화면을 돌릴 때마다 캡슐이 뷰포트를 넘는다(PICNIC-2694 의 핵심 보장 위반). 수정 범위는 렌더 분기 한 곳이라 작다.
  • B2 는 이번 범위 밖인 현재 출시 중인 1단 화면의 시각 기하를 바꾼다. 요구사항이 “1단 불변”을 명시했고, 어떤 테스트도 이 지점을 고정하지 않아 750건이 통과했다.
  • 두 건을 고치면서 N1(테두리 2px)과 N2(지연 평가)도 함께 처리할 것을 권한다 — N1 은 이번에 두 번 반복된 결함의 네 번째 사례다.
  • 그 외 요구사항 준수·데이터 정확성·OTA 범위·상태 보존·모서리 clip·전환 안정성은 모두 통과했고, 구현자가 보고한 수치 8종은 전건 재현·일치했다. 설계 자체(중립 측정 기반 순수 선택, 실제 텍스트 최소 폭, 해결된 반경 기반 clearance, 닫기 후보 3단계 탐색)는 견고하며 되돌릴 필요가 없다.
