02각각의 원인

① 코튼 게이트 (8/18, 8/15)

assert_cotton_runtime_ready() 는 그 NULL 을 즉시 실패로 보고, 이 게이트는 grant_ad_cotton() 안에 있다 — 글로벌픽(자체 숏폼)과 아시아픽(Pangle)의 정산이 만나는 지점이다. 락 스킵 한 번이 두 채널을 함께 내렸다.

자력 회복도 불가능했다. 재획득에 연속 클린 2회 ≈214분이 필요한데 유예는 120분이었다.

04구조적으로 바뀐 것

복구만 한 게 아니라 같은 유형이 재발하지 않게 고쳤다.

  • 게이트에서 신선도 검사를 제거했다. 임계값을 늘리는 대신 검사 자체를 뺐다 — CRITICAL 조건 4개 중 NEGATIVE_COTTON·NEGATIVE_STAR 는 CHECK 제약으로 발생 자체가 불가능하다. 3주간 CRITICAL 0건은 우연이 아니라 구조였고, 신선도 검사는 탐지 능력을 추가하지 않으면서 장애만 유발했다.
  • 하드코딩된 버전 핀을 제거했다. deployed_version <> '20260721095500' 이 두 곳에 있었다. 지금 DB 전체에 이 문자열을 가진 함수는 0개다.
  • 감지 알람 3종을 붙였다. cron 76, 매분. 게이트 프로브가 assert_cotton_runtime_ready() 를 직접 호출해 실패 사유 문자열까지 잡는다. 8/18 장애에 소급 적용하면 T+2분에 울린다. 7일 백테스트 오탐 0건.
  • 하트비트 알람이 스스로 닫히게 했다. resolve 분기가 없어 wallet:heartbeat:wallet-reconciliation 이 7/29부터 942회를 삼키며 사실상 꺼져 있었다.
  • 점등 블로커를 해소했다. assert_cotton_issuance_ready 가 타임아웃으로 실패해 코튼·프로모션 플래그를 켤 수 없었다. 원인은 active_bonus_amount 의 SET search_path 가 인라인을 막아 행마다 함수를 호출한 것. 셋 기반 재작성 + 부분 인덱스로 1.32초가 됐다.

05반드시 알아야 할 함정

이번에 실제로 밟은 것들. 다음 사람이 같은 데 빠지지 않도록.

① supabase-js 는 권한 오류를 예외로 던지지 않는다

{ error } 로 반환한다. error 를 확인하지 않는 호출부는 실패해도 성공처럼 로그를 남기며 지나간다. track-country 는 콘솔에 country updated KR 을 찍으면서 행은 안 바뀐 채 6일을 보냈고, 신규 가입자 797명의 국가정보가 그렇게 사라졌다.

② service key 로 만든 클라이언트가 service_role 이 아닐 수 있다
createClient(URL, SERVICE_ROLE_KEY, {
  global: { headers: { Authorization: req.headers.get('Authorization') } }
});   // ← 롤은 JWT 가 정한다. 즉 authenticated

service key 는 apikey 일 뿐이다. 이 패턴을 쓰는 엣지 함수가 7개 있다 — ad-reward-claim · ad-reward-status · artist-request-add · callback-ad-shortform-more · exchange-star-candy-to-jma · expiring-bonus · track-country.

③ deferred constraint 는 rollback 리허설로 잡히지 않는다

백필 첫 시도가 커밋 시점에 WALLET_BONUS_PROJECTION_MISMATCH 로 거부됐다. begin ... rollback 리허설은 통과했는데도 그랬다 — 투영 검사가 DEFERRED constraint 트리거라 커밋할 때만 실행되기 때문이다. 리허설에 set constraints all immediate 를 넣어야 실제 커밋과 같은 검증이 된다.

④ skip_sync_bonus 는 계약이다

app.skip_sync_bonus='1' 을 켜면 sync_or_enqueue_bonus 가 유저별 app.bonus_skip_dirty_* 를 세우고 프로필 갱신을 건너뛴다. 호출자가 프로필을 직접 맞추고 dirty 플래그를 리셋해야 한다. 끄면 트리거가 프로필을 옮기므로 수동 갱신은 이중 반영이다. skip 은 한 유저에 수천 행 쓰는 대량 경로용이다(12,800버킷 92초→0.4초).

⑤ 소급 지급 시 ad_reward_events.created_at 을 now() 로 넣지 말 것

check_ad_view_fraud 의 burst 판정이 MAX(created_at) 기준 10초다. 실행 직후 10초 내에 실제 광고를 정산하는 대상 유저가 그 광고를 영구 DENIED 로 잃는다. 원본 issued_at 으로 백데이트해야 한다.

또 ad_campaigns 는 RLS 로 wallet_command_owner 에게 0행으로 보인다. 금액 검증은 SET ROLE 이전에 postgres 로 해야 한다.

⑥ 지급 기록의 type 이름을 믿지 말 것

투표 100표당 보너스는 type='GIFT' 로 기록된다. 이름만 보면 선물/증정이라 투표 보상과 연결되지 않는다. 실제 식별자는 vote_pick_id 가 채워진 GIFT 원본 행(parent_id is null)이다. type='VOTE_SHARE_BONUS' 만 보고 "1년 8개월 중단"으로 오판했는데, 그건 2024년 45건이 전부인 별개의 미연결 기능이다.

08남은 것

  1. 1app #163 머지

    문서 변경만. RLS 핸드오프에 anon 쓰기 회수를 0단계로 편입한 내용이다.

  2. 2anon 쓰기 32개 회수 — RLS 과제 0단계

    공개 앱 키로 vote·vote_item·artist·config·version 등의 행을 지울 수 있는 상태다. RLS 과제 착수가 늦어질 것 같으면 vote·vote_item·artist·artist_group·vote_reward 다섯만 먼저 닫아도 된다 — 앱에 쓰는 코드가 없고 어드민은 authenticated 권한을 이미 갖는다. grant 한 줄로 되돌아간다.

  3. 3RLS 도입

    별도 과제. handoff-rls-rollout.html 참조. 지금은 authenticated 가 RLS 없이 전 행을 읽으므로, 계정 하나만 만들면 타인의 광고 이력·이메일·생년월일을 조회할 수 있다.

  4. 4Slack 전용 채널 확인

    WALLET_ALERT_WEBHOOK_URL 을 등록해 영수증 채널에서 분리했고 자가진단으로 실도달을 확인했다. 실제 장애 알람이 그 채널에 잘 뜨는지는 첫 발화 때 확인이 필요하다.

  5. 5경미 — 정리 대상

    비로그인 앱의 get_active_promotion_campaigns·get_wallet_summary 401(앱에서 스킵 처리 권장). idx_bonus_history_balance(30MB)가 신설 인덱스에 포섭돼 드롭 후보. credit_vote_share_bonus 등 미연결 래퍼 4종 — 삭제하지 않기로 결정했다(manifest 양방향 assert + 동결 스키마 수정이 필요해 이득 대비 비용이 크다).

09내가 틀렸던 것

기록에 남겨야 다음 사람이 같은 길로 안 간다.

  • upsert_ad_bonus permission denied 를 만성 노이즈로 분류했다. 실제로는 Tapjoy 7일 지급 중단이었다. 가짜 에러가 시간당 수천 건 쌓여 있으면 진짜를 못 본다 — 그래서 #95 로 노이즈 하나를 정리했다.
  • 투표 보너스를 "1년 8개월 중단"으로 판단했다. type='VOTE_SHARE_BONUS' 만 봤기 때문이고, 실제 기록은 type='GIFT' + vote_pick_id 였다. 사용자 지적으로 바로잡았다.
  • track-country 를 고쳤다고 잘못 보고했다. 검증 쿼리가 updated_at 갱신 + country_code is not null 이라 원래 값이 있던 기존 유저를 셌다. 신규 가입자 기준으로 보면 4명 전원 NULL 이었다. 검증은 "쓰기가 성공한 행"을 세야 한다.
  • 버전 핀 위험을 과장했다. "다음 워커 재배포 때 터진다"고 썼는데, deployed_version 을 쓰는 함수가 없어 재배포로는 안 바뀐다. 위험은 미래 마이그레이션이 재시드할 때다.
