2. 구현자용 최소 계획

Goal: cold visible 이미지가 관측 다음 프레임에 요청에 진입하고 첫 decoded frame을 바로 그린다. Architecture: 기존 visibility/lazy 상태와 단일 Image pipeline을 보존하고 시간 기반 최초 진입 대기만 없앤다. Stack: 설치 Flutter, visibility_detector 0.4.0+2, cached_network_image 3.4.1. Spec: 이 dispatch의 “불필요한 표시 대기 제거, 독립 스크롤/요청 제한 보존” 요청. 아래 구현은 후속 담당자가 수행한다.

  1. 먼저 실패 테스트: 새 visibility 테스트 파일에서 controller를 실제 기본 500ms로 되돌린 뒤, prefetch/성공 기록 없이 실제 PNG cold 요청 및 첫 픽셀이 100ms 미만의 테스트 시간에 나타나는지 확인한다. 현재 소스는 visible 기본값/명시 viewport 테스트에서 실패해야 한다.
  2. 공통 interval: initState에서 첫 detector가 만들어지기 전에 아래 설정을 적용한다. app별 main 변경이나 모든 호출부 none 전환은 필요 없다. 테스트의 이전 singleton 값은 각 테스트가 복원한다.
@override
void initState() {
  super.initState();
  // Visibility gates use post-frame geometry; request throttling stays in Image.
  VisibilityDetectorController.instance.updateInterval = Duration.zero;
  _initializeLazyLoading();
  if (widget.enableMemoryOptimization) {
    _PicnicCachedNetworkImageState._optimizeImageCache();
  }
}

Duration.zero도 build/paint 도중 콜백을 실행하지 않고 프레임 끝에 묶어서 실행한다. 설치 구현:153 변경 전에 이미 예약된 500ms callback에는 설정 변경이 소급 적용되지 않는다. 이 계획은 새 mount/앱 시작 경로를 보장하며, 기존 mount에 대한 hot reload를 완료 검증으로 쓰지 않는다. notifyNow()를 build/init마다 호출해 전역 콜백을 강제 실행하는 우회는 넣지 않는다.

  1. 최초 지연 경로 제거: _triggerLazyLoad를 아래처럼 만들고 _lazyLoadTimer, _calculateLoadDelay, _cancelLoading 및 이에만 연결된 visibility의 low-priority else-if, dispose/URL 변경 cancel 문을 제거한다. _retryTimer, _imageTimeoutTimer, 모니터 프레임 예약은 유지한다. load-state 전이, URL 교체 post-frame 및 generation 검사는 유지한다.

  1. 호환성: LazyLoadingStrategy, ImagePriority, ImageComplexity의 이름/멤버/순서, constructor named arguments와 저장된 값은 유지한다. viewport를 기본값으로 유지한다. preload/progressive는 현재도 같은 visibility 진입과 단일 provider로 동작하며 실제 호출부는 0건이다. 새로운 prefetch나 다중 decode 의미를 부여하지 않는다. lazyLoadDelay는 source-compatible하게 받되 더 이상 첫 표시를 늦추지 않는다고 문서화한다. priority가 이제 시간 지연을 결정하지 않는다는 주석도 갱신한다. 이 동작 변경은 의도적이고 실제 앱 호출부에 lazyLoadDelay 전달은 없다.
  2. 검증: 아래 새 테스트, 기존 scroll/cache/decode/retry/prefetch 집중 테스트를 실행한다. helper의 옛 200ms 기대값을 바꾸고, extended 테스트의 구현과 무관한 자체 삼항 계산은 삭제하거나 실제 helper 호출로 교체한다. enum constructor 기본값 테스트는 유지한다. 다른 파일 리팩터링은 하지 않는다.

5. 변경 금지 불변식과 판단 한계

  • Prefetch: scope 기본2:8, 허용1~3:76, 전역 active2:88, 인접 rank scope3:43를 유지한다. scope2/3는 후보 수이지 동시 네트워크 수가 아니다. scheduler는 raw provider precache를 쓰므로 자체 scroll-aware 제한은 없고 독립된 소량 speculative 작업이다. display를 이 큐 뒤에 넣지 않는다.
  • Request/decode: ResizeImage(CachedNetworkImageProvider):62 단일 provider와 동일 key, fit/no-upscale, 2000px·2,000,000px cap:103 및 화면별 q/DPR override 유지. enum progressive를 다중 URL/원본 decode로 되살리지 않는다.
  • Cache: 성공 Set은 진입 힌트(init:323), 정확한 provider cache probe는 별도(probe:702). imageCache.containsKey는 pending/keepAlive만 확인(설치 구현:455); 모든 live-only 항목 또는 파일 cache가 즉시 decoded-ready라는 뜻은 아니다. 배치 제거가 캐시 key·LRU·에러 eviction·성공 판정을 바꾸어서는 안 된다.
  • 실제 다운로드: cache manager 기본 concurrentFetches10:17 및 내부 queue:48 유지. 이는 설치된 manager의 다운로드 제어이며 앱의 모든 네트워크 요청에 걸린 전역2라는 의미는 아니다.
  • 범위: 이미 build된 완전 offscreen cold 이미지와 아직 build되지 않은 lazy-list 항목의 억제를 보존한다. 이미 진행 중인 요청을 스크롤 시 취소하거나 성공 기록에 따른 기존 eager 진입을 새로 제한하지 않는다. 10%/5% visibilityThreshold 자체의 의미는 유지하므로 “1픽셀이라도 보이면 요청”으로 바꾸려면 별도 공간 정책 변경이다.
  • 근거 수준: 설치 소스와 43개 호출부 감사로 확정한 구현 경로이며 이번 dispatch에서 새 테스트/기기 측정은 수행하지 않았다. 보고서의 테스트 코드와 명령은 후속 검증안이다. 이전 device 검증 또는 coordinator의 테스트 통과를 이 수정안의 통과로 인용하지 않는다.
