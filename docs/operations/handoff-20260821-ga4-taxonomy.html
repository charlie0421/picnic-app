코드는 이미 프로덕션에 나가 있다. GA4 택소노미는 1.3.0+130007 바이너리에 포함돼 8/13 공개·강업으로 배포됐고, 그 릴리스에 패치는 0건이다. 즉 지금 이 순간에도 프로덕션 GA4 속성으로 이벤트가 들어가고 있다.

③ 대행사 회신 — 수신 완료

2026-08-21 A-1~B-10 답변을 받았다. 구현 판단에 직접 영향을 주는 결론은 다음과 같다.

  • click_attendance는 시점이 사라져 삭제 처리됐다.
  • vote 가산 파라미터 3종과 virtual_currency_name 전송값에 이견이 없다.
  • user_id UUID는 고객을 유추할 수 없다면 허용된다.
  • purchase.currency는 필수 전송해야 한다.
  • 값이 없는 Number 파라미터는 키 자체를 빼고 전송한다.
  • 자체 숏폼 ad_click은 전체화면 CTA 클릭 시점으로 확정됐다.
  • sign_up은 별도 가입 시점을 잡을 수 없다면 제안한 휴리스틱을 허용한다.
  • B-10 이벤트명 변경은 중복 적재 확인 뒤 결정한다. DebugView 실측 전에는 변경하지 않는다.

④ 복구 구매의 매출 복원 — 설계 승인 / 구현 미착수

현재 코드는 정산 시점에 스토어 카탈로그가 메모리에 없으면 currency/value 없이 purchase를 확정할 수 있다. 대행사 B-2를 충족하기 위해 다음 계약을 선택했고 교차 검증에서 최종 승인받았다.

승인된 불변식: currency를 확보하지 못한 revenue-bearing purchase는 GA4로 보내지 않고 durable outbox의 awaiting_currency에서 재시도한다. 실제로 GA4에 전송되는 모든 매출 purchase에는 ISO 4217 currency가 있어야 한다. value만 없을 때는 B-3에 따라 그 숫자 키만 생략한다. 결제 지급 성공과 GA4 보류는 분리한다.

승인 설계: docs/superpowers/specs/2026-08-21-ga4-purchase-revenue-contract-design.md
커밋: 5bb861418 docs(analytics): finalize purchase revenue contract

교차 리뷰가 확인한 주요 안전장치:

  • analytics 통화·가격을 환불 정산용 providerCurrency/providerPaidAmountMinor와 분리해 QUANTITY 불변식 보존
  • Apple JWS price 밀리유닛을 GA4 메이저 단위로 정확히 변환
  • Shorebird OTA와 맞지 않는 app_build 게이트 대신 현재 요청의 parser capability 사용
  • grant 트랜잭션에서 immutable analytics snapshot을 원자 저장하고 inbox 전용 최소권한 RPC로 최초·replay 응답 복원
  • Android client_observed_currency를 foreground·queue recovery·서버 envelope까지 전달하되 intake identity hash에서는 제외
  • 구버전 앱에는 기존 7-key 응답을 유지하고, 앱 선배포 뒤 서버를 배포하는 순서 고정
아직 코드는 구현되지 않았다. 5bb861418은 설계 문서 전용 커밋이다. 앱 코드·Supabase Edge Function·SQL migration·테스트·배포는 모두 후속 작업이다. 로컬 가격 시각 매칭 방식(b5b138bd1)을 되살리지 말고 승인 설계를 따른다.

⑤ 다음 실행 순서

  1. 앱 워크트리: forward-compatible parser, parser capability, ISO currency gate, durable outbox awaiting_currency, receipt queue hand-off를 RED→GREEN으로 구현한다.
  2. 앱 회귀 검증: 기존 7-key, currency-only, value-only, queue recovery, alias dedup, dead-letter·sink 차단 테스트를 통과시킨다.
  3. Supabase 별도 워크트리: analytics snapshot migration/RPC, Apple·Google verifier, runtime flag, capability 기반 응답 shaping을 RED→GREEN으로 구현한다.
  4. 서버 회귀 검증: QUANTITY 정산 필드는 계속 null인지, 최초·replay가 같은 snapshot을 반환하는지, capability 없는 앱이 7키만 받는지 검증한다.
  5. 교차 리뷰: 결제·개인정보·migration 변경이므로 반대 공급자 Frontier 리뷰를 수행한다.
  6. 운영 게이트: migration apply·배포·PR·merge는 별도 승인 전 수행하지 않는다. B-10은 실기기 DebugView에서 중복 여부를 확인한 뒤에만 이벤트명을 결정한다.

4. 함정

테스트에서 저장소를 쓰는 새 소비자를 추가할 때. globalStorage(NonWebLocalStorage)의 정적 SharedPreferences future 는 자신이 생성된 testWidgets 존에 묶인다. 그 존이 끝난 뒤 다른 테스트에서 await 하면 영원히 완료되지 않고, ioTimeout 도 pump 없이는 진행되지 않아 소용없다. PurchaseService 를 세우는 위젯 테스트는 반드시 메모리 저장소를 주입하라. AnalyticsOutbox, PurchaseAnalyticsDedup, AnalyticsSendMarkerStore 모두 해당한다.
Shorebird 릴리스는 버전 번호로만 구분된다. shorebird.yaml 의 app_id 가 단일이라 스테이징/프로덕션이 같은 앱을 공유한다. 1.3.0+130007 에 패치를 쏘면 곧 프로덕션 전체 사용자 배포다.
에셋을 추가한 커밋은 OTA 로 나갈 수 없다 — 단, 지금 130007 에는 해당 없음. 에셋은 바이너리에 번들되므로 패치로 전달되지 않는다. --allow-asset-diffs 는 경고를 넘길 뿐 에셋을 전달하지 않는다.

8/10 에 #156 의 splash_key.png 때문에 OTA 기준 커밋을 제한한 적이 있으나, 그 판단은 구 릴리스 130001 기준이었다. 현재 활성 릴리스 1.3.0+130007 태그에는 해당 에셋이 이미 포함돼 있어(git cat-file -e picnic-v1.3.0+130007:picnic_app/assets/splash_key.png 확인) 130007 대상 패치에는 걸리지 않는다. 원칙은 유효하니 새 에셋이 추가되면 그때 다시 판단하라.

7. 이 작업에서 리뷰가 잡은 것

같은 실수를 반복하지 않기 위한 기록. 상세는 implementation-report.html.

반대 공급자 교차 리뷰 4회 + 되돌린 후속 작업 3회에서 배포됐다면 매출 데이터를 왜곡했을 결함들이 나왔다.

  • replayed 플래그를 발송 증거로 오용 → 매출 영구 누락
  • purchaseID 없는 결제가 전부 같은 transaction_id 로 뭉쳐 두 번째 매출부터 소실
  • dedup 동시성 경쟁으로 중복 발송
  • 마커를 전송 전에 저장 + Sink 가 실패를 은폐 → 영구 누락 (1차 수정이 만든 결함)
  • 스토어 거래 finish 후 재시도 경로 소멸 (2차 수정이 만든 결함)
  • 기존 AnalyticsService 가 이미 purchase 를 직접 logEvent 하고 있어, 통합하지 않았다면 매출이 2배로 잡혔을 상황

매 리뷰 라운드가 직전 수정이 새로 만든 결함을 잡았다. 결제·매출 경로를 건드릴 때는 한 번의 리뷰로 끝내지 말 것.
