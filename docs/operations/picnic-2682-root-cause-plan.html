Tapjoy의 비 UUID 사용자 ID가 DB 오류와 반복 콜백을 만드는 경로

목표: 잘못된 snuid를 UUID 컬럼에 전달하지 않고, 영구 처리 불가 콜백의 재시도를 멈추며, 앱이 사용자 ID 설정 완료 전에 오퍼월을 요청하지 않게 한다.

구성: Tapjoy 전용 서버 검증·응답 분류와 앱 SDK 준비 상태를 각각 수정한다. DB 스키마·지갑 지급 방식·네이티브 SDK 버전 변경은 이 계획의 최소 범위에 포함하지 않는다.

기술: Supabase Edge Functions / TypeScript / Deno, Flutter / Dart, tapjoy_offerwall 14.6.0. 요구사항: PICNIC-2682 및 코디네이터가 전달한 로그·7개 조사 항목. Jira 본문은 별도 조회하지 않았다.

결론: DB 오류 경로와 앱의 비동기 완료 대기 결함은 소스로 확인했다. 해당 64자리 값이 Tapjoy의 기본 기기 ID에서 나온 것인지는 유력 가설이며, SHA-256 생성식이나 실제 문제 단말의 최초 오퍼월 진입 경위는 미확인이다.
판정근거 / 한계
확정: snuid가 UUID 조회로 직행서버 extractParameters → verify → checkUserExists. UUID 검사가 없고, 서명 검증보다 사용자 조회가 먼저 실행된다.
확정: 현재 앱은 SDK 완료를 기다리지 않음Android 플러그인은 connect/setUserID 요청 직후 MethodChannel 결과를 반환하고 성공 이벤트를 나중에 전달한다. 앱은 MethodChannel Future만 await한다.
유력: 초기 기기 ID로 오퍼월이 생성됨connect 옵션에 사용자 ID가 없고, setUserID 성공 전 requestContent가 가능하다. 다만 해당 요청의 MD5 검증 결과·단말 버전·최초 요청 시점은 없다.
확정 규약 / 높은 확신의 원인: 400이 재시도 유발Tapjoy 공식 문서에서 중단 상태는 200/403이다. 같은 snuid·트랜잭션 3개가 반복된 관측과 부합한다.

2. 64 hex snuid의 출처와 앱 경합

공식 문서로 확인한 범위

Tapjoy Self-managed currency는 사용자 ID가 snuid가 되며, 미설정 시 보통 Advertising ID 등 기기 ID로 대체된다고 설명한다. SDK·기기·OS에 따라 Android ID·udid·MAC 등도 가능하다. 연결 옵션으로 ID를 먼저 주거나, 직접 설정할 때 성공 콜백을 확인하라는 지침이다. Android User properties도 SDK의 자동 ID 생성과 self-managed currency의 명시적 ID 필요성을 확인한다.

미확인: 공식 문서에서 “Android 14.6.0 기본 snuid = 특정 값의 SHA-256 64hex”라는 규칙은 찾지 못했다. 64hex 모양은 해시와 양립하지만 알고리즘·입력·생성 주체를 특정하지 못한다. 로컬 SDK 캐시에는 14.6.0 바이너리가 있으나 이 보고서는 내부 난독화 코드로 생성식을 입증하지 않았다.

앱에서 해시를 setUserID에 넣는가

picnic_lib/lib 전체의 Tapjoy.setUserID / setUserID / TJC_OPTION_USER_ID 검색 결과 Tapjoy 설정 호출은 picnic_lib/lib/presentation/widgets/vote/store/free_charge_station/platforms/tapjoy_platform.dart:48 한 곳이고 입력은 supabase.auth.currentUser!.id 원문이다. 해시 변환은 없다. picnic_lib/lib/core/utils/device_fingerprint_helper.dart:19의 SHA-256 기기 해시, 업로드 서명·영수증 해시는 존재하지만 Tapjoy 설정 경로와 연결되지 않는다. 과거 앱·다른 바이너리·서버측 Tapjoy 설정까지 배제한 것은 아니다.

가설 우선순위확신도반증 / 추가 확인 조건
1. 사용자 ID 미설정 또는 성공 전 오퍼월 진입으로 Tapjoy 기기 ID가 고정됨중간~높음(약 70%, 통계적 추정 아님). 현재 코드의 경합 존재 자체는 높음.문제 거래의 최초 오퍼월 요청 전에 SDK getUserID가 Picnic UUID이고 setUserID 성공이 확인되었거나, 해당 64hex 요청의 MD5가 잘못된 것으로 확인되면 사고 원인 가설을 재검토한다.
2. 구버전 앱·Tapjoy 외부 진입/잔존 오퍼·대시보드 설정이 기기 ID를 사용미확인, 대안 가설거래 최초 발생 시점의 앱/SDK 버전, Tapjoy 기기→publisher ID 이력 확인. 지금 앱을 패치해도 과거 거래 snuid가 바뀐다고 가정하지 않는다.
3. 앱이 자체 SHA-256을 setUserID에 전달현재 picnic_lib 소스에서는 근거 없음다른 실제 배포 바이너리·이전 코드·네이티브 호출원 발견 시 재평가.
4. 위조 또는 잘못된 콜백 재생미확인권한 있는 운영자가 로깅 없이 보관된 원시 파라미터와 올바른 키로 MD5를 오프라인 검증. 본 워커는 secrets·프로덕션에 접근하지 않았다.

3. 재시도 규약과 응답 정책

Tapjoy 공식 Server response requirements: 200은 지급 완료, 403은 알 수 없는 snuid·잘못된 verifier·영구 실패다. 이외 상태는 5분 간격으로 최대 4일 재시도한다. 5초 초과 응답과 UTF-8이 아닌 응답도 재시도 원인이다. 본문에 오류를 적어도 HTTP 400이면 재시도를 멈추지 못한다.

따라서 같은 3개 거래가 486회 반복된 현상은 현재의 400 정책으로 설명 가능하며 확신이 높다. 관측 간격 차이, 네트워크 응답 손실, Tapjoy 측 개별 설정은 미확인이다. 403 적용 뒤 기존 큐의 다음 1회 도착은 정상적인 종료 과정일 수 있다.

7-3. 403 이후에도 재시도하는 거래 찾기

WITH callbacks AS (
  SELECT timestamp,
         decodeURLComponent(extractURLParameter(
           log_attributes['request.url'], 'snuid')) AS snuid,
         extractURLParameter(log_attributes['request.url'], 'id') AS tx,
         toInt32OrZero(log_attributes['response.status_code']) AS status
  FROM logs
  WHERE source = 'function_edge_logs'
    AND position(log_attributes['request.path'], 'callback-tapjoy') > 0
),
terminals AS (
  SELECT tx, min(timestamp) AS first_403
  FROM callbacks
  WHERE match(snuid, '^[0-9a-fA-F]{64}$') AND status = 403 AND tx != ''
  GROUP BY tx
)
SELECT c.tx, t.first_403, count() AS requests_after_403,
       max(c.timestamp) AS last_seen
FROM callbacks AS c
INNER JOIN terminals AS t ON c.tx = t.tx
WHERE c.timestamp > t.first_403
  AND match(c.snuid, '^[0-9a-fA-F]{64}$')
GROUP BY c.tx, t.first_403
ORDER BY requests_after_403 DESC;

기대 결과는 0행. 처음 403이 관측창 밖이면 이 쿼리만으로 판단할 수 없으므로 첫 403이 포함된 배포 초기 창과 이후 24시간 창을 각각 보존한다. 경계 동시 요청·로그 전달 지연이 있으면 실제 응답 전송/5초 제한을 조사하고 window를 임의로 줄여 성공 처리하지 않는다.
