BLOCKER 1. ResizeImagePolicy.exact가 BoxFit.cover를 무력화한다 (종횡비 왜곡)

위치
picnic_lib/lib/presentation/common/picnic_cached_network_image.dart:1039-1043 (호출 값은 :912-921, 계산은 _computeCacheDimension :338-351)
근거
_computeCacheDimension은 절대 null을 반환하지 않는다(마지막 fallback 400). 따라서 ResizeImage.resizeIfNeeded(w, h, provider)는 항상 ResizeImage(provider, width: w, height: h)를 만들고, policy는 기본값 ResizeImagePolicy.exact다. Flutter 3.41.4 SDK 문서: 
// image_provider.dart:838-841
/// If [ResizeImage.width] and [ResizeImage.height] are both non-null, the
/// output image will have the specified width and height (with the
/// corresponding aspect ratio) regardless of whether it matches the source
/// image's intrinsic aspect ratio. This case is similar to [BoxFit.fill].
allowUpscaling: false의 클램프는 원본보다 큰 목표만 줄이므로 이 경우를 구제하지 못한다. 변경 전에는 표시용 Image가 원본 provider를 써서 네이티브 종횡비로 디코드되고 위젯의 fit이 크롭을 담당했다. 변경 후에는 디코드 단계에서 이미 눌려 나오고, BoxFit.cover는 이미 박스와 같은 비율인 비트맵을 받아 아무것도 크롭하지 않는다.
실패 조건 / 재현
실측 확인(코디네이터 독립 프로브, /tmp/picnic-image-aspect-probe.log): 신규 success_test를 복사해 위젯 height와 memCacheHeight만 40→80으로 바꾸고 fixture는 160×80(2:1) 유지 → 기대 80×40, 실제 RawImage 80×80. exit 1. 2:1 원본이 1:1로 눌렸다는 직접 증거다.

프로덕션 경로 — cdn.picnic.fan은 레포에 기록된 프로덕션 실측대로 비율 유지 리사이저다: common_banner.dart:244-253 "h 미지정 시 _hauto_, 비율 유지 리사이즈 … 원본보다 큰 w 는 업스케일 없이 원본 크기로 클램프". 즉 내려오는 비트맵의 비율은 원본 비율이고 위젯 박스 비율이 아니다.
  • common_banner.dart:227-262 — 박스 = 화면폭 × (화면폭/aspectRatio), fit: BoxFit.cover, memCacheWidth/Height = 그 논리 치수. 정사각 원본 배너라면 ResizeImage(exact, 390, 219)가 정사각을 390×219로 눌러버리고 cover는 무동작 → 배너가 수직으로 찌그러져 보인다.
  • vote_home_page.dart:341-346 — 이번 변경에 포함된 파일. width: 120, height: 100, fit: BoxFit.fitWidth, 명시 memCache 없음 → fallback으로 목표 120×100. 정사각 리워드 이미지가 20% 수직 압축된다. 변경 전에는 fitWidth가 120×120으로 스케일한 뒤 ClipRRect가 잘라내 비율이 보존됐다.
  • 외부(비-CDN) URL은 w/h가 아예 붙지 않아 원본 비율이 임의다 — 왜곡이 확정적이다.
기존 문제인가
아니다 — 이 변경이 만든 회귀다. 변경 전 동일 값이 OctoImage 내부 디코드에도 쓰였지만 그 출력은 imageBuilder가 통째로 교체해 화면에 닿지 않았다.
최소 수정 방향
주의: policy는 ResizeImageKey의 구성 요소다. imageBuilder 쪽만 ResizeImagePolicy.fit으로 바꾸면 OctoImage의 exact 키와 달라져 중복 디코딩이 되살아난다. 양쪽이 같은 키를 유지해야 한다. CachedNetworkImage가 OctoImage에 넘기는 경로는 memCacheWidth/Height뿐이므로 현실적인 최소 수정은 한 축만 지정하는 것이다: 
// 양쪽 모두 (memCacheWidth: N, memCacheHeight: null)
//   → policy exact + 단일 축 = BoxFit.fitWidth 의미, 비율 유지
memCacheWidth: memoryCacheWidth,
memCacheHeight: null,
...
ResizeImage.resizeIfNeeded(memoryCacheWidth, null, imageProvider)
allowUpscaling: false이므로 결과 비트맵은 원본보다 커지지 않는다 — 즉 변경 전 표시 디코드(원본 그대로)보다 항상 작거나 같다. fit: BoxFit.cover로 세로가 지배적인 원본을 다루는 화면이 있으면 그 호출부만 높이 축 지정으로 뒤집는다. 이 수정이 어려우면 #1·#2가 해결될 때까지 ResizeImage 래핑을 되돌리고 중복 디코딩 제거는 별도 롤아웃 단위로 분리한다.

BLOCKER 2. memCache*가 논리 px이라 표시 해상도가 DPR배 떨어진다 (블러)

위치
picnic_cached_network_image.dart:1039 (원인 줄) + :338-351 _computeCacheDimension (multiplier가 항상 1.0: :912-921)
근거
_computeCacheDimension은 explicit이든 논리 width/height fallback이든 DPR을 곱하지 않는다. 반면 다운로드 URL의 w/h는 _getResolutionMultiplier (DPR × 1.1~1.3, 최대 2.5~4.0, :848-861)로 물리 px 목표를 만든다. 이 단위 불일치는 이미 :302-337에 KNOWN ISSUE로 상세히 기록돼 있고, 그 주석은 "렌더 시 화면이 요구하는 물리 픽셀로 다시 업스케일되어 흐릿해지고 내려받은 고해상도 데이터도 버려진다"고 정확히 서술한다. 그 서술이 이번 변경으로 처음 사실이 된다 — 이전에는 이 값이 보이지 않는 OctoImage 디코드만 지배했기 때문이다.
실패 조건 / 재현
DPR 3 기기에서 ProfileImageContainer(width: 48, height: 48): avatar_container.dart:72-73이 memCacheWidth/Height = 48을 넘긴다. 화면이 요구하는 물리 픽셀은 144인데 디코드는 48 → 선형 3배 업스케일. CDN 아바타는 120px(48×2.5)를 받아 48로 줄이고, 외부 아바타는 원본(예: 96~1024px)을 48로 줄인다. 변경 전 두 경우 모두 받은 해상도 그대로 표시됐다.
같은 이유로 vote_detail_page, common_banner, board_list_page, common_artist_widget 등 :327-332에 열거된 명시 호출부 10곳 전부와, 명시 없이 fallback을 쓰는 나머지 호출부가 동일하게 영향을 받는다.
DPR 1인 위젯 테스트에서는 논리=물리라 구조적으로 드러나지 않는다(#6 참조).
기존 문제인가
문서화된 기존 결함이지만 이 변경으로 잠재 → 실제로 전환됐다. :327-337은 저사양 기기 OOM 검증 전에는 단독 판단하지 않겠다며 이 수정을 의도적으로 미뤘다. 그 전제는 "memCache* 는 보이지 않는 디코드만 지배한다"였는데, 이제 아니다.
최소 수정 방향
_computeCacheDimension의 multiplier에 실제 DPR을 넣어 물리 px로 올린다. 이 값은 CachedNetworkImage.memCacheWidth로도 흘러가므로 양쪽 키가 자동으로 함께 이동해 중복 디코딩 제거는 유지된다. #1의 단일 축 수정과 같은 커밋에서 처리해야 한다 (한 축만 물리 px로 올리면 상한이 명확하고 allowUpscaling: false가 원본으로 클램프하므로 변경 전 표시 디코드보다 커지지 않는다 — :333-336이 우려한 DPR² 증가는 양축 물리 px 확대 시나리오에 해당한다). 실기기 메모리 확인이 선행 조건이라면, 그 확인이 끝날 때까지 ResizeImage 래핑을 보류하는 것이 이 PR 범위에서 더 안전하다.

MEDIUM 3. 성공 latch가 같은 generation의 재로딩에서 타임아웃 재장전을 영구 차단한다

위치

근거 / 실패 조건
_successfulRequestGeneration은 generation이 바뀔 때만 비워진다 (didUpdateWidget :626-628, 재시도 타이머 :1188-1190). 같은 generation에서 이미지가 다시 로딩 상태로 돌아가면 _loading = true가 설정되지 않고 타임아웃 타이머도 장전되지 않는다.
재현 경로 — vote_detail_page.dart:1388이 유일하게 deferDuringFastScroll: true를 쓴다: 빠른 플링 중 build()가 _buildSafePlaceholder()를 반환해 CachedNetworkImage 서브트리가 unmount되고 스트림 리스너가 사라져 ImageCache 엔트리가 evict 가능해진다. 스크롤이 멎어 다시 mount될 때 엔트리가 evict되어 있으면 재요청이 발생하고, 이때 latch 때문에 effectiveTimeout이 장전되지 않는다. 네트워크가 오류 없이 스톨하면(디스크 캐시까지 만료된 경우) shimmer가 무한히 돈다 — 변경 전에는 타임아웃이 발화해 재시도/에러 경로로 넘어갔다. 오류가 실제로 발생하면 errorWidget → _scheduleRetry가 generation을 올려 자력 복구되므로 영향은 "스톨" 케이스에 한정된다.
기존 문제인가
아니다 — latch 도입으로 생긴 좁은 회귀다.
최소 수정 방향
세 조건에서 _successfulRequestGeneration != requestGeneration을 제거하고 _successTransitionScheduledFor != requestGeneration만 남긴다. 무한 프레임 방어는 _onImageLoadSuccess 내부 :1291-1295의 조기 반환이 담당하므로 루프는 재발하지 않는다. 타임아웃 장전은 이미 _loading == true를 전제하고, 성공 직후 _loading이 아직 true인 창은 _successTransitionScheduledFor가 정확히 덮는다. 즉 _successfulRequestGeneration 항은 이 세 지점에서 중복이면서 재장전만 막는다.

LOW 5. 제거된 _optimizeImageCacheForPage()를 근거로 삼는 주석이 남아 있다

위치
picnic_cached_network_image.dart:526-535
근거
이 주석은 _optimizeImageCache()를 initState에 유지해야 하는 이유로 "vote_home_page.dart의 _optimizeImageCacheForPage()가 100ms 동안 상한을 절반으로 낮춘다"를 들고, "vote_home_page 의 임시 축소 로직과 함께 재설계하기 전까지는 위젯 안에 유지한다"고 못박는다. 그 함수는 이번 변경으로 삭제됐다.
실패 조건
후속 작업자가 이 주석을 근거로 _optimizeImageCache()를 initState 밖으로 옮기면, 남아 있는 _clearPartialImageCache() :576-584의 동일 패턴이 노출된다 — 그쪽 복원은 개별 이미지 위젯의 mounted에 걸려 있어, 200ms 안에 그 위젯이 dispose되면 전역 maximumSizeBytes가 70%에 영구 고정된다. 현재는 새 이미지 위젯의 initState가 우연히 복원해 주는 구조라 자력 치유되고 있다.
기존 문제인가
_clearPartialImageCache의 누수는 기존 문제이며 이 변경으로 악화되지 않았다. 주석의 stale화만 이번 변경의 산물이다.
최소 수정 방향
주석을 "_clearPartialImageCache의 일시 축소를 복원하는 유일한 지점"으로 갱신한다.

LOW 6. 테스트 공백 — 신규 테스트가 #1·#2를 구조적으로 잡을 수 없다

근거
fixture 160×80과 목표 80×40은 종횡비가 같다. 비율이 같은 표본에서는 ResizeImagePolicy.exact의 BoxFit.fill 성질이 드러나지 않는다 — 코디네이터가 height만 80으로 바꾸자 즉시 실패했다는 사실이 이 공백을 증명한다. 또한 위젯 테스트의 DPR은 1이라 논리=물리가 되어 #2도 나타나지 않는다. 기존 loader 테스트 9종을 훑어봤을 때 디코드 치수를 단정하는 곳은 이 신규 테스트뿐이다.
최소 수정 방향
#1·#2 수정과 함께 두 케이스를 추가한다. (a) fixture 비율 ≠ 목표 비율(예: 160×80 원본, 80×80 박스)에서 디코드가 원본 비율을 유지하는지, (b) tester.view.devicePixelRatio = 3에서 디코드 치수가 물리 px을 따르는지. 두 케이스 모두 imageCache.currentSize == 1 단정을 함께 유지해 왜곡·블러 수정이 중복 디코딩을 되살리지 않는지 동시에 고정한다. 추가로 avatar http 분기(평문 CachedNetworkImage 제거)와 _isHttpUrl의 Uri.tryParse 전환은 현재 어떤 테스트도 위젯 트리를 단정하지 않는다 — avatar_container_test.dart는 resolveAvatarImageUrl 문자열과 생성 가능성만 본다.

기존 문제 — 이 변경과 무관 (참고)

  • _onVisibilityChanged :434-439의 재가시화 재시도는 _reloadToken을 올리지 않아 같은 ValueKey의 CachedNetworkImage가 재요청을 하지 않는다. 변경 전후 동일.
  • _scheduleRetry가 build 중에 _retryCount++와 로깅을 수행하고, 타임아웃과 errorWidget이 같은 실패에 대해 두 번 호출되면 카운트가 두 번 오른다. 변경 전후 동일.
