3. 2단 배치와 닫기 기하

  • 카드 폭은 2단 후보에서만 min(routeAvailableWidth, 800)이다. 851 폭 표본은 실제 라우트 가용 폭인 약 781.71, 926 이상 표본은 800으로 제한된다. 1단의 560 상한은 유지된다.
  • 두 열 간격은 16이고 40:60을 출발점으로 실제 최소 폭에 맞춰 clamp한다. 두 열은 같은 body 높이를 사용하되 서로 독립적으로 스크롤한다.
  • 좌열 상단의 초상화·이름과 잔액, 우열의 전체 사용·입력·투표 버튼은 스크롤 offset 0에서 모두 캡슐과 모든 스크롤 viewport 안에 있고 hit-test 가능해야 2단 후보가 채택된다.
  • 상수 120을 직접 사용하지 않고 resolveVoteDialogShape가 결정한 실제 반경으로 위·아래 여백을 대칭 계산한다. 이 여백으로 좌열의 48 충전 타깃과 우열 상·하단 조작부가 RRect 모서리에 잘리지 않는다.
  • 851×393/ko/1.0은 위쪽 닫기가 표시되고, 851×270/ko/1.0은 높이 적합성 때문에 닫기 strip이 숨겨진 2단을 사용한다. 두 경우 모두 충전 타깃과 닫기 hit 영역이 겹치지 않는다.
  • 닫기가 숨겨진 경우 사용자 탈출구는 기존과 동일하게 배리어 탭과 시스템 뒤로가기뿐이다. 투표 진행 중에는 기존 PopScope 가드가 두 경로를 차단한다.

8. 계획 대비 편차와 근거

편차근거 및 처리
inline 조작부를 추가하지 않음확정 결정상 키보드 구간은 무조건 1단이다. 키보드가 없는 th/2.0의 두 짧은 표본도 입력·피드백 인접성과 48 타깃을 지킨 실제 높이에 들어가지 않아 1단 폴백이 더 안전하다.
숨김 닫기에서 반경 축소 후보 추가열 자체 높이는 들어가지만 선호 반경 clearance만 부족한 경우 resolveVoteDialogShape가 푼 실제 반경을 받아들인다. 상수 120 또는 임의 반경을 쓰지 않고 모든 핵심 Rect를 RRect로 검증했다.
장잔액을 예약 폭으로 제한리뷰에서 실제 잔액이 9,999,999 fixture보다 길 수 있는 경계를 발견했다. 네트워크 잔액 갱신으로 열 수가 흔들리거나 충전 48 타깃이 밀리지 않도록 1줄 ellipsis로 제한했고, 30자리 RED→GREEN을 추가했다.
기존 viewport 테스트 1건의 단언을 경로별로 분리원래 851×393에서 무조건 ≤560을 요구해 승인된 2단 폭과 양립하지 않았다. 코디네이터의 명시적 예외 승인에 따라 이 단언만 VoteDialogColumns 여부로 나눠 1단 ≤560을 그대로 유지하고 2단만 ≤800을 검사했다. 다른 기존 테스트는 수정하지 않았다.
기존 1단 충전 pill의 극단 폭 방어공용 위젯을 유연하게 만든 뒤 600×500에서 2px overflow를 회귀 테스트가 검출했다. 정상 폭의 card-scaled geometry는 유지하고, 내부 폭이 아이콘+gap보다 작을 때만 gap을 접고 아이콘을 제약에 맞춘다.

9. 남은 위험

  • 실제 이름이 두 줄을 넘거나 지원 범위를 벗어난 잔액이면 ellipsis가 적용된다. 원문은 Text semantics에는 남지만 시각적으로 전부 표시되지는 않는다.
  • 851×393·844×390의 Thai 2.0은 실제 우열 높이 때문에 2단 이득을 주지 못하고 기존 1단 스크롤에 의존한다.
  • 좌·우 열은 독립 스크롤이므로 한 열의 긴 부가 정보가 다른 열과 같은 세로 위치를 유지하지 않는다. 핵심 블록의 최초 offset 0만 보장한다.
  • 전체 analyze의 기존 521건은 이번 범위 밖에 남아 있다. 변경 파일 단독 분석은 0건이며 전체 수는 늘지 않았다.
