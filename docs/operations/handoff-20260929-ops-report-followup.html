왜 구매자가 아닌 계정으로 제출됐나

앱은 콜드 스타트 때, 그리고 포그라운드로 돌아올 때(최소 5분 간격) 그 구글 계정이 아직 소비하지 않고 보유한 구매를 찾아 지금 로그인한 계정으로 다시 제출한다(sweepUnfinishedPurchases, Android 는 queryPastPurchases). 이 목록은 앱 계정이 아니라 구글 계정에 묶여 있다. 그래서 구글 계정은 그대로 두고 앱 계정만 바꾸면 옛 구매가 새 계정 이름으로 제출된다. 옛 경로로 지급된 구매에는 계정 각인이 없다. 각인(앱 PR #90, 7/27 커밋)과 새 경로 호출은 같은 프로덕션 태그 picnic-v1.3.0(7/29 KST)에서 함께 들어갔고, 옛 경로를 부르던 프로덕션 빌드에는 각인이 없기 때문이다. 각인이 비어 있으면 어느 계정이 제출해도 소유자 불일치가 된다. 세 번째 건(8/2 구매)에서 구매자 본인의 제출이 거절된 것도 이것으로 설명된다. 구글 응답의 각인 값을 직접 본 것은 아니다.

6. 조사할 때 알아둘 것

  • devices.created_at·last_seen 은 기기의 현지 시각이다. UTC 로 저장되지만 값은 현지 시각이다. 10/1 에 최근 24시간 안에 본 509대 중 244대의 last_seen 이 미래(최대 +9시간)였다. 서버 시각과 맞춰 볼 때는 auth.sessions.refreshed_at 이나 Edge 로그를 쓴다.
  • 결제 문제를 볼 때는 public.receipts 부터 대조한다. 옛 경로 행(platform = 'android')은 receipt_data 가 구매 토큰이고, 새 경로 행(platform = 'google')은 접수 봉투 JSON 이며 그 proof 가 토큰이다. 새 경로 행은 verification_data->>'inbox_id' 로 인박스와 이어진다. 인박스만 보면 옛 경로의 지급이 보이지 않는다.
  • public.receipts 는 RLS 가 꺼져 있고 authenticated 에 SELECT 가 있다. 구매 토큰이 평문으로 들어 있는 테이블이다. 로그인 사용자의 전 행 열람을 닫는 일은 handoff-rls-rollout.html 이 다룬다.
  • 접수 봉투의 requestContext.app_version 은 구글 접수 931건 전부 0.0.0 이다. 제출한 앱 버전은 여기서 알 수 없다. devices.app_version 도 근거가 못 된다(§3-E).
  • net._http_response 는 약 6시간, cron.job_run_details 는 14일만 남는다(9/21 핸드오프의 "성공 행 하루치"는 지금 값이 아니다). 로그 API 는 30일 전 것도 조회되고(9/1 로그 확인) 한 번에 24시간 창까지다.
  • pg_net 타임아웃 문구의 "DNS time" 을 DNS 장애로 읽지 말 것. 5초 타임아웃 행의 "DNS time: 5000ms" 는 함수가 요청을 받아 54초 동안 돈 실행에서 나왔다.
  • picnic-supabase main 에서 워크플로를 수동으로 다시 돌리면 동시성 그룹(cancel-in-progress) 때문에 진행 중인 최신 실행이 취소된다.
  • ~/Repositories/picnic-supabase 메인 폴더에 커밋되지 않은 변경 3개(.gitignore, package.json, .nvmrc)가 있다. 이번 작업과 무관해 손대지 않았다.
  • Jira 상태는 바꾸지 않았다. 검토중 전환은 명시적 요청이 있을 때만 한다.

7. 정정 기록

작업 중 틀리게 보고했다가 바로잡은 것들이다. PR 본문·커밋 메시지·Jira 댓글에 옛 서술이 남아 있을 수 있다.

  • CI: "스위트가 컨테이너를 동시에 띄운다" → 순차 실행이다. 동시 3개는 진단 워크플로의 모양이었다.
  • CI: "Rate exceeded 가 원인" → 진단에서 관측한 거절은 Data limit exceeded 다. Rate exceeded 는 진단이 스스로 만든 것이다.
  • 리포트: "9/29 의 웹훅 타임아웃은 notify-vote-progress 다" → 그 함수의 행은 리포트가 볼 수 없다. 그 행의 호출자는 추정으로 남았다(§3-A).
  • 크론: "1초짜리는 process-bonus-queue 뿐이고 이후 타임아웃 행은 0이어야 한다" → jobid 4 를 놓쳤고, 트리거 웹훅 3종(5초)도 빠뜨렸다(§3-B·C).
  • 결제: "옛 빌드로 결제해 청구된 채 미지급", "구글 응답을 봐야 안다" → 틀렸다. 옛 경로에서 이미 지급된 구매의 재제출이다. "휴면 계정"은 근거로 든 devices.last_seen 해석이 틀렸다(§3-E).
  • 결제: 되살리기로 열린 purchase_age CRITICAL 2건을 보고하지 않았다.
  • 결제: 9/30 에 옛 영수증을 대조하지 않고 DEAD 두 행을 되살렸다. 각인이 맞는 구매였다면 한 번 더 지급됐을 수 있는 조치였다.
  • 마이그레이션: 프로덕션 이력을 기록하지 않았고, 당시 그 사실을 알리지 않았다. #191·#193 을 리뷰 없이 머지했다.
