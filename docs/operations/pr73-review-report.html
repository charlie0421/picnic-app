1. 배포 전 필수 조치

Codemagic 변수 3개 추가

아래 세 변수는 이번 브랜치가 처음 요구하는 것입니다. 머지 직전 main 의 codemagic.yaml 에는 참조가 0건이었으므로 기존에 설정돼 있을 수 없습니다. 현재 ${VAR:?} 로 필수화돼 있어 미설정 시 빌드가 즉시 실패합니다.

변수값
PICNIC_STAGING_SUPABASE_URLstaging Supabase 프로젝트 URL
PICNIC_STAGING_SUPABASE_ANON_KEYstaging anon key
PICNIC_STAGING_SUPABASE_PROJECT_REFstaging project ref — URL 의 서브도메인과 정확히 일치해야 함

picnic_env 그룹에 넣으면 됩니다. project ref 가 URL 과 불일치하면 앱이 기동 시 SupabaseEnvironmentPolicy 에서 StateError 로 종료합니다.

설정하면 안 되는 것: DEPLOY_TARGET. 이제 태그에서 파생되며, environment.vars 에 존재하면 가드가 빌드를 실패시킵니다.
설정 불필요: PICNIC_PANGLE_* 4개 — staging 빌드 명령에 빈 값으로 인라인 전달됩니다.

production 태그에만 추가로 필요한 것

verify_release_target.dart --target=production 이 production 분기를 게이팅하며 CI_PROVIDER, PRODUCTION_RELEASE_EVENT, ENVIRONMENT, RELEASE_SHA, RELEASE_TAG, RELEASE_APPROVAL_REFERENCE, RELEASE_MANIFEST(+체크섬), *_EVIDENCE 를 읽습니다. staging 태그는 이 경로를 타지 않습니다.

2. 릴리스 절차 변경

production 과 staging 이 같은 picnic-v* 태그를 공유하고 런타임 변수로 갈리던 구조를, 태그가 대상을 결정하도록 바꿨습니다. 사람이 잊을 수 있는 설정 단계가 사라집니다.

picnic-v1.2.3          →  production
picnic-staging-v1.2.3  →  staging
  • 두 패턴은 한 태그에 동시 매칭되지 않습니다 (picnic-staging-v… 는 picnic-v* 에 걸리지 않음)
  • 매핑되지 않는 태그는 첫 단계에서 명시적으로 실패합니다
  • 태그 없는 수동 실행은 더 이상 불가능합니다 (의도된 동작)
  • 같은 커밋을 양쪽에 올리려면 태그 2개가 필요합니다
  • Shorebird 패치 워크플로는 변경 없음 — production 전용, 수동, SHA 게이트 유지

3. 해결된 차단 사항

해결Critical 1 — production 태그가 staging 앱을 배포할 수 있었음

모든 분기가 ${DEPLOY_TARGET:-staging} 로 판정되는데 그 변수는 레포 어디에도 정의돼 있지 않았습니다. 즉 기본값이 staging 으로 fail-open 이었고, 태그 트리거도 하나뿐이었습니다.

머지 후 확인한 결과 이 변수는 Codemagic 에도 없었습니다. 따라서 이 상태로 production 태그를 밀었다면 staging backend·sandbox 결제로 빌드된 앱이 App Store Connect 에 업로드됐을 것입니다. 해당 워크플로가 main 에서 실행된 적이 없어 실제 사고는 발생하지 않았고, 태그 기반 전환으로 함정이 발동 전에 제거됐습니다.

해결Critical 2 — 격리 가드가 회귀를 탐지하지 못했음

가드가 if 조건에 DEPLOY_TARGET 문자열이 있으면 분기 방향을 보지 않고 통과시켰고, production 경로 존재 여부는 원문 검색이라 주석도 만족시켰습니다. 재현 결과 production 가드의 비교 연산자를 뒤집어도 PASS 였습니다.

가드를 if/else/elif/fi 분기 컨텍스트를 해석하도록 재작성하고, 적대적 재리뷰가 찾은 사각지대 7건을 추가로 닫았습니다 — 결합 조건(&&/||), set -e 실효성(||·파이프·set +e·명령 치환), 모든 defaulting 연산자, 값 허용 목록, 워크플로 목록의 YAML 유도, 가드 자신의 CI 호출 강제, flutter test 경로 축소. 변형 self-test 40개를 갖췄고, 가드는 이제 두 태그 워크플로와 run_tests.sh 에서 실제로 실행됩니다 (이전에는 어디서도 실행되지 않았습니다).

해결Critical 3 — 캠페인 조회 실패가 홈 배너 전체를 지웠음

vote_home 배너가 promotion RPC 에 하드 의존해, 실패 시 일반 배너까지 오류 박스로 대체됐습니다. 실패 시 일반 배너로 degrade 하도록 고쳤고 loading 분기(shimmer)는 유지했습니다. 로컬 실행으로 실물 검증했습니다 — 5절 참조.

6. 남은 항목

판단 필요늦은 구매 순서 불변식이 고정되지 않음

프로덕션 코드는 올바르지만, 회귀 2종(판정을 정산 정리 뒤로 이동 / 이전의 항상-false 형태로 복원)을 실제로 넣어봐도 전체 스위트가 초록이었습니다. 해당 불변식이 위젯을 통해서만 도달 가능한 익명 콜백 안에 있어, 고정하려면 정산 단계를 주입 가능한 형태로 추출해야 합니다. 결제 경로라 임의로 리팩터링하지 않았습니다.

정책 필요merge-base --is-ancestor 의 범위

기존 게이트는 릴리스 태그가 main 의 tip 과 같아야 해서, 이 레포의 기존 태그 6개 중 어느 것도 릴리스가 불가능했습니다. 이것이 운영자를 staging 기본값 경로로 되돌리던 원인이라 containment 로 완화했습니다(정확한 SHA 핀 고정은 유지).

다만 containment 는 한때 main 의 조상이었던 커밋을 모두 허용하므로, non-squash 병합에서는 나중에 고쳐진 WIP 커밋 트리로도 릴리스가 가능합니다. squash 머지 정책을 강제할지 결정이 필요합니다.
