2. 1번 — JMA 280×280 첫 화면 실패

사실 확인

리뷰의 계산(body 약 173.1 vs essential 약 191.4)은 방향이 정확했다. 실제로 재현한 값은 다음과 같다. 280×280·배율 2.0·키보드 0 에서 캡슐 bottom = 216.0, 투표 버튼 bottom = 219.68 → 3.68px 잘림. 배율 1.0·1.3 은 통과. 일반(비-JMA) 다이얼로그는 여백이 24 라서 같은 크기에서 3배율 모두 통과했다 — 즉 이 건은 JMA 전용이라는 리뷰의 범위 판단도 맞았다.

원인

JMA 의 AlertDialog.insetPadding 이 상하 40 고정이었다. 280 높이 창에서 80px, 즉 화면의 29%를 빈 여백으로 쓰면서 조작부가 담기지 않는 상태를 만들고 있었다. 조작부 자체는 48 터치 영역 3개(전체 사용·입력·버튼)가 하한이라 내용으로는 더 줄일 수 없다. 줄여야 하는 것은 여백이었다.

변경

voting_dialog_layout.dart 에 공유 정책을 추가했다. 

double resolveVoteDialogVerticalInset({
  required double preferredInset,      // JMA 40/20, 일반 24
  required double availableHeight,     // 화면 − 키보드 − 시스템 바
  required double requiredBodyHeight,  // 조작부 + 팝업 chrome + 초상화 최소치 32
}) {
  if (!availableHeight.isFinite || availableHeight <= 0) return preferredInset;
  final affordable = (availableHeight - requiredBodyHeight) / 2;
  if (affordable >= preferredInset) return preferredInset;
  return math.max(kVoteDialogMinimumVerticalInset, affordable.floorToDouble());
}

조작부가 담기는 동안에는 디자인 값을 그대로 돌려주므로, 넉넉한 화면의 기하는 1px 도 변하지 않는다(일반 휴대폰 세로는 전부 이 경로). 담기지 않을 때만 여백이 하한 8 까지 양보한다. 하한 8 은 계획의 최소 인수 크기 280×280 에 유효성 문구가 떠 있는 상태(조작부 실측 218.5, 필요 body 230)를 기준으로 정했고, 그 값 이상에서는 그 상태가 담기지 않는다. 폭은 SizedBox 가 고정하므로 LayoutBuilder 이전에 조작부 높이를 미리 잴 수 있다 — 순환은 없다.

같은 정책을 일반 다이얼로그에도 적용했다. 부수 효과로 412×500 + 키보드 280 (두 다이얼로그 모두 기존에 버튼이 각각 2.99px·12.5px 잘렸던 조합)이 함께 해소됐다.

3. 2번 — 유효성 문구가 보이지 않던 회귀

변경

4. 3번 — 활성 버튼 라벨 폭 과소 예산 범위 확대

사실 확인 — 리뷰가 과소평가했다

구조적 결함은 리뷰 그대로다. 측정은 버튼 안쪽 폭 전체 (voteDialogCardExtent(172) − h(12)×2)를 라벨에 주는데, 활성 상태만 20px 아이콘과 h(8) 간격을 라벨 앞에 두므로 실제 라벨 폭이 더 좁다. 다만 리뷰는 이 조건을 "좁은 카드 + 2배 글자 + 긴 번역"으로 좁게 봤다. 실제로 쓰이는 로케일 7개 × 배율 3개 × 카드 폭 272~600 을 훑으면 252 조합에서 활성 라벨이 더 높았고, 그중 다수가 기본 배율이다.

5. 4번 — 테스트 행렬과 실제 clip 일부 반박

사실 확인

세 가지 하위 지적 모두 사실이다.

  1. 행렬 공백: 280×280, K=280, 실제 showDialog/SafeArea, 부분 부모, PIC 변형, JMA 상태 전환, IME 가 모두 없었다. 위 1~3번이 그 공백에서 나왔다.
  2. RRect clip 미검증: 사실이며, 실제로 잘리고 있었다. bounding Rect 검사만으로는 보이지 않던 모서리 clip 을 측정하니 JMA 280×280 의 "전체 사용" 행이 배율별로 6.0 / 6.0 / 8.5px 깎여 있었다 (나머지 10 크기 × 3 배율 × 2 다이얼로그 조합은 0).

반박 — K=280 × 851×393 은 충족 불가능한 인수 조건이다

리뷰의 재검증 조건은 "키보드 인셋"을 행렬에 넣으라고만 했으므로 직접 충돌은 아니지만, 보강하다 확인한 사실을 남긴다. 851×393 에 키보드 280 이 올라오면 남는 높이는 113 이고, 팝업 자체의 chrome 26.85 와 최소 여백 8×2 를 빼면 body 는 약 62px 다. 전체 사용 48 + 입력 52 = 100 이므로 어떤 레이아웃으로도 조작부를 첫 화면에 담을 수 없다. 412×500 + K=280 + 배율 2.0 도 body 169 vs 조작부 191 로 같은 부류다.

따라서 이 조합에는 담기지 않는다는 사실 대신 담기지 않을 때의 계약을 테스트로 고정했다: 예외 0, 오프셋 0, 조작부가 스크롤 조상을 갖고, ensureVisible 로 입력을 창이 허용하는 만큼 완전히 드러낼 수 있어야 한다. 더 나아가려면 "body 가 극단적으로 짧으면 전체 사용 행을 장식으로 내려 입력을 첫 항목으로 올린다" 같은 설계 변경이 필요하고, 그건 이 리뷰 대응 범위가 아니다(→ 6절).

변경 — 모서리 clip 은 검사만 추가하지 않고 원인을 고쳤다

모드와 카드 반경을 함께 결정한다. 이유는 둘이 분리 가능하지 않기 때문이다 — 카드가 clip 하는 모서리는 "조작부가 담기는가"의 일부다. 

VoteDialogShape resolveVoteDialogShape({bodyHeight, essentialHeight, horizontalContentInset}) {
  final preferred = voteDialogCardRadius(bodyHeight);            // min(120.r, body/4)
  final clearance = voteDialogCornerClearance(                   // 원의 방정식 해
      radius: preferred, horizontalInset: horizontalContentInset);
  final mode = selectVoteDialogLayout(
      bodyHeight: bodyHeight - clearance, essentialHeight: essentialHeight);
  return VoteDialogShape(mode: mode, cardBorderRadius: BorderRadius.circular(
      mode == actionsPinned ? preferred                          // 호는 장식 위에 떨어진다
                            : math.min(preferred, horizontalContentInset)));
}
  • actionsPinned: 디자인 반경을 유지하되, 조작부 위 장식 밴드가 clearance 이상 남는 경우에만 이 모드를 고른다. 호가 장식에 떨어지므로 조작부는 깎이지 않는다.
  • allScroll: 조작부가 카드 상단에 붙으므로 양보할 높이가 없다. 대신 반경을 조작부의 좌우 인셋까지 클램프해 호가 조작부에 닿지 못하게 한다 — 세로 비용 0.

테스트 작성 중 발견한 함정: Dialog 는 inset 을 100ms AnimatedPadding 으로 통과시킨다. 팝업이 이제 조작부 높이에 따라 자기 inset 을 바꾸므로, 입력에 반응한 첫 프레임은 여전히 옛 여백을 들고 있다. 상태를 바꾼 뒤 한 프레임만 pump 하면 중간 값이 측정된다(available 230 vs 264). settleDialogState() 헬퍼로 두 프레임을 pump 한다.

6. 넣은 것과 남긴 것

이번에 넣지 않은 것 — 근거와 재현 방법

  1. 긴 로케일 라벨의 무제한 감김(선행 결함, 이번 커밋 밖) — 태국어 + 배율 2.0 + 280 폭에서 투표 버튼 라벨이 7줄까지 감겨 버튼 높이가 370px 이 된다. 480 높이 화면에서는 어떤 여백 정책으로도 담기지 않는다. 버튼 폭 172.w 와 maxLines 부재는 부모 커밋 2e5ccdc20 과 동일하므로 464b70e1d 의 회귀가 아니다. 올바른 수정은 라벨 줄 수 제한(가독성 손실)이 아니라 버튼 폭 정책 (카드 안에 약 100px 여유가 있다)이고, 이는 별도 티켓 거리다. 그래서 3번의 테스트 행렬은 배율 1.0·2.0 × 담길 수 있는 조합으로 잡고, 경계 테스트는 280×320·배율 1.0 에 뒀다.

cd picnic_lib

  2. 극단적으로 짧은 body 에서 조작부 우선순위 재배치 — 851×393 + K=280(body 62px)에서는 전체 사용 48 이 먼저 와 입력이 첫 화면 밖이다. 입력을 첫 항목으로 올리려면 allScroll 의 밴드 순서를 상태에 따라 바꿔야 하고, 그건 리뷰 대응이 아니라 설계 변경이다. 현재는 "예외 없이 스크롤로 도달 가능"까지만 계약으로 고정했다.

  3. 힌지(hinge) 전용 테스트 — MediaQuery.displayFeatures 를 쓰는 코드 경로가 이 두 팝업에 없다. 부분 부모 테스트(창보다 짧은 부모)가 힌지가 만들어 내는 실제 제약(짧은 부모)을 덮는다. 힌지 자체를 넣으면 통과는 하지만 아무 것도 검증하지 않는 테스트가 된다.

    부분 부모에서는 여백 계산이 MediaQuery.size 기준이므로 창보다 짧은 부모에 맞춰 여백이 줄지 않는다(= 수정 전 동작). 이 경우도 예산은 constraints.maxHeight 에서 나오므로 레이아웃은 깨지지 않고, 테스트는 "clip 하는 박스(캡슐 또는 스크롤 뷰포트) 안에 들어간다"로 고정했다. 실제 앱 경로는 항상 전체 화면 라우트라 이 차이는 나타나지 않는다.
