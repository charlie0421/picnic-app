P1 광고 동의 상태 조회 오류가 앱 시작 대기로 이어질 수 있음

발생 조건

앱 시작 중 UMP 정보 갱신은 성공하지만 이후 getConsentStatus 호출이 PlatformException으로 실패하는 경우.

사용자 영향

처음 호출한 ConsentService.initialize Future가 완료되지 않아 이를 통해 sdkReady를 기다리는 앱이 시작 화면에 머물 수 있다. 별도의 initialize 재호출 자체가 모두 막히는 것은 아니다. 운영 발생 빈도는 이번 감사에서 측정하지 않았다.

확인한 원인

성공 콜백이 async인데 내부 예외를 completer.completeError로 전달하지 않는다. 바깥 initialize의 catch로도 전달되지 않으므로 Future가 미완료 상태로 남는다. MainInitializer는 광고·딥링크 초기화까지 await한 뒤에만 sdkReady를 완료한다. _isInitialized가 성공 시에만 true가 되므로 뒤의 별도 initialize 호출은 다시 시도할 수 있으나, 앱 시작이 기다리던 첫 Future는 자동으로 복구되지 않는다.

최소 개선 방향

콜백 내부 오류를 반드시 완료 결과로 전달하고 늦은 콜백의 중복 완료를 방어한다. 필수 앱 준비와 광고 준비를 분리하되 광고 요청에는 기존 동의 확인을 유지한다. SDK 응답 부재에 대한 제한된 대기와 복구 경로도 검증한다.

검증과 한계

실제 ConsentService와 설치된 UMP 플러그인 MethodChannel을 사용한 정상 대조군/예외 주입 2개 통과. 예외 주입 시 오류가 zone으로 빠지고 가상 시간 60초 뒤에도 initialize가 미완료임을 확인. 전체 앱 시작 화면을 실기기로 장애 재현한 것은 아니다.

P2 통신 오류를 빈 목록으로 표시하고 재시도 경로를 잃음

발생 조건

투표 목록의 첫 페이지 조회 실패 또는 상세 초기 조회·전체 새로고침 실패.

사용자 영향

실제 투표가 있어도 “투표 없음”으로 보이거나 상세 콘텐츠가 비어 보인다. 빈 상태에서는 당겨서 새로고침도 사라져 사용자가 복구 방법을 알기 어렵다.

확인한 원인

VoteList는 오류를 저장하지 않고 로딩만 종료한 뒤 VoteNoItem을 RefreshIndicator보다 먼저 반환한다. 상세 provider는 오류를 null 또는 []로 바꿔 오류 UI 분기를 우회한다.

최소 개선 방향

성공한 빈 결과와 조회 실패를 구분하고, 마지막 성공 데이터를 유지하면서 오류 안내·재시도를 제공한다. 실제 빈 목록도 새로고침할 수 있게 한다.

검증과 한계

실제 VoteList에 첫 페이지 실패를 주입해 VoteNoItem 1개, RefreshIndicator 0개를 확인한 테스트 1개 통과. 최종 오류 상태를 즉시 보기 위해 테스트에서만 Riverpod 자동 retry를 껐다. 운영 재시도 소요 시간은 이 결과로 판단하지 않는다.

P2 달성형 투표가 매초 후보 전체와 달성 정보를 반복 조회

발생 조건

달성형 투표 상세를 열어 두거나 화면이 다시 빌드될 때. 응답이 1초보다 느린 연결에서 특히 확인이 필요하다.

사용자 영향

후보·아티스트 데이터를 반복 전송·파싱하며 같은 달성 정보도 중복 조회한다. 트래픽과 화면 작업을 줄일 여지가 크고 느린 요청이 겹칠 수 있다.

확인한 원인

1초 Timer가 in-flight 검사 없이 전체 후보 provider를 refresh한다. 두 FutureBuilder가 fetchVoteAchieve를 build마다 각각 직접 실행하며, _achievements 캐시는 이 두 호출을 막지 않는다.

최소 개선 방향

일반 투표 상세에 이미 있는 id/vote_total 경량 갱신, 무변경 시 state 유지, 중복 요청 방지 방식을 적용한다. 달성 정보는 하나의 provider 또는 Future를 공유한다.

검증과 한계

일반 상세의 refreshVoteTotals와 비교해 차이를 확인했다. 다음 검증은 10초 동일 데이터 및 2초 응답 지연에서 요청 횟수·동시 요청 수를 측정하고 달성 애니메이션과 votePortal 동작을 확인하는 것이다. refresh마다 스켈레톤이 나온다는 주장은 하지 않는다.

P2 홈 탭 복귀 시 캐시된 이미지 앞에 데이터 로딩이 다시 발생

발생 조건

홈을 로드한 뒤 다른 하단 탭에 잠시 머물렀다가 홈으로 복귀.

사용자 영향

이미지는 캐시에 있어도 대표 투표 데이터를 다시 받아야 하므로 카드 대신 스켈레톤이 보이고 캐러셀 위치가 초기화된다.

확인한 원인

하단 탭 변경은 내비게이션 스택을 새 페이지 하나로 교체한다. 홈이 제거되면 단독 구독하는 featured provider도 autoDispose되어 다음 방문에 투표 및 총합 조회를 다시 실행한다.

최소 개선 방향

최근 성공 데이터를 제한된 기간 유지하고 복귀 시 우선 표시한 뒤 필요한 갱신을 수행한다. 위치 보존은 별도 상태로 관리한다. 모든 탭 전체를 무기한 유지하는 방식은 필요하지 않다.

검증과 한계

상세 push/back은 홈을 스택에 남겨 같은 원인이 아니다. 살아 있는 provider의 invalidate 역시 기존 값 표시가 가능하다. 홈→다른 하단 탭→홈에서 조회 횟수와 스켈레톤, 만료·수동 새로고침을 지연 응답 테스트로 확인해야 한다.

발생 조건

투표 상세 최초 진입 및 전체 새로고침. 후보가 많은 투표일수록 비용을 확인할 가치가 높다.

사용자 영향

상세 메타데이터 요청과 후보 목록 요청에 후보·아티스트 전체 정보가 겹쳐 전송·파싱·메모리 비용이 늘어난다. 단축 시간과 바이트 수는 미측정이다.

확인한 원인

AsyncVoteDetail가 vote_item과 artist 전체 정보를 join하고 AsyncVoteItemList도 동일 voteId의 후보·아티스트를 조회한다. 상세 화면은 두 provider를 모두 사용한다.

최소 개선 방향

상세 화면에서 메타데이터와 후보 목록의 책임을 분리해 후보 데이터를 한 번만 받는다. 목록 카드의 갱신은 기존 detail.voteItem을 사용하므로 공용 쿼리에서 일괄 제거하지 않고 호출 계약을 분리한다.

검증과 한계

상세 진입의 select/응답 바이트/후보 파싱 횟수와 카드 갱신·공유·투표 팝업을 함께 검사한다. 두 요청의 필드가 겹친다는 사실과 전체 속도가 두 배라는 주장은 다르다.

P2 시작 과정의 고정 대기와 광고 초기화 책임 중복

발생 조건

모바일 앱 시작. ATT 상태를 이미 결정한 사용자에게도 적용되는 코드 경로가 있다.

사용자 영향

PrivacyConsentManager의 ATT 상태 확인 전 고정 500ms 대기가 앱 준비 경로에 포함된다. 광고·딥링크 준비도 홈 진입 조건에 포함되어 느린 외부 초기화가 앱 전체 대기로 이어진다.

확인한 원인

Group1에서 privacy/광고를 초기화하고 Group2에서 ConsentService 및 MobileAds.initialize를 다시 호출한다. 광고 초기화가 SDK 내부에서 중복을 흡수할 수 있으므로 두 배 비용이라고 단정하지 않는다.

최소 개선 방향

동의·광고 준비의 소유자를 하나로 정리한다. 상태가 이미 결정된 경우의 고정 대기는 제거 가능성을 검증하고 첫 동의 UI는 준비 완료 신호로 제어한다. 홈 진입의 필수 의존성을 명확히 분리한다.

검증과 한계

첫 설치/재실행, 동의 허용/거부, 느린 SDK 응답을 나눠 profile 빌드로 첫 홈 표시 시점을 비교한다. 이번에는 새 cold-start A/B 측정을 수행하지 않았다.

P2 검색 중 새 검색어가 무시되어 이전 결과가 표시될 수 있음

발생 조건

사용 중인 최애 아티스트 선택 화면에서 조회가 아직 진행 중일 때 검색어를 다시 바꿈. 궁합 선택 코드도 같은 위젯을 사용하지만 이번 감사에서 해당 화면의 운영 노출은 확인하지 않았다.

사용자 영향

입력창은 새 검색어인데 결과는 이전 검색어의 결과로 남을 수 있다. 추가 스크롤은 새 검색어의 다음 페이지를 받아 서로 다른 검색 결과가 섞일 수 있다.

확인한 원인

검색어 provider는 바로 갱신되지만 _loadInitialData는 _isLoading이면 반환한다. 진행 중이던 응답에는 검색어/요청 세대 검증이 없고, 완료 후 최신 검색을 다시 수행하는 경로도 없다.

최소 개선 방향

중복 요청 방지는 같은 검색어에 적용하고 검색어 변경은 새 요청 세대로 처리한다. 오래된 응답을 무시하고 최신 검색어의 첫 페이지를 반드시 조회한다. 검색어별 페이지와 결과를 일치시킨다.

검증과 한계

지연된 A 검색 중 B 검색 입력 후 A 응답을 도착시키는 순서, 초기 로딩/추가 페이지 로딩 중 변경, 빈 검색어 복귀를 위젯 테스트로 검증해야 한다. 이번에는 코드 경로만 확인했으며 검색 위젯의 실제 장애 주입은 수행하지 않았다.
