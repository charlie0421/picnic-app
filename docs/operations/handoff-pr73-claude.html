4. 최종 리뷰 결과

Critical 1 — iOS production workflow 오염

codemagic.yaml의 App Store Connect용 picnic-app-ios workflow가 picnic-v* 태그에서 실행되면서도, 기본 DEPLOY_TARGET=staging처럼 동작한다. build 단계가 production 분기 없이 다음 값을 사용한다.

  • ENVIRONMENT=dev
  • staging Supabase URL/key/project ref
  • PAYMENT_ENVIRONMENT=sandbox
  • PANGLE_ENVIRONMENT=sandbox

이 상태로 production 태그를 만들면 staging backend를 가리키는 앱이 App Store Connect에 업로드될 위험이 있다.

Critical 2 — Wallet 기반 migration 누락

앱은 다음 RPC를 호출하지만 repository의 migration 범위에는 core schema와 함수 생성 SQL이 완결되어 있지 않다.

  • get_wallet_summary
  • get_currency_history
  • get_ad_reward_status
  • list_unacknowledged_ad_rewards
  • acknowledge_ad_reward
  • settle_shortform_view_reward
  • 일반 투표 Wallet v3 backing function

현재 reconciliation migration은 이미 존재한다고 가정한 wallet_private.reconcile_wallet_batch를 수정한다. 따라서 빈 DB에서 repository migration만으로 schema를 재현할 수 없다.

Important 1 — 투표 실패 UI가 refresh에 종속

picnic_lib/lib/presentation/widgets/vote/voting/voting_dialog.dart의 일반 투표 실패 경로에서 오류 UI와 cleanup 전에 await walletSummaryProvider.refresh()를 수행한다. RPC가 hang하면 오류 안내와 상태 복원이 지연되고, refresh 예외가 throw되면 원래 실패 처리 자체를 건너뛸 수 있다.

Important 2 — PR 범위 과대

리뷰 시점 기준 309개 파일, +36,577/-15,861이다. Shorebird startup, production release scripts, AWS deploy, YouTube/DeepL/network service, version bump 등 코튼캔디와 독립적인 변경이 포함돼 있다.

Minor — production config의 비밀값 제거

picnic_app/config/prod.json의 AWS/YouTube/DeepL 값이 빈 값으로 변경됐다. 비밀 제거 방향은 맞지만 모든 production 주입 경로가 검증되지 않으면 기능 중단이 가능하므로 별도 변경으로 분리하는 편이 안전하다.

5. 승인된 설계

목표

PR 73을 프로덕션 배포 경로에 영향을 주지 않는 상태로 정리하고, 코튼캔디 보상·구매 영수증·일반 투표 Wallet v3 기능을 재현 가능한 migration 및 테스트와 함께 머지할 수 있게 한다.

범위

  • 코튼캔디 광고 보상 적립과 공통 보상 영수증
  • 스타캔디·보너스 스타캔디 구매 영수증
  • 일반 투표 Wallet v3 연동과 PIC 투표의 기존 재시도·인증 복구
  • staging 빌드의 명시적 격리
  • 필요한 Wallet schema, RPC, RLS, grants, Edge Function
  • Task Master 제거

선택한 접근

안전 차단 수정 후 주제별 분리를 선택했다. 기존 staging 검증 자산과 충돌 해결을 보존하면서 production workflow, migration 완결성, 투표 실패 처리를 우선 보강한다. 코튼캔디에 필요 없는 변경은 목적별 후속 PR로 옮기거나 현 PR에서 제거한다.

배포 구조

  • production workflow는 ENVIRONMENT=prod, production Supabase, production 결제·광고 설정을 유지한다.
  • staging은 별도 workflow 또는 서로 겹치지 않는 명시적 staging 태그로만 실행한다.
  • production 빌드는 staging 변수에 의존하지 않는다.
  • staging 빌드는 production endpoint/project ref가 감지되면 즉시 실패한다.

DB 구조

  • 빈 staging DB에 repository migration을 순서대로 적용하면 Wallet 기능 전체가 생성돼야 한다.
  • 특권 함수는 비노출 schema에 두고 search_path를 고정한다.
  • 클라이언트 RPC는 auth.uid()를 검증한다.
  • PUBLIC execute를 철회하고 필요한 함수에만 authenticated 권한을 부여한다.
  • 노출 schema의 table은 RLS와 소유권 정책을 함께 적용한다.

투표 실패 처리

  • 오류 UI와 로딩 상태 복원을 Wallet refresh보다 먼저 보장한다.
  • 실패 후 refresh는 timeout과 자체 오류 처리를 가진 best-effort 동작으로 수행한다.
  • refresh 실패가 원래 투표 오류를 가리지 않는다.
  • 일반 투표 auth retry는 최초 UUID request ID를 재사용한다.
  • PIC 429 backoff와 auth recovery는 변경하지 않는다.
