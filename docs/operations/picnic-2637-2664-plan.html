PICNIC-2637 · PICNIC-2664 처리 방안

전제: 2026-09-11 기준 운영 장애는 해결된 상태입니다. 두 티켓의 상위 PICNIC-2633(Supabase CPU 100%)의 장애 상황이 종료됐다는 사용자 확인에 따라 작성했습니다. 이 전제는 두 티켓에 정반대 방향으로 작용합니다 — 2637은 존재 이유가 대부분 사라지고, 2664는 영향을 받지 않아 남은 항목 중 유일하게 사용자에게 직접 닿는 결함으로 남습니다.

PICNIC-2664 · High · 해야 할 일 · 담당자 없음계정 전환 후 이전 구매 정산 응답의 지갑 덮어쓰기 차단

장애 해결의 영향: 없습니다. 이 티켓은 애초에 장애와 무관합니다 — 본문이 “서버 CPU 장애의 확정 원인이나 이번 수정의 신규 회귀로 판단하지 않는다”고 명시합니다. CPU 장애가 끝나도 사용자 화면에 다른 계정 잔액이 표시되는 결함은 그대로 남아 있습니다. 장애 대응 항목들이 정리되면서 이 티켓이 남은 것들 중 유일하게 사용자에게 직접 닿는 결함이 됐습니다.

1. 티켓이 남겨둔 조사 항목부터 처리했습니다

완료 조건에 “투표/광고의 직접 setSummary 호출자도 실제 소유권 보호 여부 조사”가 있었습니다. 현재 main 기준으로 전수 확인한 결과입니다.

2. 그래서 호출처를 4곳 고치는 방식은 권장하지 않습니다

4곳을 각각 가드하면 지금은 닫히지만 다음 호출처가 또 빠뜨립니다. 실제로 이 저장소는 같은 종류의 실수를 이미 타입으로 막은 전례가 있습니다 — WalletSummaryApplier의 주석이 그 이유를 명시합니다: 

/// A named type rather than a bare `void Function(WalletSummaryModel)` because …
/// Requiring this type at the call site is what stops one being passed.

같은 원칙을 소유권에도 적용하는 것이 이 코드베이스의 결에 맞습니다.

3. 권장안 — setSummary에 소유권 토큰을 필수 인자로

앱 전용 변경이며 서버·ACL·지급 로직을 건드리지 않습니다.

설계

  1. 토큰 타입 WalletWriteToken(ownerId, authEpoch)을 도입하고, WalletSummary가 현재 값으로 발급합니다. PR #206이 이미 추가한 _authEpoch와 _currentOwner(gateway)를 그대로 재사용합니다 — 새 상태를 만들지 않습니다.
  2. 시그니처 변경 setSummary(summary) → setSummary(summary, {required WalletWriteToken owner}). 5개 호출처가 전부 컴파일 에러가 나므로 누락이 구조적으로 불가능해집니다.
  3. 판정 ownerId가 현재 소유자와 다르거나 authEpoch가 변했으면 쓰기를 버립니다. 기존 snapshotAt 검사보다 먼저 수행합니다.
  4. 캡처 지점 ContainerWalletSummaryApplier.of(context)가 이미 “mounted 상태일 때 container를 캡처”하는 자리입니다. 같은 생성자에서 토큰도 캡처하면 purchase_settlement_step.dart는 한 줄도 고치지 않아도 구매 경로가 닫힙니다.
읽기 경로의 판정을 그대로 복사하면 안 됩니다. PR #206의 _stillOwns는 identical(session)을 씁니다. 읽기에는 맞지만 쓰기에는 과잉 차단입니다 — 정산은 네트워크만큼 오래 걸리고 그 사이 토큰 갱신이 일어나면 gotrue가 새 Session 인스턴스를 만듭니다. 같은 계정인데 적립이 화면에 반영되지 않는 새 버그가 됩니다.

쓰기 판정은 ownerId + authEpoch여야 합니다. _authEpoch는 계정 전환에만 증가하도록 #206이 이미 만들어 두었으므로 (같은 계정 토큰 갱신·리플레이는 증가하지 않음), A → B → A 왕복까지 잡으면서 토큰 갱신은 통과시킵니다.

대안 B — 서버 계약에 소유자 추가 (wallet.v2)

현재 wallet.v1 계약에 user_id가 없습니다 (test/fixtures/wallet_contracts/wallet_summary_v1.json 확인). 서버가 주장하는 소유권이 가장 강한 보증이지만 picnic-supabase 레포 변경 + 구버전 v1 호환 유지가 함께 필요합니다. 권장안을 먼저 적용하고, v2는 별도 티켓으로 검토하는 것이 맞습니다. 권장안은 v2가 생겨도 버려지지 않고 클라이언트 측 2차 방어로 남습니다.

2637은 라벨부터 p1 · supabase-cpu-20260908입니다. 즉 장애 대응 항목으로 만들어졌고, 비용 절감은 그 자체가 목적이 아니라 CPU를 내리기 위한 수단이었습니다. 장애가 해결된 지금, 남은 항목들을 그 목적에 비추어 다시 보면 판단이 뒤집힙니다.

3. A를 종결 권고하는 이유

A의 가치는 두 방향에서 동시에 사라졌습니다.
① 수요 쪽 — PR #204가 배포되면 신버전 앱은 이 목록을 아예 호출하지 않습니다. 남는 것은 구버전 잔존 트래픽뿐이고 보급률이 오를수록 줄어듭니다.
② 목적 쪽 — 이 최적화를 정당화하던 CPU 장애가 끝났습니다.

두 가지가 겹치면, A는 사라지는 중인 경로에 · 이미 해소된 문제를 위해 · 고위험 운영 SQL 변경을 한 번 더 하는 일이 됩니다. 이미 적용된 PR #137·#138로 구버전 트래픽에 대한 보완은 충분히 됐습니다.

참고로, 착수하게 될 경우의 1순위 후보는 (c) index-only count였습니다 (PR #137의 부분 인덱스로 count가 index-only scan이 되는지 재확인 — 계약 변경 0건). 나머지 후보인 “첫 페이지에서만 계산”, “LEAST(count, N) 상한”은 티켓이 이미 “total 제거/근사화는 계약 변경이므로 최소 개선안에 포함하지 않는다”고 배제해 두었습니다. 기록만 남기고 착수하지 않는 것을 권고합니다.

4. C는 살아 있지만, 이 티켓의 일이 아닙니다

피크 측정 자체는 여전히 필요합니다 — 다만 그 결과를 쓰는 곳이 바뀌었습니다. PICNIC-2635는 오늘(09/11 10:33 KST) “예약 저녁·자정 CPU 검증 완료 — 다일 관측·2XL/XL 용량 판단”으로 갱신되어 진행 중입니다. 즉 지금 살아 있는 질문은 “목록 호출을 더 줄일까”가 아니라 “2XL을 XL로 내려도 되는가”이고, 피크 데이터는 그 판단의 입력입니다.

따라서 C는 2637에 남겨 두는 것이 아니라 2635의 다일 관측에 합치는 것이 맞습니다. 2637에 남겨 두면 이미 끝난 목적의 티켓이 다른 티켓의 작업을 붙들고 열려 있게 됩니다.

PICNIC-2637 상태 권고 — 종결

장애 해결로 이 티켓의 목적은 달성됐습니다. 아래를 기록한 뒤 완료로 전환을 권고합니다.

  • 달성 — 서버 최적화 2건(PR #137 인덱스, PR #138 페이지당 잔액 1회) 운영 적용 및 실측 완료. 앱 측 자동 목록 조회 제거는 #204로 main 반영.
  • 종결 — A(total_count): 상위 장애 해소 + 대상 경로 소멸 예정으로 불필요. 후보 (c)만 기록 보존.
  • 이관 — B(보급 후 호출량) → PICNIC-2634 / C(피크 관측) → PICNIC-2635.

단, 한 가지 확인이 선행돼야 합니다 — 2635의 2XL→XL 판단이 2637의 추가 절감을 전제로 하고 있지 않아야 합니다. 전제로 한다면 A를 종결하지 말고 2635에 종속시켜야 합니다.
