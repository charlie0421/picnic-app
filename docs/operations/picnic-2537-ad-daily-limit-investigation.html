PICNIC-2537 — 광고 1시간 10회 소진 후 시청 가능 시간 표기

조사일 2026-09-04 · QnA 391 · 신고자 711bd953…6565 (일본) · 대상 프로젝트 xtijtefcycoeqludlngc

표기 계산은 정확했다. 원인은 같은 무료충전소 화면의 세 구좌가 서로 다른 “1일”을 쓰고 있었던 것이다. 글로벌픽 #1(AdMob)만 rolling 24시간이었고 나머지 두 구좌는 KST 달력일이었다. 사용자는 시간당 10회에 걸렸다고 생각했지만 실제로는 rolling 24시간 120회에 걸렸고, 그 해제 시각이 “가장 오래된 24시간 내 적립 + 24h”라 6~7시간 뒤로 안내됐다.

1. 신고 내용

QnA 391 의 사용자 진술 두 건이다.

「スクリーンショットを添付している通り、深夜1:00からグローバルおすすめ#1 を10回視聴したあと、次の視聴の時間を確認したところ(1:24)、 次回の視聴が07:17(6時間後)になっています。広告の視聴のリセットも0:00(KST)の認識で違いないでしょうか？」 — 09-02 16:39 KST

「今日も同じ状況で同じ不具合が出ています。0時すぐと1時すぐに10回ずつ視聴したのち、次は2時台になるはずが7時になっています」 — 09-03 01:08 KST

2. 재현 실측

신고 시각의 cotton_candy_grants 를 그대로 집계해 화면에 뜬 값을 재계산했다. 글로벌픽 #1 은 defaultAdOrder = ['admob', 'internal-shortform', 'pangle'] 의 첫 항목, 즉 AdMob 이다(free_charge_station.dart:47-52 의 shouldShowDebugAdmobItem 이 릴리스에서도 isAdmobAvailable 을 그대로 반환한다).

신고 시점 (JST)hourlydaily (rolling 24h)oldest_daily계산된 표기사용자 신고
2026-09-02 01:241012009-01 07:17:5307:17:53“07:17” ✅
2026-09-03 01:081012009-02 07:44:2407:44:24“7시” ✅

두 건 모두 시간 한도(10)와 일간 한도(120)에 동시에 걸려 있었고, nextAvailableTime 은 두 해제 시각의 max 라 일간 해제 시각이 이겼다. 일간 해제 시각은 oldest_daily + 24h 였으므로 전날의 시청 시각을 그대로 따라다닌다.

3. 근본 원인 원인

일간 한도의 창(window)이 구좌마다 달랐다.

사용자가 물은 “리셋은 0:00 KST 맞나요?” 는 세 구좌 중 둘에서만 맞았다. 실제 손해도 있었다 — 이 사용자의 09-02 KST 일 AdMob 적립은 110회에서 멈췄다(다른 두 구좌는 120회). rolling 창이 어제 시청분을 오늘로 끌고 오면서 10회를 깎은 것이다.

표시 자체의 문제

초과 다이얼로그는 label_ads_exceeded(“이 버튼의 광고 시청 횟수를 초과했습니다”) 아래에 label_ads_limits(“1時間あたり10回、1日120回”)와 해제 시각만 보여줬다. 어느 한도에 걸렸는지도, 현재 몇 회를 썼는지도 표시하지 않는다. 일간 한도로 막힌 사용자가 “시간당 10회”와 6시간 뒤 시각을 나란히 보면 시간 한도가 고장 났다고 읽는 게 자연스럽다.

4. 함께 발견된 결함 별건

4.1 internal / pangle 사전 게이트가 죽은 테이블을 읽고 있었다

배포된 check-ads-count v102(2026-08-28)는 internal·pangle 카운트를 transaction_internal / transaction_pangle 에서 읽는다. 그런데 두 테이블은 신규 행이 없다.

테이블행 수마지막 created_at
transaction_admob12,295,1752026-04-11 09:06 UTC
transaction_pangle2,037,6752026-08-12 13:25 UTC
transaction_internal3,103,1262026-08-12 14:09 UTC
transaction_unity905,4452025-09-17 12:48 UTC

따라서 두 구좌의 사전 게이트는 언제나 allowed:true, 0/0 을 돌려줬다. 실제 차단은 지급 시점 assert_cotton_ad_reward_limit 에서 일어나므로, 사용자는 광고를 끝까지 본 뒤에야 거부되고 “다음 시청 가능 시간”을 미리 볼 방법이 없었다. PICNIC-2377 조사 문서에 남아 있는 실기기 logcat 이 그 증거다. 

checkAdsLimit raw: {allowed: true, counts: {pangle: {hourly: 0, daily: 0}}}

이 경로를 대체하려고 만든 public.get_cotton_ad_limit_status RPC 는 프로덕션에 존재하지만 호출하는 곳이 하나도 없다(앱·edge function·다른 DB 함수 전수 확인).

4.2 프로덕션 전용 함수 — 레포에 SQL 원본이 없다

wallet_private.assert_cotton_ad_reward_limit 과 public.get_cotton_ad_limit_status 는 picnic-supabase·picnic-app 어디에도 정의가 없다. 프로덕션에 직접 적용된 뒤 회수되지 않았다. 같은 경로의 public.grant_ad_cotton 도 프로덕션이 레포보다 앞서 있다(2026-08-18 코튼 게이트 사고 수정분).

public.settle_admob_ad_reward 도 프로덕션 본문이 레포(20260814130000)와 다르다 — 133줄 중 빈 줄을 뺀 전 줄의 해시가 어긋난다. 다만 각 줄을 trim 하면 133줄 전부 일치하므로 차이는 들여쓰기뿐이고 로직 드리프트는 없다. 레포가 배포본의 기준이 아니라는 사실만 다시 확인된 셈이라, 이번 마이그레이션은 그 공백 정렬을 레포 기준으로 되돌리면서 일간 창을 바꾼다.

4.3 wallet RPC manifest 게이트가 이미 red 였다

PR #119(20260902053935)가 get_artist_paid_votes 를 2-인자 → 4-인자로 교체하면서 wallet_service_rpc_catalog/manifest 를 갱신하지 않았다. 그 결과 wallet_private.assert_wallet_service_rpc_manifest() 가 로컬과 프로덕션 양쪽에서 동시에 깨져 있었고, 이 assert 를 호출하는 어떤 마이그레이션도 통과할 수 없는 상태였다. 이번 작업이 처음 노출시켰을 뿐 원인은 아니다.

6b. 교차 리뷰 대응 Codex/Sol

구현이 Claude 였으므로 반대 공급자(Codex, Sol/xhigh)가 읽기 전용으로 적대적 리뷰했다. 지적 5건 중 4건을 수정했고 각각 옛 구현에서 red 가 나는 테스트를 붙였다. 1건은 근거를 들어 범위 밖으로 남겼다.

심각도지적판정대응
major KST 일 상한을 timestamptz + interval '1 day' 로 구해 세션 TimeZone 의 DST 에 따라 23/25시간이 된다 성립 세 함수 모두 timestamp 단계에서 더한 뒤 KST 로 되돌린다. 재현: NY 세션 2026-03-07 15:00+00 + 1day → 14:00Z
minor 시간 창 비교자가 사전 게이트는 >=, AdMob 정산은 > 라 정확히 cutoff 에서 답이 갈린다 성립 >= 로 통일. 사전 게이트가 "차단" 이라 말한 상태에서 정산이 지급하지 않는다
major edge 가 성공했지만 비어 있거나 형태가 잘못된 RPC 응답을 "0회 사용" 으로 fail-open 한다 성립 행 없음·비수치·음수·verdict 없음·파싱 불가 시각을 전부 거부(fail-closed). DB 의 allowed:false 도 판정에 반영
blocker 회수한 assert 의 소유권/EXECUTE 가 지급 경로 소유자와 호환되지 않는다 부분 성립 프로덕션 영향 없음(실측: 이미 owner wallet_command_owner, revoke 대상이 ACL 에 없음). clean DB 발산은 실재 → owner/ACL 명시 선언
blocker 레포의 grant_ad_cotton 이 한도 assert 를 부르지 않아, 레포로 만든 DB 는 internal/pangle 일간 한도가 없다 성립 · 범위 밖 아래 참조

마지막 blocker 를 이 티켓에서 닫지 않은 이유

프로덕션 정의를 verbatim 회수해 md5 일치까지 확인하고 적용했다 (grant_ad_cotton 20e5da9e…, 그리고 이 함수가 부르는데 프로덕션에만 있는 wallet_private.assert_cotton_runtime_ready b5e7c7d1…). 그 상태에서 admob_release_gate_anchor.test.sql 이 ADMOB_PROVIDER_GATE_DEFINITION_UNRECOGNIZED 로 붉어졌다. 20260814120500 이 만든 wallet_private.apply_admob_provider_gate_patch() 가 grant_ad_cotton 을 md5 지문으로 확인하고 마이그레이션 시점에 텍스트로 패치하는 구조라, 본문을 통째로 바꾸면 그 지문이 깨진다.

즉 이 회수는 그 패처와의 재조정을 포함하는 별도 작업이다. 일간 창을 KST 로 통일하는 범위 안에서 기존 안전장치를 깨면서 할 일이 아니라고 판단해 되돌렸고, 마이그레이션 헤더에 알려진 공백으로 명시했다 — 프로덕션은 영향 없음, 레포로 만든 DB 에는 internal/pangle 일간 한도 없음, 회수에 필요한 두 md5 를 남겨 뒀다.

7. 배포 순서 미실행

  1. 20260904110000 → 20260904120000 순서로 프로덕션 적용(supabase db query --file, db push 불가).
  2. 곧바로 check-ads-count 배포. 그 사이에는 사전 게이트만 rolling 24h(더 엄격) 상태로 남는다 — 짧고 보수적인 방향이다.
  3. 배포 확인 후 별도 마이그레이션으로 get_admob_cotton_reward_counts 드롭.
  4. 앱 다이얼로그는 OTA 또는 신규 빌드로 나간다. 서버 수정만으로도 신고된 증상(6~7시간 뒤 안내)은 해소된다 — 앱 변경은 재발 방지용 안내 개선이다.
