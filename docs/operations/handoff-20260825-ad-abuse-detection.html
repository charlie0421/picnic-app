01이 파이프라인이 원래 하려던 것

과거 2026-04-11 에 686개 어뷰징 계정으로 AdMob 이 셧다운된 이력이 있는 서비스다(admob-shutdown-reason 참조). 그 재발을 막으려고 만든 자동 탐지 라인이다.

cron 57 (0 21 * * * = 매일 06:00 KST)
  → detect-ad-anomaly 엣지 함수 호출 (service_role Bearer)
    → detect_abuser_candidates() RPC 실행
      → 최근 30일 하루 200건+ 광고보너스를 3일+ 반복한 계정 탐지
      → custom_logs 에 요약·후보 기록 (항상)
      → 미밴 후보 > 0 이고 AD_ANOMALY_WEBHOOK_URL 있으면 → Slack 알림

자동 조치(밴·회수)는 없다. 탐지 → 기록 → 알림까지고, 실제 밴/보너스 회수는 사람이 알림을 보고 어드민 콘솔에서 수동 판단하는 구조다.

02발견한 것 — 네 겹으로 깨져 있다

① cron 이 매 실행 500 인데 "succeeded" 로 위장

함수가 permission denied for function detect_abuser_candidates 로 500 을 반환한다. 그런데 cron.job_run_details 는 172회 전부 succeeded 다 — net.http_post 이 fire-and-forget 이라 "요청 전송 성공"만 기록하고 함수 응답은 안 본다. 그래서 아무도 몰랐다. 실제 함수 응답은 function_edge_logs 에서만 보이고, 어제(v20)·오늘 수동(v24) 둘 다 500 이었다. custom_logs 의 마지막 정상 기록이 6/25 — 그 무렵부터 죽었다.

② ACL 증발 — 재정의 때마다 grant 가 날아간다

detect_abuser_candidates 의 현재 권한은 {postgres=X/postgres} — service_role 도 authenticated 도 EXECUTE 가 없다. anti-abuse RPC 17개 중 이 함수와 revoke_abuser_bonus 딱 둘만 이 상태고, 나머지 15개는 service_role EXECUTE 를 갖는다.

원인: 이 함수는 DROP FUNCTION + CREATE 로 재정의되는 패턴이라(RETURNS TABLE 타입 변경 때문) 재정의 때마다 ACL 이 초기화된다. 마이그레이션 20260506135605_fix_detect_abuser_candidates 가 GRANT ... TO authenticated 로 복원했지만, 그 뒤 또 재정의되며 다시 사라졌다. grant 한 줄로 지금 열어도 다음 재정의 때 또 터진다.

③ 소비자 불일치 — grant 대상과 호출자가 다르다

마이그레이션은 authenticated 에 grant 하는데, cron/엣지 함수는 service_role 로 호출한다. 즉 마이그레이션이 살아 있었어도 cron 경로는 애초에 안 맞았다. authenticated grant 는 어드민 콘솔이 이 RPC 를 직접 부르는 용도로 보인다(revoke_abuser_bonus 가 엣지에서 안 불리고 authenticated 여야 하는 것과 같은 맥락). 두 소비자가 다른 롤인데 grant 전략이 하나뿐이다.

④ 실효성 미검증 — 살아 있었을 때도 0명, 임계값이 현실의 3배

정상 실행 6회(5/6~6/25) 전부 total_candidates: 0. 이유: 임계값이 하루 200건인데 실제 type='AD' 적립의 하루 최대가 65건이다 — 넘을 계정이 구조적으로 없다.

더 나쁜 단서: parent_id is null 전체(타입 무관)로 보면 하루 최대 514건이고, type=null 이 최근 30일 27,158건으로 최다다(type='AD' 는 13,052건). type='AD' 필터가 실제 광고 적립의 상당수를 놓치고 있을 가능성이 크다. 임계값과 타입 필터 둘 다 실데이터로 재보정해야 한다.

⑤ 잡아도 알림이 안 간다

AD_ANOMALY_WEBHOOK_URL 이 엣지 secrets 에 없다. 다른 웹훅(ANTI_ABUSE_WEBHOOK_URL·WALLET_ALERT_WEBHOOK_URL·Slack 4종)은 다 있는데 이것만 빠졌다. 함수를 살리고 탐지가 후보를 찾아도 custom_logs 에 조용히 쌓일 뿐 아무에게도 안 알린다.

03응급 완화는 가능하나 반쪽이다

안전하게 지금 적용할 수 있는 것은 grant 한 줄뿐이다. 읽기전용 함수·service_role 한정·멱등적이고, 다른 세션이 이 grant 를 건드리지 않음을 확인했다.

grant execute on function public.detect_abuser_candidates(integer,integer,integer) to service_role;

그러나 이것만으로는 "0명 탐지하는 함수를 다시 돌게 했다"에 그친다. ②(재발), ④(0명), ⑤(알림 부재)가 남아 실질 방어가 안 된다. 그래서 이 세션은 응급 grant 도 하지 않고 통째로 넘긴다 — 반쪽 복구가 "고쳤다"는 착시를 주는 게 더 위험하다.

04다음 세션이 할 일 (권장 순서)

  1. 타입·임계값 재보정 (먼저). 실제 광고 적립이 type='AD' 로만 기록되는지, type=null(최다)에 광고가 섞였는지 규명. transaction_id 패턴으로 광고 출처를 식별할 수 있는지 확인. 그 위에서 임계값을 실분포 기반으로 정한다. 이게 안 되면 나머지는 무의미하다.
  2. ACL 증발 영구 차단. grant 를 마이그레이션 말미가 아니라 함수 재정의와 같은 트랜잭션에 묶거나, 재정의를 CREATE OR REPLACE(ACL 보존)로 바꿔 RETURNS TABLE 변경 없이 유지. revoke_abuser_bonus 도 같은 상태이므로 함께 처리.
  3. 소비자별 grant 명시. cron 경로 = service_role, 어드민 콘솔 경로 = authenticated. 둘 다 필요하면 둘 다 grant 하고 각 경로를 실호출로 검증.
  4. 알림 채널 신설. AD_ANOMALY_WEBHOOK_URL secret 설정. 기존 ANTI_ABUSE_WEBHOOK_URL 을 재사용할지 별도 채널로 분리할지 결정.
  5. cron 성공 판정 개선. pg_net fire-and-forget 이라 함수 500 이 succeeded 로 보인다. 실패를 실제로 감지하려면 함수가 실패 시 별도 알람을 쏘거나, net._http_response status 를 후속 확인하는 감시를 둔다.
