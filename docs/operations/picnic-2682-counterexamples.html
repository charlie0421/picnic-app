PICNIC-2682: Tapjoy 콜백 64-hex UUID 에러 (22P02) 반례 보고서

A. 앱 쪽 반례 (App-side Counterexamples)

Tapjoy SDK는 사용자 ID가 설정되지 않은 경우, 기본적으로 기기 식별자(Android ID 또는 GAID 등)의 SHA-256 해시값(64자리 hex)을 서버로 전송(snuid)합니다. 현재 앱 코드 구조상 setUserID가 누락될 수 있는 반례는 다음과 같습니다.

  • 코드 경로: picnic_lib/lib/core/utils/app_initializer.dart:393 에서 Tapjoy.connect()가 앱 초기화 시 호출되지만, picnic_lib/lib/presentation/widgets/vote/store/free_charge_station/platforms/tapjoy_platform.dart:48 의 Tapjoy.setUserID()는 사용자가 무료충전소 광고를 보기 위해 진입(showAd)할 때만 호출됩니다.
  • 반례 시나리오: 사용자가 타 앱의 Tapjoy 오퍼월에서 앱 설치를 완료하고 딥링크로 진입하여 앱이 켜진 경우, connect()에 의해 Tapjoy 서버로 전환 이벤트가 보고되어 콜백이 발생하지만, showAd()를 누르기 전이므로 setUserID()는 한 번도 호출되지 않았습니다. 결과적으로 기본 해시값이 전송됩니다.
사용자 상태 / 액션 사용자 ID (snuid) 상태
로그아웃 / 미로그인 setUserID 호출 시 currentUser!.id가 null이므로 예외가 발생하거나 접근 불가. Tapjoy는 64-hex 기본 해시 송신.
계정 전환 오퍼월 재진입 전까지 이전 계정 ID가 남아있거나, 새로 초기화될 경우 64-hex 송신 가능성 존재.
앱 재시작 / 딥링크 진입 앱 실행 시 connect()만 불리고 setUserID 미호출. 보상 전환 발생 시 64-hex 송신.
백그라운드 복귀 프로세스가 죽었다 살아난 경우 초기화만 다시 되고 오퍼월을 열기 전까지 64-hex 유지.

B. 서버 쪽 반례 (Server-side Counterexamples)

서버측 callback-tapjoy의 검증 로직 결함으로 인하여 22P02 DB 예외와 불필요한 재시도가 유발됩니다.

  1. 파라미터 추출: _shared/ad/platforms/tapjoy-service.ts:44 (extractParameters)
  2. 사용자 존재 여부 확인: _shared/ad/platforms/tapjoy-service.ts:67 (checkUserExists) -> _shared/ad/base-ad-service.ts:91 (DB 조회)
  3. 중복 트랜잭션 검사: tapjoy-service.ts:72 (checkExistingTransaction)
  4. 서명(Verifier) 검증: tapjoy-service.ts:77 (verifySignature)
콜백 케이스 서버 내부 처리 및 에러 발생 지점 응답 HTTP 상태 및 본문 Tapjoy 재시도 유발 여부
비 UUID snuid (예: 64 hex) checkUserExists에서 UUID 컬럼에 String 질의 -> PostgreSQL 22P02 invalid input syntax 발생. catch 되어 false 처리. 400 {"success":false,"error":"검증 중 오류가 발생했습니다."} 유발 (Tapjoy는 400을 실패로 간주하고 재시도함)
존재하지 않는 사용자 checkUserExists 정상 동작 후 false 반환 400 {"success":false,"error":"존재하지 않는 사용자입니다."} 유발
중복 트랜잭션 checkExistingTransaction true 반환 400 {"success":false,"error":"이미 처리된 트랜잭션입니다."} 유발
verifier 불일치 (서명 오류) verifySignature false 반환 400 {"success":false,"error":"서명이 유효하지 않습니다."} 유발

C. 다른 광고 콜백 결함 유무

  • callback-admob: 안전함. (supabase/functions/callback-admob/index.ts) Opaque claim 토큰 내에서 서명된 user_id를 추출하여 DB 예외 우려 없음.
  • callback-pangle: 안전함. (supabase/functions/callback-pangle/index.ts) 서명된 extra 토큰 검증 후 정보 활용.
  • callback-unity: 비활성화. (supabase/functions/callback-unity/index.ts) 403 반환 처리됨.
  • callback-pincrux: 동일 결함 존재. (supabase/functions/_shared/ad/platforms/pincrux-service.ts:43) checkUserExists(params.usrKey)를 먼저 호출하여 비 UUID 입력 시 22P02 예외가 동일하게 발생할 수 있습니다. 또한 이 클래스는 서명 검증 로직(verifySignature) 자체가 누락되어 있습니다.

E. 결론

원인 1 (확신도: 매우 높음): 앱에서 Tapjoy.connect()는 초기화 시 전역으로 호출되나, setUserID()는 사용자가 명시적으로 무료충전소에 진입할 때만 호출됩니다. 따라서 Tapjoy 광고로 앱을 설치 후 처음 실행할 때 발생하는 자동 전환 콜백 등에서는 SDK가 설정된 ID를 찾지 못하고 기기 고유값의 SHA-256 64자리 hex를 snuid로 대신 보냅니다.

원인 2 (확신도: 매우 높음): 서버측 TapjoyService는 수신된 snuid 형식을 검증하지 않고, 서명(verifier) 검증보다 먼저 user_profiles(UUID 타입) 테이블 조회에 사용합니다. 이로 인해 PostgreSQL 22P02 예외가 발생하여 400 Bad Request가 반환됩니다. Tapjoy는 400을 실패로 인지해 4분 간격으로 계속 재시도하므로, 대량의 에러 로그 폭풍이 발생합니다.

추가 검증이 필요한 데이터:

  • Tapjoy 서버가 400 응답 외에 403 Forbidden 이나 에러 플래그가 포함된 200 OK 응답에 대해서는 재시도를 중단하는지에 대한 공식 문서 또는 실제 연동 테스트 결과.
  • Pincrux 콜백 역시 22P02 에러에 노출되어 있으므로 동일한 재시도 폭풍이 발생하는지에 대한 백엔드 로그 확인.
