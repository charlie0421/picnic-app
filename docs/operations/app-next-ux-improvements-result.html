resend — a user-driven duplicate write.

Re-checks I was asked to make after the narrowing:

 (a) SINGLE-FLIGHT still holds. `_isSending = true` is still set synchronously
     at :220, before the first await, so a second synchronous tap is still
     rejected by the :194-200 guard. Unchanged by the narrowing.

 (b) FINALLY semantics are correct on every exit.
     - success: try completes -> finally (_isSending=false) -> falls through
       to :243.
     - failure: catch runs the snackbar, then `return` at :238; Dart runs the
       finally BEFORE returning, so _isSending is still cleared. No stuck
       spinner / permanently disabled send button.
     - unmounted at completion: `if (mounted)` in the finally is false, so no
       setState on a defunct State; the flag is irrelevant on a dead State.

File: picnic_lib/test/presentation/pages/my_page/my_artist_page_render_test.dart
Test: 'same element rebuild preserves the active search'

My objection to the old coverage was precise: the remount test toggles
`const MyArtistPage()`, const instances are canonicalised, and Flutter's
Element.updateChild short-circuits on `child.widget == newWidget`, so
MyArtistPage.build — and therefore ProviderScope.didUpdateWidget /
updateOverrides — was never re-entered by any test.

The new test fixes exactly that, and I verified it does:
 - The host builder returns `MyArtistPage(key: const ValueKey(...))`. The KEY
   is const; the WIDGET is not. Each `rebuildHost(() {})` therefore produces a
   non-identical MyArtistPage, MyArtistPage does not override operator==, so
   updateChild takes the `child.update(newWidget)` branch and the State
   rebuilds. This is the one detail that makes or breaks the test and it is
   correct.
 - `expect(identical(pageElement, tester.element(find.byType(MyArtistPage))),
   isTrue, reason: 'the test must rebuild, not remount, MyArtistPage')` pins
   rebuild-not-remount, so the test cannot silently degrade into a duplicate
   of the remount test.
 - `expect(identical(innerContainer, rebuiltInnerContainer), isTrue)` proves
   the nested ProviderScope container survived, i.e. this really is the
   didUpdateWidget/updateOverrides path and not a fresh scope.
 - `rebuiltInnerContainer.read(myArtistSearchQueryProvider) == 'Alpha'` and
   `TextField.controller!.text == 'Alpha'` assert input and provider still
   agree.
 - zero additional `/rest/v1/artist` requests after the rebuild.

Can it fail? Yes, three ways at once. If updateOverrides re-ran the notifier
build, the provider would read '', the _querySubscription listener would fire
_loadInitialData('') producing a new HTTP request, and the TextField would
still show 'Alpha'. Not a false-green.

Harness check: `capturedMockRequests` is `List<Uri>` in
