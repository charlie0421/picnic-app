S0 기준 기록소스 HEAD·상태·빌드 입력 존재와 주요 소스·lock 해시를 기록한다. 실기기 버전·갱신 시각, 기존 AVD 이름·설정 파일 크기·수정 시각도 보관한다. CM 서명 환경변수와 ANDROID_SERIAL을 빌드 자식 환경에서 제외하고 key.properties 부재를 확인한다.
S1 빌드 · 1,800초제품 디버그 빌드를 수행한다. 소스·설정 변경이나 릴리스 자격증명이 필요하면 중단한다. Flutter가 생성하는 gradlew·wrapper jar·local.properties는 허용된 생성 파일이다. 성공 종료, 추적 소스·lock 유지, 소유 빌드 프로세스와 Gradle 정리를 확인한다.
S2 APK 검사APK를 소유 경로에 복사한다. 그 파일의 SHA256, 패키지, 버전 1.3.6+130605, arm64 ABI, prod 설정 자산의 존재, 공개 서명자 인증서를 검사한다. 설정 내용·키스토어는 열람하지 않는다. 검사한 복사본만 설치한다.
S3 새 대상 · 생성 60초 / 부팅 300초 / GMS 60초고유 이름의 AVD 하나만 생성한다. 실행 PID·AVD 이름·정확한 새 emulator serial을 연결한다. 부팅 완료, 사용자 0 하나와 현재 사용자 0, 활성 GMS·Play Store 패키지를 확인한다. 제품 패키지가 이미 있거나 조회가 불명확하면 중단한다. 이미지 이름만으로 GMS 동작을 판정하지 않는다.
S4 설치 · 120초정확한 새 serial과 사용자 0에 설치한다. 설치된 APK를 다시 읽어 검사한 파일과 해시가 같은지 확인하고 버전·패키지를 대조한다. 실기기에 설치·삭제 명령을 보내지 않는다.
flutter build apk --debug --no-pub   --dart-define=ENVIRONMENT=prod   --dart-define=PANGLE_ENVIRONMENT=prod   --dart-define=PAYMENT_ENVIRONMENT=prod

없는 gradlew는 설치된 Flutter의 getExecutable → injectGradleWrapperIfNeeded가 캐시에서 생성한다. 파일 부재만으로 빌드 실패를 단정하지 않는다. 실제 빌드 결과는 별도 증거다.

S5–S9 · 실제 등록 관측

앱 첫 실행 전에 서버 기준값 B0를 읽는다. 결과는 지정 계정 행의 존재 여부, Android 토큰 존재 여부·해시, 갱신 시각, 서버 현재 시각만 포함한다. 행·토큰이 없는 상태도 유효하다. 조회 실패를 변화 없음으로 처리하지 않는다. 사용자에게 에뮬레이터 단계 동안 실기기 앱을 열지 않도록 안내한다.

  1. S5: 앱 시작을 180초 안에 관측한다. 정상 로그인 화면, 초기화 오류, 업데이트 요구, 네트워크·동의 대기를 구분한다. 업데이트 요구를 우회하지 않는다. 첫 실행부터 운영 SDK 통신이 가능하다.
  2. S6: 준비된 에뮬레이터에서 사용자가 Google 계정 추가·선택·동의와 알림 권한을 처리한다. 대기 상한은 600초다. canceled·No credentials·인증 오류만으로 SHA 미등록을 확정하지 않는다.
  3. S7: Supabase 세션 생성 뒤에도 기기 등록·로컬 저장·후속 처리에서 실패할 수 있다. 인증 흐름의 실패는 세션·토큰 쓰기 가능/불명으로 둔다. 로그 부재나 사용자 취소 진술로 서버 쓰기 부재를 증명하지 않는다.
  4. S8: 최신 getToken 실패는 이전에 보관된 토큰의 등록 부재를 뜻하지 않는다. 허용된 경우에만 사용자 주도의 복귀를 한 번 요청한다.
  5. S9: 로그인 후 120초 동안 등록 성공·HTTP 오류·시간 초과·네트워크 오류 등을 허용한 이벤트로 구분한다. 성공 이벤트 뒤 15초 간격 최대 4회 서버를 조회한다. Android 토큰이 존재하고 B0 이후 갱신됐으며 기준 해시에서 바뀌어야 관측된 에뮬레이터 해시 E로 기록한다.

클라이언트의 12초 timeout은 서버 처리 종료나 취소를 증명하지 않는다. 자동 재호출과 이미 발행된 요청이 남을 수 있다. 해시가 같아도 같은 토큰의 재등록이 있었을 수 있다. E를 관측하지 못하면 unknown으로 보존한다.

로그 수집과 증거 범위

앱 UID로 제한한 logcat -v epoch을 scripts/qa/fcm_event_filter.py에 바로 연결한다. 연도가 없는 시각 대신 epoch 밀리초를 사용해 새 이벤트의 시간 창과 기기·서버 시각 보정을 확인한다. 필터가 허용한 시각·단계·결과 클래스·숫자 상태 코드·소요 시간만 저장한다. 원시 stdout, tail, 전체 앱 로그를 파일이나 화면에 남기지 않는다. 필터 소스는 승인됐으며, 실제 수집은 정확한 대상·앱 UID와 정상 필터 종료를 확인해야 한다. 수집·종료 처리가 준비되기 전에는 앱을 실행하지 않는다. 인식되지 않거나 누락된 로그는 unknown이며, 세션·쓰기 부재의 증거가 아니다.

계정 객체, 이메일·사용자·기기 ID, UID 접두부, 세션·access/refresh/id 토큰, FCM 토큰 원문, 응답 data/details, 예외 본문·스택은 제외한다. 원시 Edge 함수 로그와 계정 목록 덤프·로그인 화면 캡처를 수집하지 않는다. 실기기 복구 로그에도 같은 제한을 적용한다.

공개 APK 인증서·패키지·버전은 검사에 사용할 수 있다. 원시 계정·기기 식별자와 서버 토큰 해시는 Git 보고서에 넣지 않는다. Android 출력 형식 검사는 shell UID의 합성 기록만 사용했다. 첫 검사에서는 줄마다 다른 PID를 사용해 거부됐고, 한 프로세스의 완전한 박스로 바꾸자 인식됐다. 필터 코드 변경이나 제품 앱 실행은 없었다. 보고서에는 단계 결과와 필요한 시각·해시 변화 여부만 남긴다.

모든 결과의 복구·정리

정리는 단계 번호가 아니라 생성한 자원의 소유권으로 선택한다. 설치 전에 중단했어도 소유 에뮬레이터와 AVD는 정리한다. 첫 앱 실행 이후에는 성공·실패·취소·시간 초과·불명 결과 모두 아래 복구 처리에 들어간다.

  1. 소유 앱을 명시한 사용자 0에서 중지하고 프로세스 부재를 확인한다. 소유 에뮬레이터는 PID·AVD 이름을 다시 검증한 뒤 종료한다. 앱 중지와 에뮬레이터 종료를 모두 확인할 수 없으면 복구 성공을 추정하지 않고 자원을 보존해 미해결로 보고한다.
  2. 등록 상태를 60초 후와 그다음 30초 후에 관측한다. 설명되지 않은 변화는 최대 두 번 더 확인한다. 이 시간 창은 이미 발행된 서버 작업의 완료나 취소를 보장하지 않는다. 불안정 상태에서 복구 성공을 선언하지 않는다.
  3. 실기기의 안전한 등록 이벤트 수집과 서버 기준 시각을 준비한다. 기기·서버 시각 오프셋을 기록한다. 사용자가 기존 운영 앱을 정상 재실행하거나 포그라운드로 가져오도록 요청한다. 대기 상한은 600초다.
  4. 실기기의 새 등록 성공 이벤트와 그 이후 서버 갱신을 모두 확인한다. 서버 시각은 기준 시각 이후이며 보정한 이벤트 시각의 ±30초 안이어야 한다. 15초 간격 최대 8회 조회한다. E를 실제 관측한 경우만 E와 다른 해시를 요구한다. 정상 토큰 회전은 허용하며 기존 B0 해시와 같을 필요는 없다.
  5. 복구 후 60초 동안 두 번 더 확인한다. 변화가 있으면 대응하는 실기기 등록 이벤트로 설명할 수 있어야 한다. 불명확한 추가 변화는 미해결로 남긴다.
  6. 소유 에뮬레이터 종료가 확인된 뒤 소유 AVD만 삭제한다. 기존 AVD 목록·설정과 실기기 앱 버전·갱신 시각이 기준과 같은지 확인한다. 토큰 원문이나 직접 DB 쓰기로 복구하지 않는다.

실기기 등록 로그가 없거나 연결·서버 조회·정리를 확인하지 못하면 복구 미확인이다. 사용자에게 남은 상태를 알리며 통과로 바꾸지 않는다. 사용자 재실행 요청은 한 번만 추가할 수 있다.

판정과 남은 확인

등록 관측과 복구 확인은 별도로 보고한다. 둘 다 충족하고 소유 자원 정리가 확인돼야 B 절차 완료다. 실제 APK·GMS·대화형 인증·FCM 발급·서버 등록·실기기 복구는 각각 실행 증거가 필요하다.

현재 Cloud OAuth·API 키 제한은 조회 권한 부족으로 미확인이다. 로컬 인증서 목록이나 과거 운영 등록은 새 빌드의 로그인 성공을 증명하지 않는다. 업로드 키와 Play 배포 앱의 서명이 같다고 가정하지 않는다. iOS 실제 등록, 알림 전달, 늦은 서버 쓰기의 완전한 부재, 배포·Sentry/Jira 해결을 이 절차의 결과로 주장하지 않는다.
