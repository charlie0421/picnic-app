RLS 도입

공개 anon 키 노출면 조사에서 파생된 별도 과제. 앞선 조치들은 비로그인 접근만 막았고, 로그인한 사용자가 타인의 데이터를 읽는 문제는 RLS 없이는 닫히지 않는다. 사이드 이펙트가 커서 장애 대응과 분리했다.

01지금 상태

무엇이 이미 됐고 무엇이 남았는지.

public 스키마 테이블 193개 중 88개는 RLS 가 켜져 있고 105개는 꺼져 있다. 꺼진 105개 중 90개가 공개 anon 키로 읽힌다. 쓰기 가능했던 32개는 0단계에서 전부 회수했다(2026-08-21). 이 과제에 남은 것은 읽기다.

0단계는 끝났다 — 다시 하지 말 것

2026-08-21 프로덕션에 anon 의 INSERT·UPDATE·DELETE 를 32개 테이블 전부에서 회수했다. 이력 20260821990001. 초안이 제안했던 "위험한 5개 먼저" 축소안은 쓰지 않았다 — 적용 스크립트의 preflight 가 32×3=96 정확 일치를 요구해서, 쪼개면 검증되지 않은 SQL 을 새로 써야 했기 때문이다.

실측 결과: anon 쓰기 grant 96 → 0, 컬럼·PUBLIC·롤 멤버십을 포함한 effective write path 없음, anon 읽기 32 유지(이 단계는 읽기를 건드리지 않는다), authenticated·service_role INSERT 32/32 유지.

기록: picnic-supabase 브랜치 charlie0421/rls-prep 의 supabase/prod-cutover/rls-0b-anon-write-revoke/. 아직 PR 이 없다 — 프로덕션에 적용된 변경이 저장소 main 에 없는 상태이므로 이 과제 착수자가 먼저 올릴 것. 롤백은 rollback/01_restore_anon_writes.sql, 테이블 하나만 되돌릴 때는 해당 줄만 실행한다.

2026-08-19 에 가장 민감한 6개 테이블(receipts, star_candy_history, star_candy_bonus_history, vote_pick, transaction_internal, view_transaction_all)과 함수 2개(get_user_activity_unified, _count)의 anon 권한을 회수했다. 이건 비로그인만 막은 것이고 RLS 와는 다른 층위다.

이 과제가 닫으려는 것

지금은 authenticated 롤이 RLS 없이 전 행을 읽는다. 계정 하나만 만들면 transaction_admob 1,229만 행에서 타인의 광고 이력을, user_profiles 10.7만 행에서 타인의 이메일과 생년월일을 조회할 수 있다. 계정 생성이 자유로운 서비스이므로 공격자도 authenticated 가 될 수 있다는 전제로 봐야 한다.

02지켜야 하는 불변식

  • SECURITY DEFINER 함수는 RLS 를 우회한다. 이 DB 에 297개가 있고, 지갑·정산 로직이 전부 그 위에 서 있다. RLS 를 켜도 이들은 그대로 동작한다 — 오히려 이게 안전한 이전 경로다.
  • 서비스 롤도 RLS 를 우회한다. 순수 service_role 로 도는 엣지 함수 35개는 영향이 없다.
  • 이미 켜진 88개를 건드리지 않는다. 특히 지갑 신세대 테이블은 "RLS ON + 정책 없음 + authenticated 권한 없음" 으로 완전 차단돼 있고, 접근은 전부 SECURITY DEFINER 함수를 거친다. 이게 이 코드베이스의 정답 패턴이다.
  • 어드민 콘솔은 authenticated 로 동작한다. service_role 이 아니다. 정책에 관리자 분기가 없으면 어드민 화면이 통째로 빈다.

03반드시 알고 있어야 할 함정

이 코드베이스에서 실제로 밟은 것들. 순서대로 위험하다.

① 엣지 함수 7개는 authenticated 로 돈다 — RLS 가 적용된다

service key 로 클라이언트를 만들어도 Authorization 헤더를 호출자 JWT 로 덮어쓰면 PostgREST 는 그 JWT 로 롤을 정한다. 즉 service key 는 apikey 일 뿐이고 실행 롤은 authenticated 다.

createClient(URL, SERVICE_ROLE_KEY, {
  global: { headers: { Authorization: req.headers.get('Authorization') } }
});   // ← 이건 service_role 이 아니다

해당 함수: ad-reward-claim · ad-reward-status · artist-request-add · callback-ad-shortform-more · exchange-star-candy-to-jma · expiring-bonus · track-country

2026-08-19 에 track-country 가 정확히 이것 때문에 6일간 조용히 깨져 있었다. 1b 컷오버가 authenticated 의 user_profiles UPDATE 를 회수했는데, 이 함수가 그 롤로 쓰고 있었다. RLS 를 켜면 나머지 6개에서 같은 일이 난다.

② supabase-js 는 권한 오류를 예외로 던지지 않는다

{ error } 로 반환한다. try/catch 만 있고 error 를 확인하지 않는 호출부는 실패해도 성공처럼 로그를 남기며 지나간다. track-country 는 콘솔에 country updated KR 을 찍으면서 행은 바뀌지 않은 상태로 6일을 보냈다.

RLS 를 켜기 전에 대상 테이블을 쓰는 모든 호출부의 error 확인 여부를 먼저 점검할 것. 이게 없으면 롤아웃 실패를 감지할 수단이 없다.

③ 뷰는 기본이 definer 의미론이다

view_transaction_all 은 security_invoker 가 설정돼 있지 않다. 이런 뷰는 기반 테이블에 RLS 를 켜도 뷰 소유자 권한으로 읽으므로 RLS 를 통과한다. 뷰를 통한 우회 경로를 함께 닫지 않으면 테이블만 잠그는 셈이 된다.

대상 뷰를 전수 조사하고 alter view ... set (security_invoker = on) 을 함께 검토할 것. 단 이걸 켜면 뷰를 읽던 화면이 정책의 영향을 받게 되므로 같은 롤아웃 단위로 묶어야 한다.

④ 정책 없이 RLS 만 켜면 전면 차단이다

PostgreSQL 은 정책이 하나도 없는 RLS 테이블을 "아무도 못 읽음"으로 해석한다. 지갑 테이블 19개가 의도적으로 이 상태다 — 하지만 앱이 읽는 테이블에 같은 짓을 하면 화면이 빈다.

앱이 직접 조회하는 테이블은 최소 30종이며 user_blocks(13곳) · artist(11) · posts(10) · comments(7) · user_profiles(5) 순으로 참조가 많다. 정책을 먼저 만들고 RLS 를 켜는 순서를 지킬 것.

0단계(anon 쓰기)용으로 2026-08-19 에 확인한 것. 0단계는 이 감사를 근거로 적용됐고, 아래 표는 1~6단계에서도 그대로 유효하다.

이 감사가 덮지 못하는 것 — 0단계에서는 실제로 문제가 없었다

정적 감사는 현재 코드만 덮는다. 이미 배포돼 사용자 폰에 있는 구버전 앱이 로그인 전에 쓰고 있었다면 회수 직후 드러난다. 그래서 적용 후 permission denied for table <이름> 을 추적했다.

결과: 회수한 32개 테이블에서 거부 0건(2026-08-21 13:19 KST 확인). 같은 기간에 잡힌 테이블 거부는 user_profiles 뿐이고, 이건 회수 대상이 아니며 8/20 84건 → 8/21 18건으로 회수 이전부터 있던 별건이다. 함수 거부 get_active_promotion_campaigns(anon EXECUTE 없음) 도 8/18 에 이미 12시간당 676건씩 나던 선재 건이다.

다만 관찰이 끝난 것은 아니다 — 24~48시간 기준으로는 절반쯤 왔다. 1~6단계에서도 같은 추적이 필요하고, 뜨면 그 테이블만 grant 한 줄로 즉시 복구한다.

05권장 진행 순서

한 번에 105개를 켜지 않는다. 되돌리기 쉬운 순서로 쪼갠다.

anon 쓰기 회수는 이 과제의 0단계였다 — 적용 완료

별도 작업으로 뺄지 검토했지만 같은 부류의 작업이다 — 감사 대상(앱·웹·어드민·구버전), 조용한 실패 위험, 단계적 적용, 로그 감시, 롤백 규율이 전부 겹친다. "이 테이블에 anon 이 쓰는가"는 "이 테이블에 어떤 정책이 필요한가"의 부분집합이라, 따로 하면 같은 테이블을 두 번 감사하게 된다.

다만 설계 비용은 다르다. RLS 는 테이블마다 "누가 무엇을 볼 수 있나"를 정해야 하는 제품 결정이고, anon 쓰기 회수는 판단이 없다 — 비로그인 쓰기를 허용할 이유가 있는 테이블은 없다. 그래서 정책 설계보다 먼저 닫았다. 2026-08-21 에 32개 전부 적용됐으므로 아래 0단계는 이력이고, 착수 지점은 1단계다.

  1. 0anon 쓰기 회수 — 완료 (2026-08-21)

    32개 테이블의 anon INSERT·UPDATE·DELETE 를 한 트랜잭션에서 전부 회수했다. 읽기는 건드리지 않았다. 운영 데이터가 있던 12개는 application_logs(125,197) · vote_item(77,895) · devices(29,103) · artist(3,141) · posts(575) · artist_group(291) · vote(235) · cs_4_11_ad_fast_analysis(183) · vote_reward(182) · media(139) · comments(66) · comment_likes(53), 나머지 20개는 미운영·설정성이었다.

    적용 후 거부 0건이고 authenticated 경로는 32/32 살아 있다. 여기서 할 일은 남아 있지 않다 — 저장소 PR 만 아직 없다(01 참조).

  2. 1분류

    105개를 넷으로 나눈다 — ⓐ 공개 콘텐츠(정책 true), ⓑ 본인 데이터(auth.uid() = user_id), ⓒ 서버 전용(정책 없음 + 권한 회수), ⓓ 관리자 전용. user_id 컬럼 유무가 1차 힌트지만 그것만으로 판단하지 말 것.

  3. 2ⓒ 서버 전용부터

    앱이 안 읽는 테이블이 가장 안전하다. transaction_* 4종, debug_logs, application_logs, function_request_log, 로그·큐 계열. 지갑 신세대 패턴(RLS ON + 정책 없음 + 권한 회수)을 그대로 적용한다.

  4. 3ⓓ 관리자 전용

    admin_*, role*, permissions, blocked_ips, device_bans. is_admin_or_super() 정책 하나로 끝난다. 어드민 콘솔이 authenticated 로 도는 것만 확인할 것.

  5. 4ⓑ 본인 데이터

    여기서 함정 ①이 터진다. 엣지 함수 7개가 이 테이블들을 건드리는지 먼저 확인하고, 건드리면 그 함수를 순수 service_role 로 고친 뒤에 켤 것.

  6. 5ⓐ 공개 콘텐츠

    정책 true 라 읽기는 기능 영향이 없어 마지막에 몰아서 해도 된다. 쓰기는 0단계에서 이미 닫혔다.

  7. 6user_profiles 는 마지막에 단독으로

    참조가 가장 많고 컬럼별 민감도가 다르다. 공개 프로필(nickname, avatar_url)과 비공개(email, birth_date, last_ip, 잔액)를 나눠야 하므로 정책만으로 부족하고 컬럼 권한이나 뷰 분리가 함께 필요하다.

06검증 방법

단계마다 롤별로 실제 쿼리를 돌려 확인한다. 권한 구조만 보면 함정 ①·③ 을 놓친다.

-- 진행률
select
  count(*) filter (where not relrowsecurity) as rls_off,
  count(*) filter (where not relrowsecurity
    and has_table_privilege('anon', oid, 'SELECT')) as anon_readable,
  count(*) filter (where not relrowsecurity
    and has_table_privilege('anon', oid, 'DELETE')) as anon_deletable
from pg_class
where relnamespace = 'public'::regnamespace and relkind = 'r';
-- 2026-08-19 조사 시점: 105 / 90 / 32
-- 2026-08-21 0단계 적용 후: 105 / 90 / 0   <- 지금 여기
-- 목표:                    0 / 0 / 0

-- 정책 없이 RLS 만 켜진 테이블 (의도한 것인지 확인)
select c.relname
from pg_class c
where c.relnamespace = 'public'::regnamespace and c.relkind = 'r'
  and c.relrowsecurity
  and not exists (select 1 from pg_policies p
                  where p.schemaname = 'public' and p.tablename = c.relname);

-- 실제 가시성 확인 (구조 검사로는 안 잡히는 것)
set role authenticated;
select count(*) from <table>;   -- 타인 행이 보이면 정책이 안 먹은 것
reset role;
롤백

alter table ... disable row level security 로 즉시 되돌아간다. 정책은 남겨둬도 무해하다. 단계별로 나눈 이유가 이것 — 문제가 나면 그 단계만 끄면 된다.

07남은 결정

  • user_profiles 공개 범위. 다른 사용자의 nickname·avatar_url 을 어디까지 보여줄지는 제품 결정이다. 커뮤니티·투표 화면이 타인 프로필을 표시하므로 전면 차단은 불가능하다.
  • 뷰 security_invoker 전환 범위. 켜면 뷰를 읽던 어드민 화면이 정책 영향을 받는다. 어드민을 service_role 경유로 바꿀지, 정책에 관리자 분기를 넣을지 먼저 정해야 한다.
  • anon 쓰기 32개 회수 시점. 종결 — 0단계로 2026-08-21 적용 완료. 01 참조.
  • 0단계 기록의 PR. 프로덕션에는 적용됐는데 picnic-supabase main 에는 없다. 브랜치 charlie0421/rls-prep 에 1~6단계 초안이 함께 얹혀 있어, 0단계만 떼서 먼저 올릴지 통째로 올릴지 정해야 한다.
착수 전 한 가지

0단계가 끝나 공개 앱 키로 데이터를 지울 수 있는 상태는 해소됐다. 이 과제가 몇 주 걸려도 그 위험은 다시 열리지 않는다.
