판정과 우선순위

  1. 구매 정산을 먼저 확인한다. 표본의 소유자 불일치(422), 정산 실패(503), 서버 오류(500)는 최종 지급 여부 확인이 필요하다. 실제 과금 손실이나 이중 지급은 확인되지 않았다. 확인 없이 스토어 거래를 소비하거나 재지급하면 안 된다.
  2. Firebase resume 경로와 unmounted ref는 현재 main에도 남아 있다. 푸시 서비스는 Firebase 준비 전 singleton을 읽을 수 있다. 두 화면 경로는 await 뒤 유효하지 않은 widget ref를 다시 사용한다. 재현 테스트와 별도 수정이 필요하다.
  3. 기존 수정의 배포 여부와 실제 해결 여부를 분리한다. PR #294/#295 구매 수정, #296 마감 처리, #278 영상 처리는 130504에 없지만, 이번 정확한 표본에 대한 직접 해결은 확인하지 못했다. PR #303은 최신 태그 130605에도 없다.
  4. 앱 멈춤·네이티브 크래시를 단순 노이즈로 삭제하지 않는다. WebKit·광고·GPU·시스템 경로의 증거는 있으나 모든 원인이 특정되지는 않았다. 심볼화·스레드 덤프·기기 재현이 필요하다.

수정·배포·검증 순서

  1. 구매: 표본 거래의 소유권·기존 지급·워커 최종 상태를 승인된 최소 조회로 확인한다. 상태가 확인되기 전에는 consume/finish·재지급·영구 스윕 제거를 하지 않는다. #294의 거래 보존·완료 대기 제한과 #295의 지급 확인 응답 처리는 별도로 회귀 검증해 배포 후보에 포함한다.
  2. Dart 수정: Firebase 준비 전 resume, refresh 중 화면 이탈, 저장 실패, 픽커 중복 입력을 재현한다. 동시 실행·초기화 실패·로그아웃·앱 재시작도 검증한다. 단순 오류 숨기기보다 복구 경로를 보장한다.
  3. 130504 OTA 후보: 해당 릴리스의 호환 가능한 소스·Flutter/Shorebird 조합에서 Dart 변경만 분리한다. main의 Firebase 네이티브 SDK 변경을 130504 OTA에 섞지 않는다. iOS·Android별 패치와 멱등성 검증 후 대상·버전·플랫폼을 제시해 별도 배포 승인을 받는다.
  4. 새 바이너리: PR #303과 검증된 네이티브/플러그인 변경을 포함한 main으로 새 build number를 결정한다. 기존 130605 번호나 태그를 재사용·이동하지 않는다. 스토어 업로드·승인·공개와 Shorebird release 생성은 각각 확인한다.
  5. 효과 측정: release와 shorebird.patch_number로 나누고 세션/사용자 노출량을 함께 본다. 패치 적용 세션에서 재현 오류가 사라졌는지 확인한다. 48시간 무발생만으로 해결을 확정하지 않는다. 일부 ANR 샘플링 때문에 전체 발생량을 단순 배수로 환산하지 않는다.

  • 공개 Android 트랙·TestFlight·Codemagic 빌드 상태, 임의 태그 없는 빌드 내용.
  • Firebase 초기화 전/후의 정확한 복귀 순서. 표본에 초기화 breadcrumb이 없지만 초기화 미실행을 증명하지 않는다.
