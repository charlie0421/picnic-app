3. 발견 사항 (블로커 0건)

LOWF1 — "keepAlive 가 디코드 완료를 증명한다"는 주석이 실제 동작과 다르다

위치: picnic_lib/lib/presentation/widgets/vote/voting/voting_dialog_widgets.dart:98-101

실패 조건 / 재현: 상세 항목이 live 이지만 keepAlive 캐시에서는 축출된 상태 (keepAlive=false, live=true, pending=false)에서 팝업을 연다. 재현: 상세 Image 를 마운트해 디코드시킨 뒤 imageCache.clear()(_liveImages 는 남음)하고, 그 Image 를 마운트한 채 팝업을 띄운다. 실행 결과:

P1 after clear: keepAlive=false live=true pending=false
P1 preview adopted = true (w=78) detailRequests=1 popupRequests=1

원인: ImageCache.putIfAbsent 의 _liveImages 분기가 _touch() 로 해당 completer 를 _cache 에 다시 넣은 뒤 반환한다. 코드가 statusForKey 를 읽는 시점은 그 이후이므로 keepAlive 는 이미 true 다. 즉 게이트가 검사하는 상태는 "조회 전 상태"가 아니라 "조회가 만들어 낸 상태"다.

영향: 동작 자체는 요구사항에 부합한다(디코드 완료된 이미지이며 추가 요청 0건). 다만 (a) 주석이 보장하지 않는 불변식을 주장하고, (b) "원자적 캐시 전용 조회"가 부수효과가 없지 않다 — MRU 재배치와 재삽입을 하며 _checkCacheSize 를 태워 다른 이미지를 축출시킬 수 있다.

최소 수정: putIfAbsent 호출 전에 cache.statusForKey(key) 를 읽어 판정하거나(엄격), 주석을 "pending 이 아닌 live 항목도 채택하며 이때 keepAlive 캐시로 의도적으로 승격된다"로 정정한다(현행 동작 유지). 후자를 권장한다.

5. 한계

  • 지시에 따라 작성자 분석 문서와 Astra 리포트를 읽지 않았다. 따라서 그쪽 주장과의 교차 검증은 하지 않았다.
  • 디바이스/시뮬레이터를 구동하지 않았다. 증거의 iOS 관측치(Gyuvin 114ms/263ms, Taemin 111..2007ms/3006ms)는 여기서 검증하지 않았으며, 제출된 대로 관측치이지 HTTP 벤치마크가 아니다 — 요청 단위 로그 없이는 "상세 캐시가 warm 이라 프리뷰가 떴다"와 "CDN 이 빨랐다"를 구분할 수 없다. 대신 위젯 테스트의 실제 RenderImage 픽셀 단언으로 메커니즘을 확인했다.
  • iOS 전용 isIPad MediaQuery 의존(F4)은 호스트 테스트에서 UniversalPlatform.isIOS == false 라 직접 재현할 수 없어, Directionality 로 didChangeDependencies 를 유발해 대체 검증하고 나머지는 Flutter SDK 소스로 추론했다.
  • 델타의 6개 파일과 그 직접 의존성만 읽었다. 함께 배포될 나머지 미커밋 변경(수정 20개 파일, 신규 7개 파일)은 이번 리뷰 대상이 아니다.
  • 프로덕션 해시 4fc11b3b… 동일성은 재도출하지 않았다.
