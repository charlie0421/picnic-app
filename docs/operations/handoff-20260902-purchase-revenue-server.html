GA4 purchase 매출 서버 사이드 — 핸드오프

2026-09-02 · picnic-supabase #109 프로덕션 배포 및 후속 회귀 수정 · 선행 문서 docs/operations/handoff-20260821-ga4-taxonomy.html

2026-09-02 정정 — GA4 확인 결과, 서버 사이드 매출 계약은 프로덕션에서 한 번도 동작한 적이 없다.
플래그·capability 게이트·#117 모두 앱에 관측 불가한 no-op 이었다. 원인은 워커의 타입 게이트가 영원히 false 인 것(§0). 수정은 picnic-supabase #118(1줄 + 핸들러 테스트), 미배포. 아래 §2 결함 B 와 §3 은 정정 전 서술이며, 실측 근거가 스냅샷이었음을 §0 에 적었다.
한 줄 요약(정정 전) — #109(GA4 매출 계약 서버 사이드)가 프로덕션에 전부 적용됐고 플래그도 켜졌다. 적용 과정에서 결함 2건을 잡아 각각 PR #116·#117 로 고쳤다. 남은 것은 GA4 에서 Android 매출 복귀를 눈으로 확인하는 것 하나뿐이다.

0. 정정 — GA4 실측과 진짜 원인 (2026-09-02)

GA4 가 보여준 것

GA4 ✅ 실제 매출 (purchase 전용) 을 날짜+시간(속성 시간대 GMT+9) × 앱 버전 × 통화로 쪼개 DB 의 Google 정산과 1:1 대조했다. 플래그 ON(9/1 07:55Z = 16:55 KST) 이후 #117 배포(9/2 02:41Z = 11:41 KST) 전까지 Google "통화만" 정산 16건 전부 GA4 에 카탈로그 금액이 찍혀 있다. 9/1 하루 Android value 가 비어 있어야 한다는 §3 의 예측은 틀렸다 — 결함 B 는 GA4 에서 발생한 적이 없다.

진짜 원인 — 워커의 타입 게이트가 영원히 false

// wallet-operation-worker/index.ts (배포본 v28 번들에도 그대로)
const shaped = actualType === "MOBILE_PURCHASE" || actualType === "WEB_PURCHASE"
  ? await withPurchaseAnalytics(client, inboxId, processed)
  : processed;

-- get_wallet_operation_event_type (20260721104000, 프로덕션 pg_get_functiondef 동일)
select case when operation_type in('MOBILE_PURCHASE','WEB_PURCHASE') then 'PURCHASE' ...

RPC 가 두 타입을 'PURCHASE' 하나로 접어서 돌려주므로 게이트가 절대 맞지 않는다. 플래그 ON 이후 정산 63건(Apple 38 · Google 25)을 프로덕션에서 조회하니 전부 actual_type='PURCHASE'. 즉 withPurchaseAnalytics 는 프로덕션에서 한 번도 호출되지 않았고, 응답은 항상 7키였다.

  • §2 결함 B 의 "Google 17건 중 16건 통화만" 은 스냅샷 컬럼(analytics_currency)을 센 것이지 응답을 본 게 아니다. §3 의 경고("스냅샷으로 판정하지 말 것")를 §2 가 스스로 어겼다.
  • #117 자체는 옳다(잠재 결함을 막았고, 게이트를 고쳐 켜도 Google 이 안전한 이유다). 실측 서술만 틀렸다.
  • Apple JWS 금액도 스냅샷에만 있고 앱에는 간 적이 없다. iOS 매출도 내내 카탈로그 값이다.
  • 단위 테스트 187개가 못 잡은 이유: 게이트는 handler 안에 있고, 테스트는 withPurchaseAnalytics 를 직접 불렀다.

수정 — picnic-supabase #118 (미배포)

게이트를 actualType === "PURCHASE" 로(1줄). 가짜 PostgREST 가 프로덕션처럼 "PURCHASE" 를 답하게 하고 실제 handler 를 통과시키는 테스트를 추가했다(RED 확인 후 GREEN, 188 passed).

플래그가 여는 것

영수증 검증 응답에 currency·value 두 키를 실을지만 정한다. 그게 전부다.

  • 판정 지점은 wallet-operation-worker 의 withPurchaseAnalytics 한 곳이고, 모든 실패 경로가 원본 결과를 그대로 돌려준다(플래그 조회 실패·RPC 오류·통화 형식 불일치·예외).
  • 스냅샷 기록은 플래그와 무관하다. p_analytics_* 는 항상 기록된다.
  • 구버전 앱은 플래그가 아니라 capability 게이트가 막는다 — parser_capabilities: ['purchase_revenue_v1'] 미선언 요청에는 shapeForCapabilities 가 두 키를 키 자체로 삭제한다(null 이 아니라 부재).

되돌리기는 SQL 한 줄이고 재배포가 필요 없다.

update public.wallet_runtime_flags
   set value_json = 'false'::jsonb, version = version + 1
 where flag_key = 'wallet.purchase_revenue_fields_enabled';

2. 잡은 결함 2건

결함 A — 마이그레이션이 프로덕션에 적용 불가 (PR #116, 머지)

alter ... owner to wallet_command_owner 는 새 소유자가 그 스키마에 CREATE 를 가져야 통과한다. 두 마이그레이션은 public 에만 CREATE 를 빌렸는데, 프로덕션은 wallet_private 에도 직접 쓰기 잠금을 걸어 소유자 자신에게서 CREATE 를 회수해 둔 상태였다.

스테이징 통과 ≠ 프로덕션 통과. wallet_command_owner 의 wallet_private CREATE 는 스테이징 true / 프로덕션 false 다. 그래서 이 계열 결함은 스테이징에서 성공하고 프로덕션에서만 실패한다. 실제로 스테이징 리허설은 두 파일을 오류 없이 통과시켰고, 같은 파일이 프로덕션에서 첫 소유권 이전에 죽었다.

How to apply: wallet_private 에 객체를 만드는 마이그레이션은 반드시 grant create on schema wallet_private to <owner> … revoke 쌍을 넣는다 (20260721104000 의 wallet_state_owner 선례와 동일). 그리고 프로덕션에서 begin; …; rollback; 으로 먼저 시연한다.

결함 B — 플래그를 켠 것이 Android 매출을 0 으로 만들었다 (PR #117, 머지·배포) — 정정: 실제로는 발생하지 않았다(§0)

아래 "프로덕션 실측" 표는 스냅샷 컬럼을 센 것이다. 응답에는 통화가 실린 적이 없어(§0) 앱은 카탈로그 짝을 계속 썼다. #117 의 코드 변경은 그대로 유효하다.

앱의 우선순위 규칙(analytics_outbox.dart enqueueOrMergePurchase):

currency = server ?? catalog ?? observed;
value    = server != null ? serverValue : (catalog != null ? catalogValue : null);

서버가 통화를 주는 순간 금액도 서버 것만 쓴다. Google 은 provider 응답에 가격 필드가 없어 serverValue 가 항상 null 이므로, 통화만 보내면 앱이 이미 들고 있던 카탈로그 금액까지 버린다.

프로덕션 실측 (플래그 ON 이후):

공급자정산통화+금액통화만없음
APPLE262600
GOOGLE170161

앱을 탓할 수 없다. 응답이 출처를 알려주지 않아서 APPLE_JWS(서버가 실제로 아는 값)와 GOOGLE_CLIENT_STOREFRONT(앱이 방금 보낸 값의 메아리)를 구분할 방법이 없다.

수정: shapeForCapabilities 가 금액 없으면 통화도 뺀다(7키로 복귀). Google 응답에는 두 키가 모두 없어지고 앱은 카탈로그 짝을 쓴다 — 플래그를 켜기 전과 같은 동작이다. 그 둘은 같은 ProductDetails 한 번 읽기에서 나오므로 어긋날 수 없다. Apple 은 JWS 에서 둘 다 나오므로 영향이 없다. 기존 B-3 규칙("통화만 있는 것은 정상")을 대체한다.

3. 남은 작업 — 딱 하나 (정정: §0 참조)

GA4 확인 완료(2026-09-02) — Android 매출은 끊긴 적이 없다. 이유는 §0. 아래 예측표는 기록으로 남긴다. 실제 남은 작업: #118 머지·배포 결정, 배포 후 iOS 매출 변화 관찰.
(정정 전) GA4 에서 Android purchase 매출 복귀 확인 (2026-09-03 예정)
서버 쪽 검증은 끝났다(배포본 코드 확인 · 단위 테스트 187 passed · 정산 회귀 0). 그러나 응답은 앱으로 가고 앱이 GA4 로 보내므로, 끝단은 서버 DB 로 확인할 수 없다.

확인 방법 — GA4 → 탐색 → ✅ 실제 매출 (purchase 전용) 리포트에서 날짜×플랫폼으로 본다.

4. 다음 사람이 반드시 알아야 할 것

배포 대상은 verify_receipt 가 아니라 verify-receipt-v2

앱 상수가 receiptVerificationFunction = 'verify-receipt-v2' 이고, verify_receipt 슬롯(v186, 2025-12-30)은 구버전 앱 전용 레거시 v162 로 동결돼 있다. 레포의 verify_receipt/index.ts 는 wallet.v1 구현이라 그 슬롯에 배포하면 동결이 풀린다. verify-receipt-v2 가 그 파일을 import 해서 번들한다. 그 슬롯은 건드리지 말 것.

함수 배포 전에는 딸려 갈 변경을 반드시 확인한다

git log <현재_배포본_sha>..origin/main -- supabase/functions

이번에 실제로 걸렸다. main 에 #115 가 들어와 있었는데, 그 _shared/wallet/purchase-provider-verifiers.ts 변경(Google pending 을 retryable 로 전환)의 짝인 마이그레이션 ..._google_pending_purchase_retry_policy.sql(518줄)이 프로덕션에 미적용이었다. 재시도 정책 없이 검증기만 나가면 안 되므로, 2d14e79(당시 프로덕션 배포본) + #117 만으로 번들해 배포했다. 배포본을 다시 읽어 구버전 GOOGLE_NOT_PURCHASED 가 남아 있는 것으로 미혼입을 확인했다.

#115 롤아웃은 별도 워크트리 hotfix/google-pending-purchase-rollout 가 소유한다.

프로덕션 쓰기 경로

  • supabase db query --file <path> --linked 를 쓴다. SQL 을 손으로 옮겨 적지 않아도 되고 (통화 코드 157개에서 오타가 난다) 파일 전체가 한 트랜잭션이라 실패 시 전부 롤백된다.
  • db query 에는 --project-ref 플래그가 없다. --linked 만 있다. (이걸 몰라 감시 스크립트가 조용히 빈 값을 0 으로 읽고 "정산 없음"을 오보한 적이 있다. 스크립트에서 stderr 를 버리지 말 것.)
  • MCP execute_sql 과 CLI db query 둘 다 current_user=postgres 다. 권한 차이가 있다고 오해하지 말 것.
  • supabase db push 는 못 쓴다. 스테이징은 로컬에 없는 버전이 있어 거부되고, 프로덕션은 버전을 재번호해 적용한다(레포 20260824031038 → 프로덕션 20260824042222).
  • wallet-production-rollout.yml 도 경로가 아니다 — 매니페스트가 status: blocked 다.

Android 매출은 iOS 와 상한이 다르다

통화 출처구버전 앱
iOS서버가 Apple JWS 를 직접 읽음 (APPLE_JWS) ✅ 스냅샷엔 남는다(응답만 capability 게이트)
Android앱의 client_observed_currency 뿐 ❌ 영구 결측

Google Play 검증 응답에는 가격·통화 필드가 없다(구 purchases.products.get, 신 productsv2 양쪽 다). Billing 8.x 로 올려도 서버는 통화를 모른다. 출처 A(regionCode → 카탈로그)는 2026-08-25 에 불필요로 종결했다 — 다시 꺼내지 말 것.

client_observed_currency 는 130104 부터 나간다. 2026-09-01 실측 보급률 (public.devices, 최근 2일 활성): android 828/1188 = 69.7%, ios 566/812 = 69.7%. 실제 Google 통화 확보율은 88.9% 로 보급률보다 높았다(구매자가 최신 버전에 쏠린 것으로 보인다).

analytics_* 컬럼은 불변 트리거로 잠겨 있어 소급 backfill 이 불가능하다. 구버전 앱에서 들어온 Android 구매는 영구히 매출 없는 건이다. 확실한 레버는 강제 업데이트뿐이다.

스냅샷의 app_build=0 은 정상

앱이 요청 본문에 app_build·app_version 을 아예 넣지 않는다 (receipt_format_helper.dart). 서버가 0/"0.0.0" 으로 기본값을 채운다. 구버전 신호로 오독하지 말 것 — 스냅샷만으로는 앱 버전을 알 수 없다.
