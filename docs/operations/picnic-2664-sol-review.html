대상: fix/wallet-summary-owner-guard, HEAD 0a8f2b712, base origin/main cf111821a · 검토일: 2026-09-11

판정: 변경 요청 — blocker 1건, minor 1건.
직접 A→B 또는 로그아웃 상태에서 도착하는 이전 계정 정산은 차단하지만, 실제 gotrue의 비동기 인증 이벤트 전달 전에 A→B→A가 완료되는 창에서는 가드가 우회된다. 또한 새 로그가 사용자 식별자를 평문으로 기록한다.

지적 사항

1. [blocker] 비동기 auth 이벤트가 전달되기 전 A→B→A 왕복 정산이 통과한다

근거: picnic_lib/lib/presentation/providers/wallet_provider.dart:234-238에서 _authEpoch는 auth stream listener가 이벤트를 받은 뒤에만 증가한다. 반면 captureOwner()는 ownerId와 현재의 _authEpoch만 저장하고(라인 433-436), _ownsWrite()도 그 둘만 비교한다(라인 448-450). 세션 인스턴스 또는 아직 전달되지 않은 전환을 판별하는 정보는 토큰에 없다.

재현/실패 조건: owner A에서 정산 작업을 시작해 토큰 (A, epoch 0)을 잡는다. 같은 Dart turn에서 gotrue가 currentSession을 B로 바꾸고 B 이벤트를 비동기 큐에 넣은 다음, 다시 새 A 세션으로 바꾸고 A 이벤트도 큐에 넣는다. 이벤트 listener가 실행되기 전에 A의 이전 정산 continuation이 setSummary를 호출하면 현재 owner는 A이고 epoch는 여전히 0이므로 가드가 통과한다. 요구사항이 특별히 지적한 BehaviorSubject의 sync: false 창이며, A→B→A 또는 로그아웃→동일 A 재로그인에서 발생한다.

테스트가 놓치는 이유: 정산 왕복 테스트는 picnic_lib/test/presentation/providers/wallet_provider_test.dart:2292-2319에서 _MutableAuthGateway를 사용하고, 이 가짜는 라인 237-240에서 StreamController.broadcast(sync: true)다. 또한 각 전환 뒤 provider future를 기다려 epoch 반영을 강제한다. 투표/숏폼 테스트의 게이트웨이도 각각 voting_dialog_account_switch_test.dart:47-65, ad_shortform_fullscreen_page_test.dart:333-351에서 sync: true이고 A→B만 검증한다. 따라서 “요구사항을 위반하면서도 추가 테스트 전체를 통과하는 구현”이 현재 구현 그대로 존재한다.

최소 수정 방향: 쓰기 토큰에 캡처 당시 Session 인스턴스도 포함하고, 적용 시 같은 owner지만 세션이 달라졌다면 즉시 허용하지 말고 auth 이벤트 큐가 한 턴 처리된 뒤 epoch를 재검증하도록 쓰기 적용을 직렬화/비동기화한다. 그 결과 epoch가 바뀐 로그아웃·왕복은 폐기하고, 동일-owner 토큰 갱신 이벤트는 epoch가 유지되므로 허용해야 한다. 실제 BehaviorSubject(sync: false) 기반 테스트에서 이벤트를 drain하기 전에 정산 continuation을 먼저 실행하는 A→B→A 및 logout→A 시나리오를 추가해야 한다.

2. [minor] 폐기 로그가 사용자 식별자를 새로 노출한다

근거: picnic_lib/lib/presentation/providers/wallet_provider.dart:478-480의 logger.i('🚫 이전 계정의 정산 무시: ${owner.ownerId}')가 Supabase user ID를 평문 로그에 포함한다. 실제 테스트 출력에서도 owner-a가 그대로 나타났다.

재현/실패 조건: A에서 시작한 구매·투표·광고 정산이 B 로그인 또는 로그아웃 뒤 도착하면 정보 로그에 A의 ID가 남는다. 운영 로그 수집이 활성화된 모든 빌드에서 사용자 식별자가 노출될 수 있다.

최소 수정 방향: owner ID interpolation을 제거하고 “이전 계정 정산 무시” 같은 비식별 메시지만 남긴다. 필요 시 카운터/고정 reason code만 기록한다.

동시성·회귀 검토

  • snapshotAt: 라인 483-488의 기존 isBefore 규칙은 소유권 검사 뒤 그대로 유지되어 오래된 snapshot은 무시되고 동일 시각은 나중 쓰기가 채택된다.
  • 토큰 갱신: owner/epoch 비교만 하므로 listener가 동일 owner 이벤트를 무시하는 정상 토큰 갱신은 허용된다. 다만 이 선택 때문에 blocker의 “이벤트 전 왕복” 구분이 사라진다.
  • route unmount: app-level ProviderContainer와 applier를 미리 캡처하므로 기존 route 이탈 후 반영 성질은 유지된다.
  • gateway.isEnabled false: owner는 일관되게 null로 캡처/비교되어 테스트 환경 쓰기는 허용된다.
  • provider override: overrideWithBuild 또는 build를 재정의한 notifier는 production build의 auth listener를 설치하지 않으므로 epoch 기반 A→B→A 검증이 동작하지 않는다. 현재 사용처는 테스트로 검색되었으며 production 결함으로 별도 승격하지 않았지만, 테스트가 실제 가드를 과대평가하는 원인이다.
  • 서버/ACK: diff는 repository 지급 RPC, 구매 완료 판정, ACK 호출을 변경하지 않는다. 광고 복구는 wallet write 뒤 기존 dialog/ACK 흐름을 유지한다.
  • setSummary/refresh/build 경합: snapshot 쓰기 중 refresh가 완료되면 refresh 결과가 명시적으로 최신으로 간주되어 덮어쓰는 기존 설계가 유지된다. refresh 실패는 현재 state를 다시 읽어 정산 snapshot을 보존한다.

테스트 커버리지 평가

직접 A→B, sign-out, 토큰 갱신, 이벤트가 완전히 전달된 뒤의 A→B→A, snapshot 순서, route unmount는 검증된다. 그러나 가장 중요한 추가 공백은 blocker에 설명한 비동기 BehaviorSubject 이벤트 전달 전 A→B→A다. 또한 광고 복구 테스트는 adRewardOwnerReaderProvider의 문자열만 바꾸고 wallet auth gateway는 비활성 override 상태라 실제 wallet owner guard가 아니라 상단의 recovery owner early-return만으로도 통과할 수 있다. 즉 해당 테스트는 host의 early-return 회귀는 잡지만 새 WalletWriteToken 가드가 깨져도 통과 가능하다.
