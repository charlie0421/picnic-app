리워드 이미지 CDN 후속 과제 조사

2026-09-19 · 관련 PR #243 (리워드 팝업 원본 요청) · 측정은 전부 프로덕션 cdn.picnic.fan 와 s3://picnic-prod-cdn 읽기로 수행

결론. 리사이저가 느린 근본 원인은 리워드 원본이 사진인데 PNG 로 저장된 것이다. 리사이저는 원본 확장자 포맷으로 다시 인코딩하므로, 사진 PNG 는 변형 1개 생성에 8~12초가 걸리고 같은 크기의 JPEG 원본은 0.7초다. 리워드 PNG 는 알파 채널이 있지만 전부 불투명(255)이라 PNG 일 이유가 없다. 두 번째 원인은 홈 리워드 그리드가 기기 레이아웃 크기로 요청해서 캐시 키가 기기마다 갈리는 것이다(썸네일 1장에 변형 375개).

3. 대안 (효과 큰 순)

A. 어드민 업로드 시 불투명 이미지를 JPEG 로 변환 — 권장

  • upload/direct 라우트(nodejs 런타임)에서 sharp 로 알파가 전부 불투명이면 JPEG q85 로 변환, 긴 변 상한(예: 1500px)도 함께 적용. 확장자를 .jpg 로 저장해야 리사이저가 JPEG 로 출력한다.
  • 효과: 원본 1.7MB → ~0.2MB, 콜드 변형 8~12초 → ~0.7초. PR #243 의 원본 요청도 전송량 문제가 사라진다.
  • 투명 PNG(로고 등)는 그대로 둔다. 리워드 외 폴더(artist 등)에도 같은 이득이 있으나 범위는 폴더별로 결정.
  • 기존 리워드 PNG 111개는 새 키로 재업로드 + reward 행(12개) 경로 갱신이 필요 — 프로덕션 쓰기라 별도 승인·백업 필요.

B. 홈 리워드 그리드를 고정 변형으로 요청 — 앱, OTA 가능

  • _rewardCard 가 기기와 무관한 폭 하나(예: w=600, 높이 미지정, maxResolutionMultiplierCap 으로 DPR 고정)만 요청. 홈은 조회가 많아 전역 첫 사용자 1명만 콜드를 맞고 이후 전원 캐시 적중.
  • 팝업과 달리 원본 요청은 부적합(카드 4장 이상 × 1.7MB). A 적용 후라면 원본 요청도 선택지.

C. 업로드 직후 고정 변형 사전 워밍 — 어드민

  • B 처럼 키가 고정된 경우에만 의미가 있다. 저장 성공 후 해당 변형 URL 을 GET 1회. A 를 하면 콜드가 0.7초라 우선순위 낮음.

D. 리사이저 자체 개선 — 인프라 담당 필요

  • PNG 출력 압축 레벨/팔레트 설정 완화, fm 존중(webp 출력). 소스·권한이 없어 이번에 확인 불가.

E. 앱 전역 요청 크기 버킷팅 — 별도 과제

  • PicnicImageRequest 가 요청 폭을 고정 단계(예: 128/256/512/768/1024)로 올림하면 artist 22만 개 수준의 파편화를 줄일 수 있다. 영향 범위가 앱 전체라 설계 검토가 먼저다.

4. 참고: 기타

  • 투표 상세의 28px 리워드 칩(vote_detail_page.dart)과 달성 사다리 50px 썸네일은 출력이 작아 콜드도 짧다(w=512 급도 0.5초). 우선순위 낮음.
  • 조사 중 생성된 CDN 변형(측정용 GET) 약 20개가 캐시에 남았다. 무해하다.
