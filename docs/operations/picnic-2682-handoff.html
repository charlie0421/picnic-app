작성 2026-09-17 · 대상 user_profiles.id 조회 22P02 (Tapjoy 콜백 snuid)
앱 수정 머지 완료 · 서버 수정 미착수 · 배포 모니터링 진행 중

1. 한 줄 요약

Tapjoy 가 user ID 가 설정되기 전에 생성된 오퍼의 콜백에 기기 ID 를 snuid 로 실어 보냈고, 서버가 그 값을 검증 없이 uuid 컬럼 조회에 넣어 22P02 로 터졌다. 앱 측 원인은 고쳐 배포했고, 서버 측 방어와 재시도 증폭 문제는 그대로 남아 있다.

2. 확정된 원인

2-1. 공식 문서에 적힌 동작이다

Tapjoy 자체관리 가상화폐(Self-Managed Currency) 문서:

"If there's not a user ID associated with the device, Tapjoy will send a device ID as snuid in the callback URL... Usually, this will be the Advertising ID for the device. However, depending on the SDK version, device model/version, device operating system (OS) version, and Google Play Services, the exact ID might vary. Other possible values include the Android ID, udid, and mac_address."

권고 사항도 명시돼 있다. "Set the user_id with connect flags during the initial connection, before any content requests."

대체값이 보통 광고 ID(UUID 형태라 우리 검증을 통과한다)여서 평소에는 드러나지 않는다. 광고 ID 를 못 쓰는 기기에서만 Android ID 계열로 떨어져 64자리 hex 가 된다.

2-2. 메커니즘 — setUserID 는 기다리지 않는다

Tapjoy.setUserID 는 리스너만 등록하고 즉시 반환한다. 플러그인 tapjoy_offerwall 14.6.0 의 Android 구현이 result.success(null) 을 리스너 바깥에서 호출한다 (TapjoyOfferwallPlugin.kt:157-171). iOS 도 setUserIDWithCompletion 의 완료 핸들러 바깥에서 result(nil) 을 호출해 동일하다. 

// 플러그인 Android
Tapjoy.setUserID(userId, object: TJSetUserIDListener{ ... })
return result.success(null)   // 리스너를 기다리지 않는다

수정 전 프로덕션 코드는 그 반환 직후 곧바로 오퍼를 요청했다.

await _setupTapjoyUser();        // 즉시 반환 — 등록 완료가 아니다
await _requestTapjoyPlacement(); // 등록을 기다리지 않고 오퍼 요청

등록이 늦거나 실패하면 Tapjoy 서버는 "user ID 없는 기기" 로 보고, 그때 만들어진 오퍼의 snuid 가 기기 ID 가 된다.

Tapjoy 는 200 과 403 만 종료 상태로 보고 그 외(400 포함)는 5분마다 최대 4일 재시도한다. 응답이 5초를 넘어도 실패로 보고 재시도한다. 우리가 중복 트랜잭션에 400 을 돌려주는 탓에 정상 사용자의 정상 트랜잭션이 건당 약 90회씩 재전송되고 있다.

4. 기각된 가설

가설기각 근거
앱이 Tapjoy user ID 로 기기 ID 를 넣었다 git 전 이력에서 항상 supabase.auth.currentUser.id 였다. 기기 지문을 넣은 버전은 없다.
앱 기기 지문이 샜다 문제의 snuid 가 devices 테이블에 없다. 우리 해시는 picnic.android_id: 네임스페이스를 붙여 SHA-256 하므로 Tapjoy 식별자와 원리상 일치할 수 없다.
SDK 를 올리면 해결된다 14.6.0 이 pub.dev 최신이고 이미 사용 중이다. 런타임 실측으로도 14.6.0 확인.
getUserID() 로 snuid 를 예측할 수 있다 에뮬레이터 실측 결과 connect 전후 모두 null. 우리가 설정한 값만 되돌려주며, Tapjoy 가 콜백에 실을 값과 무관하다.
피해자 특정은 구조적으로 불가능하다. 위 두 번째 항목 때문이다. Tapjoy 만 광고 전 claim 을 남기지 않아(PICNIC-2698) 대조할 기록도 없다. AdMob 은 custom_data, Pangle 은 extra 에 우리 user_id 를 요청에 직접 싣는다.

5-2. 왜 static 가드인가

플러그인의 성공·실패 리스너는 Dart 쪽 static 단일 슬롯이고 (TapjoyMethodCallHandler:102-110) 콜백에 요청을 식별할 값이 없다. A 가 timeout 된 뒤 B 를 보내면 슬롯이 B 로 바뀌어 늦게 도착한 A 의 결과가 B 의 결과로 처리된다. 그 사이 계정이 바뀌었다면 SDK 는 A 를 들고 있는데 B 로 오퍼월을 열어 적립이 다른 계정에 귀속된다. 인스턴스 필드로는 화면 재생성을 못 막으므로 static 이어야 한다.

값(user id)을 기억하는 이유: 위험한 것은 늦은 이벤트 자체가 아니라 그 사이의 계정 변경이다. 같은 user id 재시도는 늦은 이벤트가 새 시도의 결과로 처리돼도 SDK 가 든 값과 우리가 믿는 값이 같다.

7. 모니터링

7-1. 지표 정의 — 주의할 함정

요청 대비 200 비율을 지표로 쓰지 마라. 같은 트랜잭션이 5~11회 재전송돼 분모가 부풀어 구조적으로 낮게 나온다. 초기에 15.4% 를 보고 "낮다" 고 오판할 뻔했다.
올바른 지표는 고유 트랜잭션 대비 200 건수이고 정상 범위는 85~94% 다.

7-2. 적립 0건 판정 기준

표본이 작으면 0건도 우연이다. 적립자 기준율 p 에서 n 명 전원 미적립 확률은 (1-p)^n 이다.

사용자 수전원 미적립 확률 (p=1.4%)
5049%
10024%
2105%

210명 미만에서 0건인 것은 경고 대상이 아니다.

7-3. 경고 조건

  • 새 64 hex snuid 발생, 또는 알려진 값 3a1db1ef… 의 재등장
  • user_profiles 22P02 재발 (2026-09-16 18시 구간을 끝으로 0)
  • 130404 코호트 사용자 210명 이상인데 적립 0건, 또는 적립자 비율이 나머지의 절반 이하
  • 트랜잭션당 200 비율 70% 미만

7-4. 발견한 측정 결함 — 채택률을 신뢰하지 마라

devices.app_build_number 는 로그인 시점에만 갱신된다. registerDevice 는 auth_service.dart:91 한 곳에서만 호출되고, 앱 실행 시 도는 updateLastSeen 은 last_seen 만 건드린다.

따라서 앱을 업데이트했지만 세션이 살아 있어 재로그인하지 않은 사용자는 옛 빌드 번호로 남는다. 실측에서 최근 6시간 활성 기기 중 130202 로 잡힌 140대의 106대가 등록 기록이 2일 이상 묵어 있었다.

측정된 채택률은 하한이며, "채택률 90%" 를 종료 기준으로 쓰면 영원히 도달하지 않을 수 있다. 시간 기반 기준(예: 강업 후 N일)으로 대체하거나 다른 버전 신호를 찾아야 한다.

8. 종료 기준

64 hex 는 전체 조사에서 기기 1대·snuid 1개만 관측됐다. 원래 드문 사건이라 부재만으로는 약한 증거다. 발생률을 모르니 필요한 관찰 기간도 계산할 수 없다.

단계기준성격
앱 수정 종료 충분한 채택 후 신규 64 hex 0건 · 22P02 0건 · 코호트 적립 정상이 7일 연속 "재발 미관측" — 불가능 증명 아님
진짜 종료 서버에 snuid 형태 가드 적용 (UUID 아니면 DB 조회에 넣지 않고 403) 앱이 어떻든 22P02 가 구조적으로 불가능해진다

따라서 티켓은 서버 가드까지 열어두는 것이 맞다.
