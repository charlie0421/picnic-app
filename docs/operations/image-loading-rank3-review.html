3. 적대적 검증 — 반증에 실패한 가설들

아래는 결함을 의심하고 파고들었으나 근거로 기각된 항목이다. 리뷰 깊이의 기록으로 남긴다.

(1) 지연 generator가 두 카드의 후보를 섞을 수 있는가 — 아니오

_adjacentImageRequests()는 sync*라 첫 moveNext()까지 본문이 실행되지 않고, 2·3번째 moveNext()는 await request.obtainKey(...) 이후에 일어난다. 그러나 nextIndex, vote, status, previewItems(...) 리스트가 모두 첫 moveNext() 시점의 지역 변수로 고정되므로, 중간에 _currentIndex가 바뀌어도 후보가 다른 카드와 섞이지 않는다.

(2) signature가 3번째 변경을 놓칠 수 있는가 — 아니오

_requestSignature = (url, requestW, requestH, decodeW, decodeH). 실제 캐시 키는 ResizeImage(CachedNetworkImageProvider(url, cacheKey: url), decodeW, decodeH, policy: fit, allowUpscaling: false)이고 policy·allowUpscaling은 상수이므로 url + decode 크기가 키를 완전히 결정한다. GIF 여부에 따른 quality(85/80) 차이도 resolver를 거쳐 url에 반영되므로 포착된다. 또한 세 분기가 각각 5-tuple / 7-tuple / 9-tuple이라 Dart record 규칙상 분기 간 충돌이 불가능하고, 순서가 뒤바뀐 경우(2·3위 교체)도 위치별 비교라 정상적으로 무효화된다.

(3) replace 도중 in-flight ranks 1·2가 유실되거나 중복 요청되는가 — 아니오

replace()는 await 이전에 동기적으로 generation 증가 → _desiredKeys = {} → removeScope(this)를 수행한다. 대기 중이던 3번째 job은 관심사가 비어 _queue에서 제거되고, in-flight 1·2는 취소 불가로 계속 달리되 뒤이은 addCandidates의 in-flight 분기(picnic_image_prefetch.dart:106-110)에서 새 generation의 관심사로 재부착된다. 즉 3번째만 바뀌면 1·2는 재요청 없이 재사용된다. 이미 완료된 키는 statusForKey(...).tracked 검사로 건너뛴다.

(4) _drain()이 unmounted context를 골라 job을 통째로 버릴 수 있는가 — 아니오

_drain()은 job.interests.removeWhere((_, i) => !i.isCurrent)(:148)로 먼저 걸러내고, isCurrent는 context.mounted를 포함한다. 따라서 values.first.context(:159)는 항상 mounted가 보장되며, 다중 scope가 한 job을 공유할 때 살아있는 scope의 관심사가 조용히 버려지는 경로는 없다.

(5) deactivated element에서 MediaQuery 조회가 일어날 수 있는가 — 아니오

rankImageRequest는 MediaQuery.devicePixelRatioOf(context)를 부르지만, 각 moveNext() 직전 같은 동기 턴에서 context.mounted를 검사한다(:37-39). 또 obtainKey가 SynchronousFuture를 돌려주므로 await는 microtask 규모이고 yield 사이에 프레임 경계(따라서 DPR 변화)가 끼어들 수 없다. 만일의 throw도 on Object { break; }로 봉쇄된다.

(6) 후보 3개가 디코드 상한·해제를 악화시키는가 — 아니오

rev 2에서 수치 서술을 정정했다. 관측값과 계산값을 분리한다.

판정의 근거(수치 무관). 세 랭크가 완전히 동일한 rankImageRequest(context, item)를 쓴다 — VoteCardColumnVertical(vote_info_card_vertical.dart:30)은 rank별로 막대 높이와 테두리 그라디언트만 다르고 이미지 요청은 분기하지 않는다. 따라서 rank 3 추가는 장당 디코드 상한을 전혀 바꾸지 않고, prefetch 총량만 2장 → 3장(1.5배)이 된다. 이 결론은 픽셀 수치에 의존하지 않는다.

관측된 geometry (root의 iOS 스냅샷)

  • 포트레이트가 배치된 논리 크기 69.95, DPR 3, 디코드된 비트맵 281×281.
  • 69.95는 레이아웃 결과다. VoteCardColumnVertical의 내부 컨테이너는 80×.9 = 72이고 Border.all(width: 1.w)가 양쪽을 파고들어 자식이 72보다 약간 작아진다. 반면 요청은 rankImageRequest에 하드코딩된 width: 72, height: 72로 만들어진다. 즉 요청은 배치 크기보다 ~3% 과잉 공급이며, 방향상 안전하다(부족하지 않다).

resolver 계산 상한 (picnic_image_request.dart)

요청 픽셀 = 72 × _resolutionMultiplier(context), 이후 .round(). 분기는 셋이다:

분기배율DPR 3일 때 72 논리의 요청·디코드 픽셀
Androidmin(dpr × 1.1, 2.5)2.5 → 180
iOS, isIPad(context) 참min(dpr × 1.3, 4.0)3.9 → 72×3.9 = 280.8 → 281
그 외(iOS 비-iPad, web 등)min(dpr × 1.2, 2.5)2.5 → 180

관측된 281은 두 번째 분기와 정확히 일치한다. 주의할 점은 isIPad(lib/core/utils/ui.dart:46-53)가 screenSize.width >= 768 || screenSize.height >= 768이라서, 포트레이트 iPhone(논리 높이 844·852·926 등)도 참이 된다는 것이다. 즉 실기기 iPhone은 "iPad 분기"의 3.9배를 타며, 그래서 180이 아니라 281이 나온다. (isIPad의 이 동작은 이번 delta 밖의 기존 사항이며, 여기서는 관측값을 설명하기 위해서만 인용한다. 별도 지적 아님.)

rev 1의 오류. rev 1은 Android 분기 계산값 180×180(≈127 KiB/장)을 플랫폼 구분 없이 제시했다. 보편적인 180px 디코드는 존재하지 않는다 — 값은 플랫폼과 DPR에 따라 달라지며, 위 표 기준 흔한 구성에서 180~281px 범위다. 참고로 픽셀당 4바이트 기준 장당 대략 180² ≈ 127 KiB, 281² ≈ 308 KiB이지만, 이는 계산된 상한이지 측정된 힙 사용량이 아니므로 단일 확정 수치로 인용하지 말 것.

해제·경합. 교체 시점에 취소 불가한 in-flight job 수는 전역 상한 2에 묶여 있으므로 2-candidate 기준선 대비 최악 경합이 악화되지 않는다 (3번째는 항상 대기열에만 있다가 removeScope로 즉시 취소된다).

원 문제. 3번째 열거 시 StateError를 던지는 generator로 상한을 증명하려 했으나, _resolveCandidates가 try { iterator.moveNext() } on Object { break; } (picnic_image_prefetch.dart:39-42)로 그 throw를 삼켜 단언이 실패할 수 없었다. 상한이 2→3으로 회귀해도 스위트가 green으로 남았다.

적용된 수정. throw generator를 명시적 카운터로 교체하고 for (final maximumCandidates in [2, 3])로 파라미터화했다. 후보 URL 4개(a·b·c·d)를 모두 유효·고유하게 주고 expect(enumerated, maximumCandidates)로 정확한 등가를 단언한다. bound 2는 기본 생성자(PicnicImagePrefetchScope())로, bound 3은 명시 인자로 만들어 기본값 경로 자체도 함께 검증한다(:181-183). 이어 최종본에서는 scope.dispose() → 4개 URL release() → 드레인을 단언보다 앞으로 옮겨(:198-211), 단언이 실패해도 held 응답 해제가 건너뛰이지 않게 했다.

검증 1 — 과다 열거를 실제로 잡는가

추론이 아니라 뮤테이션으로 확인했다. 실제 회귀(프로덕션이 _maximumCandidates를 무시하고 3으로 고정)가 테스트에 보이는 모습을 그대로 재현 — maximumCandidates: 3 scope에 bound-2 단언을 걸고 실행했다. 테스트는 실패했다:

MUTANT enumerated=3 (expected-by-real-test: 2)
Expected: <2>
  Actual: <3>
03:06 +0 -2: Some tests failed.

즉 단언에 실제 검출력이 있다. 등가 단언이라 과소 열거(2 미만)도 동일하게 실패한다. 프로덕션 무수정 상태에서 진짜 테스트는 enumerated == 2 / == 3으로 통과한다.

검증 2 — 타이밍·재정렬이 단언을 헐겁게 만들지 않는가

카운터 검사(:212) 전에 _pumpUntil(activeRequests == 2) + _pumpAsyncWork가 선행한다. activeRequests == 2는 addCandidates → _drain이 돌았다는 뜻이고 그건 _resolveCandidates 루프가 이미 끝난 뒤에만 가능하므로, 열거는 그 시점에 이미 확정된다. _pumpAsyncWork가 지연 열거 여지까지 흡수한다.

cleanup을 단언 앞으로 옮긴 것이 수치를 흐리지 않는다: iterator는 _resolveCandidates 종료와 함께 소비·폐기되므로 이후의 dispose()·release()·드레인이 enumerated를 더 늘릴 경로가 없다. requestsFor 카운터도 누적이며 감소하지 않으므로 드레인이 값을 되돌리지 않는다. 즉 재정렬 후에도 두 단언의 값은 정확히 동일하다. 조기·지연 판독으로 인한 위음성 없음.

검증 3 — 정리(cleanup)

5. QA 관찰에 대한 메모

초기 iOS/Android 실기기에서 반복적으로 "1·2위는 준비됨, 3위 지연"이 관찰된 것과 이번 변경은 정합적이다: 기존에는 3위가 후보에조차 들어가지 않았다. 이제는 후보에 들어가되 전역 상한 2 때문에 1·2위 중 하나가 끝나야 시작한다. 따라서 3위가 항상 미리 준비된다고 보장되지는 않으며, 느린 네트워크에서 1·2위가 끝나기 전에 스와이프하면 3위는 여전히 포그라운드에서 시작한다. 통제된 기준선 성능 측정이 없으므로 이 리뷰는 성능 개선 폭에 대해 어떤 주장도 하지 않는다. 기능적으로는 회귀 없이 3위가 준비 대상에 포함되며, 그 자체가 요구사항이다.
