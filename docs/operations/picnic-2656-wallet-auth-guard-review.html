PICNIC-2656 지갑 인증 가드 독립 리뷰

2026-09-10 · 읽기 전용 적대적 리뷰

판정: 차단 지적 3건(High)과 중간 지적 1건(Medium). 확인된 신규 회귀는 없지만, 네 건 모두 이번 인증 가드의 명시적 수용조건에 남아 있는 경계다.

기준: base 5aeeb706c0220a3b63eef35e44cb0f2fe9867454, 검토 diff SHA-256 65c5e20f3c5e454dfacb2cb63efbdf759b34228ff30929b9a216a5ea52d143f8.

범위: 변경된 지갑 repository/provider와 두 테스트 파일. setSummary 지적은 범위 안 메서드의 실제 도달 가능성을 확인하기 위해 기존 production purchase adapter를 읽고 그대로 호출했다.

차단 지적

High — 세션 resolve 직후 로그아웃하면 익명 지갑 RPC가 한 번 나간다

위치
picnic_lib/lib/presentation/providers/wallet_provider.dart:138, :159-173
원인
_resolveSession()이 반환한 과거 Session으로 builtForUserId를 정하고, await 이후 현재 세션을 다시 확인하지 않은 채 _read()를 호출한다. GoTrue 2.18의 비동기 BehaviorSubject replay가 로그아웃 이벤트를 listener에 전달하기 전에 RPC 호출이 동기적으로 시작될 수 있다.
재현
A 세션으로 provider를 mount하고 _resolveSession의 즉시 완료 Future가 이어지기 전에 signedOut으로 바꾼다. focused test에서 repository가 기록한 호출 owner는 기대값 []가 아니라 [null]이었다.
분류
기존에도 가능했으나, 이번 변경의 핵심 수용조건인 “signed-out build는 wallet RPC 0회”를 충족하지 못하는 잔여 경계다.
최소 수정 방향
await 뒤 실제 gateway.currentSession을 다시 스냅샷하고, resolve 결과와 현재 owner가 다르거나 현재 owner가 null이면 읽지 않는다. 이 검사와 아래 인증 epoch 검사를 같은 경계에 둔 회귀 테스트를 추가한다.

High — 초기 세션 대기 중 AuthException이 나면 이후 initialSession을 영구히 놓친다

위치
picnic_lib/lib/presentation/providers/wallet_provider.dart:180-193
원인
firstWhere()가 auth stream 오류로 실패하지만 _resolveSession()은 TimeoutException과 StateError만 처리한다. GoTrue의 BehaviorSubject는 마지막 오류를 새 구독자에게 replay하므로 Riverpod의 1회 재시도도 같은 AuthException으로 끝나며, build가 장기 auth listener를 설치하는 :160-164에 도달하지 못한다.
재현
세션 null 상태에서 build를 시작하고 auth stream에 AuthException을 보낸 뒤 재시도가 끝난 후 initialSession(A)를 보냈다. 기대한 A 소유 read 1회 대신 실제 read는 0회였고 provider는 자동 복구되지 않았다.
분류
기존 대기 로직의 결함이지만, 이번 요구의 stream error 및 지연된 initialSession 복구를 동시에 깨뜨리는 잔여 경계다.
최소 수정 방향
세션을 기다리는 동안 auth stream 오류는 자격정보 없이 기록하고 계속 기다리거나, 오류 뒤 signed-out 값으로 정착하더라도 장기 listener를 반드시 설치한다. wallet RPC의 PostgrestException 처리와 분리하여 42501 등 실제 읽기 오류는 그대로 노출한다.

High — 실제 purchase applier가 A의 늦은 정산 지갑을 B 화면에 쓸 수 있다

위치
picnic_lib/lib/presentation/providers/wallet_provider.dart:269-275; 실제 도달 경로 picnic_lib/lib/presentation/widgets/vote/store/purchase/wallet_summary_applier.dart:61-73 → purchase_settlement_step.dart:103-109
원인
setSummary()는 snapshot 시각만 비교하고 응답을 시작한 계정/세대를 받지 않는다. purchase adapter는 앱 수준 container를 미리 캡처하고 route가 사라진 뒤에도 결과를 적용하도록 설계되어 있어, 인증 전환이 이 호출을 차단하지 않는다.
재현
A에서 ContainerWalletSummaryApplier를 캡처하고, B로 전환하여 B 지갑 20이 정착한 뒤 A 요청의 더 늦은 snapshot 99를 production adapter로 적용했다. B의 20이 99로 바뀌었다.
분류
이번 diff가 새로 만든 회귀는 아니다. 다만 “logout/account switch에서 이전 owner의 late response를 절대 표시하지 않는다”는 수용조건을 실제 production caller가 위반하므로 차단 사항이며, 올바른 수정에는 caller 계약의 좁은 범위 확장이 필요하다.
최소 수정 방향
비동기 작업 시작 시 owner 또는 인증 epoch 토큰을 캡처해 WalletSummaryApplier/setSummary까지 전달하고, 현재 토큰과 다르면 drop한다. owner 정보가 없는 WalletSummaryModel만으로는 provider가 출처를 사후 추론할 수 없으므로 timestamp 비교만 강화해서는 해결되지 않는다.

중간 지적

Medium — A→B→A가 한 event-loop에 들어오면 첫 A refresh 응답이 새 epoch에 반영된다

위치
picnic_lib/lib/presentation/providers/wallet_provider.dart:160-163, :219-245
원인
_generation은 auth event를 관찰할 때가 아니라 예약된 다음 build()가 시작될 때만 증가한다. A→B→A 후 rebuild 전에는 generation이 같고 최종 user ID도 다시 A이므로 첫 A epoch의 응답이 두 검사를 모두 통과한다.
재현
A 값 10에서 refresh를 보류하고 B와 새 A를 연속 발행한 뒤 첫 A 응답 11을 완료했다. 기대한 기존 10 유지 대신 실제 상태가 11로 바뀌었다.
분류
새 회귀가 아니라 새 stale-response guard가 놓친, 요구사항에 명시된 rapid A→B→A 경계다.
최소 수정 방향
최종 user ID 비교 대신 모든 관찰된 owner 전환에 대해 즉시 증가하는 auth epoch를 캡처·검사한다. rebuild 예약 여부와 무관하게 전환을 식별하도록 하고, 이벤트 전달보다 먼저 세션 객체가 바뀌는 창까지 막으려면 캡처한 session/token identity도 함께 검증한다.

확인된 보존 동작과 한계

  • 42501은 zero wallet로 삼켜지지 않고 오류로 남는다.
  • 일반 signed-out build/refresh는 RPC 0회이며, 늦은 initialSession과 disabled gateway 하네스는 기존 focused test에서 통과했다.
  • 일반 A→B의 stale failure는 B 상태를 훼손하지 않았다.
  • 전체 suite는 이 worker가 반복하지 않았다. coordinator가 전달한 원본에는 관련 44 tests와 변경 4파일 analyze의 exit 0이 기록되어 있다.
  • production Supabase 접속은 하지 않았다. 타이밍 재현은 lockfile과 동일한 GoTrue 2.18.0의 실제 BehaviorSubject를 사용했다.
