03Sentry 5G9 — 왜 급한가

무료충전소 폴링이 위젯 dispose 후에도 ref.read 를 호출한다. 프로덕션 최대 이슈로 66.5k 이벤트 / 170명이 쌓였고, 수정이 배포되기 전까지 매일 늘어난다.

수정 #165 는 ad_platform · ad_service · internal_shortform_reward_flow · pangle_platform 네 파일과 테스트다. 크래시가 아니라 노이즈성 예외지만, 이 볼륨은 Sentry 에서 진짜 신호를 가리는 비용이 크다 — 8월 지갑 장애 때 "가짜 에러가 쌓이면 진짜를 못 본다"를 실제로 겪었다.

04배포 경로 — 결정이 필요하다

미배포 세트가 전부 Dart 컴파일 대상이라 두 길 다 열려 있다.

로컬 shorebird patch 는 막혀 있다

picnic_app/scripts/shorebird-patch.sh 가 NO-GO 가드로 로컬 프로덕션 패치를 차단한다. 패치는 Codemagic 보호 워크플로 picnic-app-patch-ios · picnic-app-patch-android 전용이고, 정확한 SHA 승인 증빙이 필요하다. 과거 핸드오프(handoff-cotton-candy-production.html)와 공통 flutter-release 정책의 로컬 CLI 패치 절차는 이 프로젝트에서 구절차다.

경로 A — 130008 신규 빌드 (8/18 결정된 기본안)

  1. 선행 검증 2가지 (8/18 결정에 명시): Android 실기기 결제 E2E(+130001 이후 빌드는 전부 Billing 8 인데 기존 E2E 는 Billing 7 기준) · 큰 금액 투표와 "전액 사용" 실기기 확인(지갑·투표 경로가 여러 군데 바뀜)
  2. pubspec.yaml 을 1.3.0+130008 로 범프해 main 에 머지 (MmPPBB 규칙: 같은 버전 빌드 순번 +1)
  3. HEAD == origin/main·클린 트리 확인 → 사용자 승인 → annotated tag 푸시 → Codemagic → 스토어 업로드 확인 → 새 Shorebird release 확인
  4. #166 ANR 심볼리케이션은 이 빌드부터 효력 — 첫 130008 빌드에서 Sentry 심볼리케이션이 실제로 되는지 확인할 것. 이후 패치 워크플로는 빌드번호 ≥130008 에만 --split-debug-info 를 자동 전달한다

경로 B — 130007 대상 OTA 선행 (5G9 이 급하면)

미배포 앱 코드가 전부 Dart 라 release 1.3.0+130007 대상 패치가 기술적으로 가능하다(#147~#152·splash_key.png 은 이미 릴리스 안 — 02 참조). 단:

  • 기존 결정 두 개를 뒤집는 일이다. 8/16 "투표 수정(#159)은 OTA 하지 않는다"(서버측 근본 수정 picnic-supabase #90 으로 증상은 이미 해소, 앱 수정은 안전망), 8/18 "다른 세션 작업까지 모아 130008 일괄". 뒤집을 근거는 그 뒤에 생긴 #165(5G9) 뿐이다
  • main HEAD 로 패치하면 8건이 한꺼번에 나간다 — 사실상 130008 내용의 조기 배포다. 이를 의도하는지 먼저 판단할 것
  • 실행은 Codemagic picnic-app-patch-ios·picnic-app-patch-android 로, 정확한 대상 SHA 승인 증빙과 함께. 플랫폼별 각각 실행
  • 패치 시 native/asset diff 경고가 없어야 정상이다. 경고가 나오면 멈추고 원인을 확인할 것 (#162 의 l10n 은 생성 Dart 로 컴파일되므로 원칙상 안 걸린다)
  • 패치 후 shorebird patches list --release-version=1.3.0+130007 --json 으로 stable 채널·롤백 아님·플랫폼별 artifact 를 확인 — 워크플로 성공만으로 완료 처리하지 않는다

5G9 는 비치명 노이즈(일 4~20k)라 그것만으로 두 결정을 뒤집을 정도는 아니다. 기본은 경로 A 유지하되, 130008 이 1주 이상 더 밀리면 그때 #165 단독(또는 main HEAD) 패치를 결정권자와 다시 논의하는 것을 권한다. 패치 워크플로에는 release provenance 미검증 구멍(스테이징 릴리스에 prod 패치 가능)이 알려져 있으니 실행 시 대상 릴리스를 수동으로 재확인할 것.

05함정

① #159·#160 은 방어이지 근본 수정이 아니다

8/15 대량 투표 허위 실패의 실제 원인은 플랫폼 저하 3분이었다. 이 수정들은 그런 상황에서 응답 유실을 reconcile 하고 이중 차감 창을 막는 방어다. 배포 후에도 플랫폼 저하가 재발하면 투표 지연 자체는 다시 생길 수 있다 — 그때 "수정이 안 됐다"고 오판하지 말 것.

② 배포 검증은 이벤트 소멸로 한다

5G9 는 배포 후 새 버전/패치 번호에서 신규 이벤트가 0인지로 검증한다. 구버전 이벤트는 미적용 단말에서 계속 들어오므로 총량 감소만 보면 오판한다.

③ 서버 쪽은 이미 별도로 닫혔다

같은 기간의 지갑·적립 서버 장애 4건(코튼 게이트·Tapjoy·투표 보너스)은 handoff-20260819-wallet-incidents.html 에서 전부 복구·소급 완료됐다. 이 문서의 대기열은 앱 클라이언트 쪽이다. 혼동하지 말 것.
