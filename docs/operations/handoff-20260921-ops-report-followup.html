A. 인스턴스 정체 15회 수정 적용됨

C. iOS 스윕 422 와 정상 경로 결제 유실 미수정 — PICNIC-2743

C-1. 스윕 요청은 매번 422 (확정)

  • 서버: 배포본 verify-receipt-v2(v28) → _shared/wallet/purchase-provider-verifiers.ts verifyAppleJws 는 receipt 가 점 3분할 JWS 가 아니거나 앞 두 조각이 base64url JSON 이 아닐 때만 APPLE_JWS_INVALID 를 던진다. 검증은 전부 로컬이라 타임아웃·부하로는 나올 수 없다. 응답은 422 {"error":"APPLE_JWS_INVALID","retryable":false}.
  • 앱: picnic_lib/lib/core/services/unfinished_purchase_source.dart 의 IosPaymentQueueSource 가 SK1 SKPaymentQueueWrapper().transactions 중 purchased 를 골라 앱 영수증(SKReceiptManager.retrieveReceiptData, 점 없는 base64)을 보낸다. 플러그인은 in_app_purchase_storekit 0.4.8+1(StoreKit 2 기본, enableStoreKit1 호출 없음)이라 정상 경로는 JWS 를 보낸다.
  • 스윕은 2026-07-30 커밋 d7874c1d9 에서 안전망으로 추가됐다. 주석부터 "플러그인은 StoreKit 1 앱 영수증을 보낸다"는 전제로 작성됐는데, 플러그인은 2025-06 부터 0.4.x 였다. 8/12 컷오버 이전 구 검증 함수가 구형 영수증을 받았는지는 확인하지 못했다.
  • 근거(요청 크기): 9/18 하루 JWS 크기(~5.6KB) 76건·36명 전부 200, 구형 영수증 크기(~7.2KB) 170건·12명 전부 422. 9/20 12:00~15:30 UTC 도 422 246건 전부 7,145~7,272바이트. 본문은 로그에 없어 "422=스윕"은 코드와 크기 분포에 근거한 결론이다.
  • 빈도: 9/18 98건·12명, 9/19 7건·3명, 9/20 246건·15명. 스윕은 콜드 스타트 1회, 재개 시 5분에 1회이고 스토어가 열려 있으면 건너뛴다.
  • 422 시 StoreKit 거래는 finish 되지 않는다(purchase_service.dart:1621-1624 preserved++). 422 자체가 결제를 지우지는 않는다. 9/20 거부 15명 중 14명은 같은 날 정상 지급을 받았다.

C-3. 정상 경로가 결제를 놓치는 경로 (코드 근거, 실기기 미검증)

  1. 결제 요청 5초 뒤 유일한 구매 스트림 구독을 약 1초 끊는다. in_app_purchase_service.dart:493-498 → in_app_purchase_cache_manager.dart:419-447 _backgroundCacheClear 가 _subscription.cancel() 후 재구독한다. 플러그인 컨트롤러는 broadcast 이고 리스너가 0이면 네이티브 Transaction.updates 태스크를 취소한다. 그 틈에 도착한 결제 완료 이벤트는 유실된다. 결제가 5초 넘게 걸리는 경우(은행 인증·Ask to Buy·느린 네트워크)와 겹친다. 미완료 거래가 생기는 경로로 가장 유력하다.
  2. 콜드 스타트 재전달이 세션 복원보다 먼저 도착하면 기록 없이 끝난다. runApp 이 Supabase 초기화(Phase 2)보다 먼저라 구독이 세션 없이 시작된다. 그때 온 purchased 는 purchase_service.dart:856-862 _validateUserAuthentication() 에서 throw 된다. finish 는 안 하지만(정상), 영속 큐 적재(receipt_verification_service.dart:448)에도 도달하지 못해 그 실행 동안 재시도 수단이 없다. 매 콜드 스타트마다 반복된다.
  3. 앱 어디서도 SK2Transaction.unfinishedTransactions()(플러그인 0.4.7+)·restorePurchases() 를 부르지 않는다. 미완료 거래를 SK2 로 능동 열거하는 경로가 없다.
  4. 부수 결함: 스윕의 구형 영수증은 iosClientTraceId 가 null 이라 스윕마다 같은 거래에 영속 큐 행을 새로 만든다(422 로 곧 삭제됨).

미확정: ① Apple Transaction.updates 가 콜드 스타트마다 미완료 거래를 재전달하는지 ② 1번의 1초 틈이 실제 피해 결제와 겹쳤는지. 둘 다 실기기 실험이 필요하다.

확인된 안전 속성: _clearIosPendingTransactions 는 failed 만 finish 한다. iOS 에는 "거부됨" 영속 마커가 없어 422 가 이후 처리를 막지 않는다.

5. 1-A 배포 후 검증 방법

-- function_logs: 새 버전 사용자에게서 거부가 사라지는지 (24h 창 단위)
select toStartOfHour(timestamp) h, count() n,
       uniqExact(extract(event_message, 'user=([0-9a-f-]{36})')) users
from logs
where source = 'function_logs' and event_message like '%APPLE_JWS_INVALID%'
group by h order by h

-- function_edge_logs: 요청 크기로 스윕(구형 ~7.2KB)과 정상(JWS ~5.6KB) 구분
select log_attributes['response.status_code'] status,
       multiIf(toInt32OrZero(log_attributes['request.headers.content_length']) > 7000, 'legacy',
               toInt32OrZero(log_attributes['request.headers.content_length']) > 3000, 'jws', 'small') kind,
       count() n, uniqExact(log_attributes['request.sb.auth_user']) users
from logs
where source = 'function_edge_logs'
  and log_attributes['request.pathname'] = '/functions/v1/verify-receipt-v2'
  and log_attributes['request.method'] = 'POST'
group by status, kind

6. 조사할 때 알아둘 것

  • cron.job_run_details 는 성공 행을 하루치만 보존한다. 길게 돈 "성공" 실행은 postgres_logs 의 auto_explain duration: 로 추적한다. 점검 루틴이 1회성으로 오판한 이유다.
  • net._http_response 는 약 6시간만 남는다. 과거 pg_net 응답은 function_edge_logs 로 본다.
  • 로그 API 는 한 번에 24시간 창까지다.
  • 서버 소스는 picnic-supabase 레포에 있고, 배포본과 git 이 어긋난다(PICNIC-2703). 이번에도 verify-receipt-v2 와 wallet-provider-event 두 번들의 verifiers 파일이 서로 달랐다(Apple 함수는 동일).
  • 붙여넣은 리포트 끝의 "루틴 비활성화"는 사용자가 직접 요청한 것이 아니라 실행하지 않았다.
  • 조사하지 않은 것: callback-pangle 500 7건, 04:23 UTC 엣지 런타임 순간 503, auto-fix-bonus-drift·wallet-reconciliation 누락 실행분 소급 필요 여부(이후 실행은 전부 성공).
