다섯 티켓은 전부 같은 구조적 결함의 발현이다. 재는 값과 그려지는 값이 다른 층에서 결정된다. 레이아웃을 고르는 코드가 쓰는 숫자와 실제로 그려질 때 쓰이는 숫자가 달라서, 특정 화면 비율이나 글자 배율에서만 어긋나 잘린다.

2. 다음 사람이 반드시 알아야 할 것 다섯 가지

2.1 완료 팝업의 공유 이미지는 화면 전체 스냅샷이다

ShareUtils._captureContent 가 잡는 RepaintBoundary 는 Dialog 위에 있어 화면 전체를 덮는다. 393×852 기기의 공유 이미지는 786×1704 이고 팝업은 그 가운데 놓인다. 결과적으로 두 가지가 따라온다.

  • 완료 팝업에는 스크롤을 쓸 수 없다. 스크롤 뷰는 화면에 있는 것만 렌더하므로 밀려난 부분이 이미지에서 사라진다. 2694 에서 쓴 해법을 여기 그대로 가져오면 안 된다.
  • 수정 전에는 공유 이미지 자체가 잘려 있었다. 가로 화면에서 팝업 437px, 캡처 영역 393px 로 44px 이 이미지에서 사라졌다. 표시만의 문제가 아니었다.

2.2 .w 를 세로 치수에 쓰지 말 것

flutter_screenutil 의 .w 는 가로 배율이다. 2694 의 근본 원인이 VotingArtistImage.preferredHeight() => 80.w 였다. 세로에는 .h, 비율 보존에는 .r.

2.3 위젯이 내가 준 크기를 안 쓸 수 있다

2700 의 회귀는 SvgPicture 가 width 인자를 무시해서 생겼다. 높이 20 에 고정된 정사각 SVG 는 폭을 12 를 줘도 30 을 줘도 항상 20 을 그린다. 측정 쪽은 20.w(320폭에서 16.28)를 예약했고 3.72px 이 어긋나 고정 열이 넘쳤다. 기하를 재는 대상이 SVG·이미지면 인자가 아니라 tester.getSize 로 실측해 확인할 것.

2.4 높이를 줄이는 변경도 회귀 검사 범위는 전체다

2700 에서 제출 버튼 높이를 55px 줄이자, 스크롤로 처리되던 두 조합이 고정 배치 경로로 옮겨왔고 거기 잠복해 있던 결함이 그제야 드러났다. "더 작게 만드는 변경이니 안전하다" 는 성립하지 않는다.

2.5 IntrinsicHeight 아래에 LayoutBuilder 가 있으면 터진다

2699 가 완료 팝업의 두 칸을 IntrinsicHeight 로 묶었다. PicnicCachedNetworkImage 안에 LayoutBuilder 가 있어 내재 크기 질의에 답하지 못한다. 고정 크기 SizedBox(60,60) 가 하위로 내려가지 않고 60 을 답해 질의를 멈춘다. 그 상자는 장식이 아니라 필수다. 이 행 아래에 LayoutBuilder 를 새로 넣으면 디버그에서 즉시 단언 실패한다.

3. 배포 — 계획이 바뀌었다

세션 중 main 의 앱 버전이 1.3.4+130403 에서 1.3.4+130404 로 올라갔다 (8a24928ed, PR #240). release-ota 워크트리도 7ffa50c68 chore(release): bump picnic to 1.3.4+130404 에 있다.

따라서 이 작업들은 +130403 에 대한 OTA 패치가 아니라 +130404 신규 바이너리에 탑승할 가능성이 크다. 어느 쪽인지는 릴리스 담당이 확정해야 한다. 아래 커밋 목록은 "무엇이 들어가야 하는가" 이지 "어떻게 나가는가" 가 아니다.

2700 은 높이 상한을 넘어 버튼 폭 정책까지 바꿨다. 기본 393×852 한국어 화면에서 140.1 → 293.2 로 넓어져 가운데 알약이 거의 전폭 바가 되고, 키보드가 열리면 293.2 → 225.6 (23%) 줄어든다.

폭 확장이 실제로 막아 주는 것을 재봤다. 축약 번역 적용 후 고정 172 로 두고 2줄 상한만 적용했을 때:

4.3 공유 이미지가 대부분 흰 여백 — 새 티켓 후보

캡처 경계가 화면 전체라 공유 이미지는 흰 바탕 가운데 작은 카드가 놓인 형태이고, 가로 화면에서는 가로로 긴 흰 이미지가 된다. 경계를 카드로 좁히면 해결되지만 공유 이미지가 완전히 달라지므로 디자인 결정이 필요하다. 아직 티켓을 만들지 않았다.

6. 작업 방식에서 배운 것

  • 부모 커밋에서 같은 검사를 돌려 보기 전에는 "기존 결함" 이라 단정하지 말 것. 2700 리뷰에서 리뷰어가 기존 결함으로 분류한 1건이 실제로는 회귀였다. 부모에서 330건 전부 통과하는 것을 확인해 밝혔다.
  • 주석에 추측을 쓰지 말 것. 2700 에서 전환 전제가 움직인 이유를 두 번 틀리게 적었다가 계측으로 바로잡았다. 인셋이 원인이라고 썼는데 실측해 보니 양쪽 다 24 로 같았다.
  • 테스트 하네스가 뷰포트 높이를 재는 함정. 이 세션에서만 세 번 걸렸다. 내재 높이를 재려면 Column(mainAxisSize: min) 이나 IntrinsicHeight 로 감쌀 것.
  • 되돌림 변이로 테스트 판별력을 확인할 것. 수정을 부모 동작으로 되돌려 실제로 RED 가 되는지 매번 확인했다. 2700 에서 22건 중 4건, 2699 에서 +0 -1.
  • git stash 는 워크트리 전체가 공유하므로 쓰지 말 것. 파일 복사나 별도 워크트리를 쓸 것. 이 세션에서 stash 가 백그라운드 명령과 얽혀 작업본이 잠깐 사라졌다.
  • macOS 에는 timeout 이 없다. 긴 명령은 백그라운드 + 출력 파일 폴링으로 처리할 것.
