원 차단 지적은 2건 완전 종결, 2건 부분 종결이다. 가시성·활성 버튼 overflow 자체는 개선됐지만, JMA 유효성 밴드의 높이 예산이 실제 렌더보다 작고 활성 폭을 무조건 적용해 비활성 상태를 최대 52px 과대 예산하는 새 차단 지적 2건이 남는다.

1. 원 지적 4건 종결 여부

원 지적판정독립 확인 근거
1. JMA 280×280·2.0배 첫 화면 clip 종결 resolveVoteDialogVerticalInset가 필수 높이를 기준으로 40/20·24를 최대 8까지 낮추고, 실제 라우트 제약 안에서 카드 chrome을 별도로 차감한다 (voting_dialog_layout.dart:99-140, jma_voting_dialog.dart:290-324, voting_dialog.dart:206-249). 280×280 일반/JMA×3배율, 키보드 280 조합, SafeArea 경로의 Rect·RRect·hit-test 검사가 포함된 viewport 102건이 통과했다. 최소 여백은 SafeArea 안쪽에 적용되므로 시스템 영역이나 다른 터치 영역을 침범하는 경로는 diff와 테스트에서 발견하지 못했다.
2. JMA 유효성 설명이 캡슐 밖에 위치 부분 종결 문구는 장식 밴드에서 입력 직후 조작부 밴드로 이동했고 Semantics(liveRegion: true)가 추가됐다 (jma_voting_dialog.dart:471-487,1434-1501). 851×393·412×430·280×280의 위치·캡슐·스크롤 조상 단언과 live-region 단언도 의미 있게 이전 구현을 구별한다. 다만 새 높이 계산이 아이콘 최소 높이와 가로 border를 빠뜨려 실제 높이의 상한이 아니므로 아래 차단 지적 1에 따라 예산 측면은 미종결이다.
3. 활성 JMA 버튼 라벨 폭 과소 예산 부분 종결 활성 라벨 폭에서 20px 아이콘과 간격을 차감하고 렌더도 같은 상수를 사용한다 (jma_voting_dialog.dart:593-624,1567-1585). 280×320 태국어·버마어 경계 테스트는 실제 활성 아이콘, RenderFlex 예외, Rect/RRect를 검사하므로 이전 폭으로 되돌리면 실패하는 경로가 코드상 분명하다. 그러나 활성 폭을 비활성 상태에도 무조건 적용하여 첫 화면의 모드·여백을 불필요하게 바꾸는 반대 방향 회귀가 아래 차단 지적 2로 남는다.
4. 행렬·RRect clip·느슨한 fallback 종결 실제 전달한 카드 반경과 컨트롤 네 꼭지점으로 RRect overhang을 계산하며, 기존 fallback도 hidden strip을 포함한 LargePopupWidget Rect가 아니라 anti-alias capsule을 찾는다 (voting_dialog_viewport_test.dart:73-212, voting_dialog_presentation_test.dart:55-69,493 부근). PIC·키보드·실제 showDialog/SafeArea·짧은 부모·활성/invalid·정책·IME 행렬이 추가됐다. 모드와 반경은 동일 프레임의 외부 제약·측정값만 입력받는 순수 결정이라 순환 의존은 없다.

2. 새 차단 지적

중간1. 이동한 validation 밴드의 높이 예산이 실제 Row보다 작다

근거와 실패 조건
렌더 Row의 왼쪽 아이콘 박스는 16px 글리프와 사방 2px padding으로 높이 20px이다. 그러나 _inputFeedbackHeight는 텍스트 높이만 사용한다. 1.0배 한 줄은 12 × 1.45 = 17.4px이므로 실제 Row가 최소 2.6px 더 높다. 또한 Container의 1px border는 decoration padding으로 좌우 폭도 2px 소비하지만 측정용 textWidth에서는 빼지 않아, 줄바꿈 경계에서는 한 줄 전체를 과소 계산할 수 있다. 따라서 estimatedEssential + cornerClearance ≤ bodyHeight < actualEssential + cornerClearance인 짧은 부모/창에서 actionsPinned를 잘못 고르고 첫 조작부를 RRect 모서리에 걸치게 한다. 신규 invalid 테스트는 한국어·1.0배의 세 개 고정 크기만 보고 실제 밴드 높이와 예산을 직접 비교하지 않아 이 경계를 건너뛴다.
최소 수정 방향
측정 폭에서 _validationBorderWidth * 2를 차감하고, 세로 본문은 max(_validationIconSide, measuredTextHeight)에 padding과 border를 더한다. 실제 validation 컨테이너 높이가 계산값 이하인지 로케일·배율별로 검증하고, 짧은 부모 높이를 임계값 전후로 둔 RRect 회귀 테스트를 추가한다.

중간2. 활성 폭을 항상 예산해 비활성 첫 화면을 최대 52px 과대평가한다

근거와 재현 조건
_essentialHeight는 _canVote와 무관하게 항상 아이콘 폭을 뺀 _submitLabelMaxWidth()를 쓴다. 구현 보고의 자체 측정에서도 280폭·1.0배 태국어는 비활성 라벨 78px, 활성 라벨 130px으로 차이가 52px이다. 따라서 280×320, locale=th, textScale=1.0, 빈 입력에서는 실제 비활성 버튼에 없는 52px을 예약해 route inset을 대략 27px 대신 하한 8px까지 낮추고, 실제 비활성 조작부라면 가능한 actionsPinned 대신 allScroll을 선택한다. 그 결과 첫 화면에서 아티스트/신원 장식이 조작부 아래로 이동한다. “조작부가 담기는 동안 디자인 여백을 유지한다”는 정책과 배치 순서를 불필요하게 깨는 시각 회귀다.

테스트 공백
태국어·버마어 경계 테스트는 먼저 5를 입력해 활성 상태만 검사하고 모드도 단언하지 않는다. 이어지는 3상태 예산 테스트는 아이콘이 없는 일반 VotingSubmitButton을 대상으로 하므로 JMA 전용 폭 정책을 검증하지 않는다.
최소 수정 방향
현재 렌더 상태의 실제 폭으로 JMA 버튼 높이를 재거나, 활성 시에도 줄 수가 늘지 않도록 가용 카드 폭을 사용하는 버튼 폭 정책으로 상태 간 높이를 같게 한다. 태국어/버마어 빈 입력→활성 전환에서 inset·모드·장식 순서와 overflow를 함께 검증한다.

3. 테스트의 결함 포착력과 RED 표본

  • 의미 있는 단언: _capsuleCornerOverhang는 실제 LargePopupWidget.cardBorderRadius와 컨트롤 모서리를 사용하므로 단순 bounding-box tautology가 아니다. _capsuleCard도 outer capsule이 descendant 순서상 첫 anti-alias Container이고, _nearestGestureTarget은 Flutter finder의 가까운 조상 우선 순서로 JMA의 실제 GestureDetector를 고른다.
  • validation RED 감도: 이전 구현처럼 문구를 장식 밴드로 되돌리면 851×393에서 캡슐 containment가 깨지고, 문구와 입력의 Scrollable 조상 목록도 달라진다. 따라서 an over-the-maximum amount explains itself 3건은 이전 결함을 실제로 구별한다.
  • 활성 폭 RED 감도: 측정 폭만 이전 값으로 되돌리면 실제 버튼의 아이콘·간격은 남고 예산만 낮아진다. 280×320 태국어/버마어 테스트는 예외와 Rect/RRect를 검사하므로 이전 actionsPinned 오판 경로를 포착한다. 다만 현재 green이 올바른 비활성 모드까지 증명하지는 않는다.
  • 실행 제한: 이 worker의 sandbox에서는 flutter_tester가 127.0.0.1:0 서버 소켓을 bind할 때 Operation not permitted로 중단돼 RED 되돌림과 green 테스트를 직접 실행할 수 없었다. 위 RED 판단은 old/new 코드 경로와 단언을 대조한 정적 역검증이며, green 수치는 동일 HEAD를 코디네이터가 비제한 환경에서 실행한 결과다.

6. 구현자가 남긴 2건의 판단

남긴 항목판단근거
(a) 긴 로케일 라벨 무제한 감김 타당 — 선행 결함 부모 2e5ccdc20의 JMA 버튼도 width: 172.w이고 Text에 maxLines가 없다(jma_voting_dialog.dart 부모의 1262-1326). 280폭에서 활성 라벨 가용 폭 약 80px, 태국어 2.0배 한 줄 높이 약 52.2px이므로 7줄과 vertical padding을 합친 약 370px 주장은 계산상 일치한다. 이번 회귀는 아니며 버튼 폭 정책을 별도 티켓으로 다루는 판단이 타당하다.
(b) 851×393 + K=280에서 조작부 첫 화면 수용 불가 타당 — 물리적으로 불가능 키보드 뒤 남는 높이는 113px이다. 시스템 padding이 0인 최대치에서도 최소 route inset 16px과 hidden strip+border 약 27px을 빼면 body는 약 70px이며, 추가 안전영역이 있으면 보고한 약 62px까지 줄어든다. 투표 버튼을 제외해도 전체 사용 48px + 입력 최소 52px = 100px이라 동시에 담을 수 없다. 따라서 “예외 0 + 스크롤로 입력 도달” 계약은 타당하다. 다만 62px은 padding 조건에 따른 값이지 모든 테스트 환경의 고정값은 아니다.

7. OTA 범위

Shorebird 소스 OTA 범위에 해당한다. 누적 diff는 문서 4개, production Dart 5개, Dart 테스트 2개뿐이다. Android/iOS/macOS 네이티브 코드, 플러그인 등록, 에셋, pubspec.yaml, pubspec.lock 변경은 없다. 실제 patch 생성·배포 성공은 이 읽기 전용 리뷰 범위가 아니다.

8. Non-blocking 관찰

  • 유효성 문구의 별도 live region은 값 변경 시 낭독에는 유효하지만 TextFormField semantic node에 error/validation 상태를 직접 연결하지는 않는다. 후속 접근성 개선에서는 SemanticsValidationResult 또는 동등한 field association을 검토할 수 있다.
  • validation 등장으로 route inset이 바뀌면 Dialog의 100ms AnimatedPadding 도중 모드가 한 번 바뀔 수 있다. 결정 함수는 순수하고 되먹임이 없어 프레임 간 진동은 아니지만, 테스트는 400ms 두 번 pump해 중간 프레임의 시각 연속성을 검증하지 않는다.
  • viewport 테스트 상단의 “모든 경우 keyboard-free” 설명은 같은 파일에 키보드 그룹이 추가된 현재 내용과 어긋난다. 동작에는 영향이 없는 문서 주석 문제다.
  • JMA 3상태 예산을 설명하면서 일반 VotingSubmitButton을 검사하는 2건은 해당 아이콘 결함에 직접적인 증거가 아니다. 실제 JMA 활성 경계 테스트가 원 결함을 포착하므로 중복 테스트의 설명·대상을 맞추는 것은 non-blocking이다.
