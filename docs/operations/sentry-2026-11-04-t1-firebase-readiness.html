T1 · Firebase 준비 전 푸시 접근 수정

작성: 2026-11-04 KST · 대상: PICNIC-APP-5K3, PICNIC-APP-5JZ · 수정 전 기준: d544f015bf9334407c6e06ba2bd4be7c8f4cb8ed

결론: 두 이슈의 [core/no-app] 호출 경로는 앱 빌드 증가와 Firebase SDK 업그레이드 이후에도 남아 있었다. 현재 SDK에서 같은 오류를 재현했고, 기본 Firebase 앱이 준비된 뒤 푸시 초기화를 시작하도록 수정했다. 관련 자동 검증과 독립 코드 리뷰는 완료했다.

남은 조건: Android 격리 패키지의 네이티브 Firebase 테스트는 통과했다. 별도로 기존 운영 앱 1.3.5+130502에서 지정 테스트 계정의 FCM 서버 등록을 확인했다. 미배포 수정본의 SDK 실패 → 앱 재시도 → FCM 서버 등록 연결은 검증하지 않았다. iOS·Android의 전체 연결 검증이 끝나기 전에는 T1 전체 완료나 배포 검증 완료로 볼 수 없다. 이 작업은 로컬 브랜치에 보존하며 배포·OTA·스토어 상태·Sentry/Jira 상태를 변경하지 않았다.

아래 버전은 각 Git 기준점의 picnic_app/pubspec.lock과 picnic_lib/pubspec.lock에서 대조했다. 두 패키지의 해당 SDK 버전은 각 기준점에서 같았다.

설치된 Messaging 16.1.2와 17.0.1의 소스는 모두 FirebaseMessaging.instance → Firebase.app()으로 기본 앱을 조회한다. Core platform interface 6.0.2와 8.1.1은 기본 앱이 없으면 core/no-app을 발생시킨다. 따라서 SDK 업그레이드는 이 호출 순서 결함을 해결하지 않는다. 네이티브 SDK 변경이 발생 빈도에 영향을 주는지는 기기 증거가 없어 판단하지 않았다.

미배포 수정과의 관계

기존 SDK 업그레이드가 사용자에게 아직 전달되지 않았다는 사실만으로 이 두 오류를 설명할 수는 없다. 업그레이드된 현재 SDK에서도 같은 오류가 재현됐기 때문이다. 이번 T1 가드는 기존 SDK 업그레이드와 별도의 Dart 수정이다. 설치된 구버전 앱의 해결 여부는 이 수정의 실제 전달과 등록·알림 동작을 확인한 뒤 판단해야 한다.

130605는 소스 비교 기준이다. 제공된 두 이슈의 릴리스 표본에 130605가 없다는 사실을 무발생·해결·미배포의 증거로 사용하지 않았다. 이번 T1에서 스토어 배포 상태를 새로 조회하지 않았다. 구 SDK 태그에 이 변경을 적용한 실행 검증이나 OTA 호환성 판정도 수행하지 않았다.

수정 범위

제품 변경은 push_token_service.dart 한 파일이다. 기존 initialize()·resume() 인터페이스를 유지했다.

  • 기존 coordinator가 있으면 그대로 사용한다. 없으면 Firebase.apps에 [DEFAULT]가 있을 때만 생성한다. 보조 앱만 있는 상태는 준비 완료로 보지 않는다.
  • 미준비 상태를 성공으로 저장하지 않는다. 준비 후 initialize() 또는 resume()이 coordinator 생성과 토큰 등록을 재개한다.
  • Firebase가 미준비여도 초기화의 콜백 설치, 대기 중인 알림 탭 전달, 로컬 실행 알림 읽기는 유지한다. 권한 요청 중 합류와 dispose 이후 이전 작업 무효화도 유지한다.
  • 예상 밖의 팩토리·SDK 오류를 숨기는 catch를 추가하지 않았다. 최초 SDK 초기화 실패 보고와 앱 resume의 기존 전역 zone 오류 보고 경로를 유지한다.

SDK 버전, lockfile, 네이티브 코드와 앱의 초기화 연결은 바꾸지 않았다. SDK 설정·reset을 위한 테스트 전용 제품 API도 추가하지 않았다. Firebase 상태 격리 helper는 test/helpers에만 두었다.

기기 검증 준비와 실행 범위

Android 검증은 scripts/qa/run_firebase_device_android.py로 생성하는 별도 패키지 io.picnic.qa.firebase_readiness에서 수행한다. 현재 라이브러리의 의존성 버전을 대조하며 운영 앱의 패키지·설정·서명·계정 파일을 사용하지 않는다.

Android 실기기에서 네이티브 Firebase Core의 실패·재시도, 실제 core SDK 단계와 푸시 준비 가드를 검증했다. 권한, FCM 토큰, 서버 등록과 알림 입력은 제어된 테스트 값으로 대체했다. 이 결과는 운영 FCM 등록이나 전체 앱 재시도 연결의 성공을 의미하지 않는다.

iOS 개발 환경 복구

사용자 승인과 macOS 관리자 인증 후 Xcode 27.2의 필수 구성요소를 설치했다. CoreSimulator는 1174.9.2 → 1174.21, XcodeSystemResources는 27.1 계열에서 27.2 계열로 갱신됐다. xcodebuild -checkFirstLaunchStatus와 simctl list가 exit 0으로 종료됐다.

새 Picnic Firebase QA 시뮬레이터는 iOS 27.1에서 bootstatus: Finished를 확인했고 Flutter가 지원 기기로 인식했다. 기존 시뮬레이터의 데이터 마이그레이션 실패 기록은 별도로 남기고 데이터를 지우지 않았다. 이 결과는 개발 환경 복구에 한정하며 iOS 앱·Firebase·FCM 테스트 통과를 의미하지 않는다.

15시 후속 확인: iOS 27.1 QA 시뮬레이터를 다시 부팅하자 Data Migration Failed가 나타났다. bootstatus의 exit 0만으로 성공 처리하지 않았다. Xcode의 첫 실행 구성 검사는 계속 통과했지만 마이그레이션 실패의 원인은 확정하지 않았다. 해당 시뮬레이터의 데이터를 보존하고 종료한 뒤, 설치된 iOS 26.5 런타임과 iPhone 16 Pro 유형으로 별도 Picnic Firebase QA 26.5를 만들었다. 새 기기는 bootstatus: Finished와 exit 0을 확인했고 마이그레이션 실패 문구가 없었다. 후속 검증은 이 시뮬레이터에서 수행한다.

앱의 등록 성공 로그와 지정 계정의 서버 갱신 시각이 일치한다. 기존 Android 운영 앱에서 실제 서버 등록 경로가 동작한 근거다. 검증 후 기기 연결 도우미를 종료했고 운영 앱과 기기 데이터는 유지했다.

설치된 130502에는 이번 미배포 T1 가드가 없다. 이 결과는 수정본의 실패·재시도 복구, FCM 토큰의 실제 전달 가능성, 알림 수신 또는 iOS 등록 성공을 증명하지 않는다. 기존 서버 행에 iOS 토큰이 있다는 사실도 이번 iOS 실행 증거로 사용하지 않았다.

사용자는 현재 iOS 검증 범위를 시뮬레이터로 지정했다. iOS 네이티브 Core와 준비 가드 검증 도구를 준비 중이며, 아직 iOS 앱 테스트 통과 결과는 없다. 실기기 FCM 등록 검증은 현재 범위에서 보류한다.

배포 전 남은 기기 검증

iOS와 Android 테스트 빌드에서 아래 항목을 확인해야 한다. 사용자 ID·FCM/APNs 토큰 원문 없이 단계 기록과 등록 성공 응답을 남긴다.

  1. Firebase 최초 초기화를 지연하거나 실패시킨 상태에서 앱을 복귀시켜 core/no-app이 발생하지 않는지 확인한다.
  2. 실제 앱 재시도로 Firebase를 준비시킨 뒤 MainInitializer → App → AppInitializer → PushTokenService 연결에서 FCM 등록 성공을 확인한다.
  3. 권한 창 중 연속 resume가 한 작업에 합류하고, dispose 뒤 늦은 완료가 이전 owner를 갱신하지 않는지 확인한다.
  4. Firebase 준비 전후의 cold remote 알림과 local launch 알림 목적지가 각 소스에서 한 번 전달되는지 확인한다.

배포 후보·버전·OTA 호환성과 승인 절차는 T8에서 다룬다. 현재 코드의 검증 결과를 구 SDK 바이너리나 이미 설치된 앱의 해결 증거로 사용하지 않는다.
