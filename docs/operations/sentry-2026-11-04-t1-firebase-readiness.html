T1 · Firebase 준비 전 푸시 접근 수정

작성: 2026-11-04 KST · 대상: PICNIC-APP-5K3, PICNIC-APP-5JZ · 수정 전 기준: d544f015bf9334407c6e06ba2bd4be7c8f4cb8ed

결론: 두 이슈의 [core/no-app] 호출 경로는 앱 빌드 증가와 Firebase SDK 업그레이드 이후에도 남아 있었다. 현재 SDK에서 같은 오류를 재현했고, 기본 Firebase 앱이 준비된 뒤 푸시 초기화를 시작하도록 수정했다. 이 Firebase 가드의 자동 검증과 독립 코드 리뷰는 완료했다. 후속 Fable 감사에서 찾은 Supabase 미준비 경계도 별도로 재현했다. 보완 후 원래 재현 테스트는 통과했으며, 보완 코드의 Sol/high 독립 리뷰도 APPROVE로 완료했다.

남은 조건: Android 격리 패키지와 iOS 격리 시뮬레이터 앱의 Firebase 준비·복구 테스트는 각각 통과했다. 별도로 기존 운영 앱 1.3.5+130502에서 지정 테스트 계정의 FCM 서버 등록을 확인했다. 미배포 수정본의 SDK 실패 → 앱 재시도 → FCM 서버 등록 연결은 검증하지 않았다. iOS·Android의 전체 연결 검증이 끝나기 전에는 T1 전체 완료나 배포 검증 완료로 볼 수 없다. 이 작업은 로컬 브랜치에 보존하며 배포·OTA·스토어 상태·Sentry/Jira 상태를 변경하지 않았다.

130504 → 130605는 이 표의 Firebase SDK 버전을 바꾸지 않았다. Core 5.1.0·Messaging 17.0.1은 그 이후 SDK 업그레이드에서 들어왔다. 네 기준점의 PushTokenService.resume()은 같았고 Firebase 준비 확인이 없었다.

설치된 Messaging 16.1.2와 17.0.1의 소스는 모두 FirebaseMessaging.instance → Firebase.app()으로 기본 앱을 조회한다. Core platform interface 6.0.2와 8.1.1은 기본 앱이 없으면 core/no-app을 발생시킨다. 따라서 SDK 업그레이드는 이 호출 순서 결함을 해결하지 않는다. 네이티브 SDK 변경이 발생 빈도에 영향을 주는지는 기기 증거가 없어 판단하지 않았다.

미배포 수정과의 관계

기존 SDK 업그레이드가 사용자에게 아직 전달되지 않았다는 사실만으로 이 두 오류를 설명할 수는 없다. 업그레이드된 현재 SDK에서도 같은 오류가 재현됐기 때문이다. 이번 T1 가드는 기존 SDK 업그레이드와 별도의 Dart 수정이다. 설치된 구버전 앱의 해결 여부는 이 수정의 실제 전달과 등록·알림 동작을 확인한 뒤 판단해야 한다.

130605는 소스 비교 기준이다. 제공된 두 이슈의 릴리스 표본에 130605가 없다는 사실을 무발생·해결·미배포의 증거로 사용하지 않았다. 이번 T1에서 스토어 배포 상태를 새로 조회하지 않았다. 구 SDK 태그에 이 변경을 적용한 실행 검증이나 OTA 호환성 판정도 수행하지 않았다.

수정 범위

제품 변경은 push_token_service.dart 한 파일이다. 기존 initialize()·resume() 인터페이스를 유지했다.

  • 기존 coordinator가 있으면 그대로 사용한다. 없으면 Firebase.apps에 [DEFAULT]가 있을 때만 생성을 검토한다. 보조 앱만 있는 상태는 준비 완료로 보지 않는다. 후속 보완은 실제 coordinator에 필요한 Supabase 클라이언트도 확인한다. 기존 제어용 팩토리는 실제 Supabase를 요구하지 않는다.
  • 미준비 상태를 성공으로 저장하지 않는다. 준비 후 initialize() 또는 resume()이 coordinator 생성과 토큰 등록을 재개한다.
  • Firebase가 미준비여도 초기화의 콜백 설치, 대기 중인 알림 탭 전달, 로컬 실행 알림 읽기는 유지한다. 권한 요청 중 합류와 dispose 이후 이전 작업 무효화도 유지한다.
  • 후속 보완의 catch는 Supabase getter 조회의 StateError에만 적용한다. 팩토리와 coordinator 생성은 이 catch 밖에서 실행한다. 최초 SDK 초기화 실패 보고와 예상 밖의 앱 resume 오류의 기존 전역 zone 보고 경로를 유지한다.

SDK 버전, lockfile, 네이티브 코드와 앱의 초기화 연결은 바꾸지 않았다. SDK 설정·reset을 위한 테스트 전용 제품 API도 추가하지 않았다. Firebase 상태 격리 helper는 test/helpers에만 두었다.

기기 검증 준비와 실행 범위

Android 검증은 scripts/qa/run_firebase_device_android.py로 생성하는 별도 패키지 io.picnic.qa.firebase_readiness에서 수행한다. 현재 라이브러리의 의존성 버전을 대조하며 운영 앱의 패키지·설정·서명·계정 파일을 사용하지 않는다.

Android 실기기에서 네이티브 Firebase Core의 실패·재시도, 실제 core SDK 단계와 푸시 준비 가드를 검증했다. 권한, FCM 토큰, 서버 등록과 알림 입력은 제어된 테스트 값으로 대체했다. 이 결과는 운영 FCM 등록이나 전체 앱 재시도 연결의 성공을 의미하지 않는다.

  1. Firebase 기본 앱이 없을 때 initialize/resume를 반복해도 coordinator를 만들지 않고, 제어된 로컬 실행 알림 목적지를 한 번 전달했다.
  2. 설정이 없는 네이티브 Core 초기화가 실패하고 같은 오류가 호출자에게 전달되는 것을 확인했다. 실패한 단계는 성공으로 저장되지 않았다. 이 누락 설정 오류는 운영 앱의 일시적 초기화 실패 원인을 재현한 것은 아니다.

  4. resume만으로 coordinator가 생성되고 제어된 토큰 등록이 재개됐다. 초기·실시간·로컬 실행 알림의 목적지는 각 소스에서 한 번 전달됐다.

최종 병합 AndroidManifest에서 별도 패키지 ID와 Messaging 자동 초기화·Analytics 수집 비활성화 값을 확인했다. 테스트 뒤 Gradle 정리는 verified=true였고 남은 프로세스와 강제 PID 신호는 없었다. QA 패키지는 제거됐으며 기존 운영 앱의 버전과 설치·갱신 시각은 실행 전후 같았다. 검토한 세 파일의 SHA256도 실행 뒤 일치했다.

실행기는 각 작업의 프로세스 그룹과 전용 GRADLE_USER_HOME을 사용한다. Gradle daemon의 명령, 열린 파일과 시작 시각으로 소유권을 확인한다. 소유권이나 종료 여부가 불명확하면 성공으로 기록하지 않는다. Android 실행의 DEVELOPER_DIR은 해당 자식 프로세스에만 Command Line Tools로 지정한다.

iOS 개발 환경 복구

사용자 승인과 macOS 관리자 인증 후 Xcode 27.2의 필수 구성요소를 설치했다. CoreSimulator는 1174.9.2 → 1174.21, XcodeSystemResources는 27.1 계열에서 27.2 계열로 갱신됐다. xcodebuild -checkFirstLaunchStatus와 simctl list가 exit 0으로 종료됐다.

새 Picnic Firebase QA 시뮬레이터는 iOS 27.1에서 bootstatus: Finished를 확인했고 Flutter가 지원 기기로 인식했다. 기존 시뮬레이터의 데이터 마이그레이션 실패 기록은 별도로 남기고 데이터를 지우지 않았다. 이 결과는 개발 환경 복구에 한정하며 iOS 앱·Firebase·FCM 테스트 통과를 의미하지 않는다.

15시 후속 확인: iOS 27.1 QA 시뮬레이터를 다시 부팅하자 Data Migration Failed가 나타났다. bootstatus의 exit 0만으로 성공 처리하지 않았다. Xcode의 첫 실행 구성 검사는 계속 통과했지만 마이그레이션 실패의 원인은 확정하지 않았다. 해당 시뮬레이터의 데이터를 보존하고 종료한 뒤, 설치된 iOS 26.5 런타임과 iPhone 16 Pro 유형으로 별도 Picnic Firebase QA 26.5를 만들었다. 새 기기는 bootstatus: Finished와 exit 0을 확인했고 마이그레이션 실패 문구가 없었다. 후속 검증은 이 시뮬레이터에서 수행한다.

검증은 실제 네이티브 Core와 제품의 푸시 준비 가드·core SDK 단계 그룹을 사용한다. 옵션 없는 첫 초기화는 네이티브 initializeCore가 빈 목록을 반환한 뒤 Dart에서 core/not-initialized가 발생하는 경로다. 네이티브 configure 실패로 부르지 않는다. 이후 demo 옵션으로 재시도하며 권한·토큰·서버 등록·알림 입력은 제어된 테스트 값이다. Messaging 자동 초기화와 Analytics 수집은 비활성화한다.

최종 실행에서 다음 사항을 확인했다.

  1. Firebase 기본 앱이 없을 때 initialize/resume를 반복해도 coordinator를 만들지 않았으며, 제어된 로컬 실행 알림 목적지를 한 번 전달했다.
  2. 옵션 없는 첫 초기화에서 발생한 core/not-initialized가 같은 오류 객체로 호출자에게 전달됐다. 실패한 Firebase 단계는 성공으로 저장되지 않았다.
  3. demo 옵션으로 같은 단계 그룹을 재시도해 실제 네이티브 기본 앱을 만들었다. 독립 단계와 성공한 Firebase 단계는 중복 실행되지 않았고 Messaging 자동 초기화는 false였다.
  4. resume만으로 제어된 토큰 등록이 재개됐다. coordinator는 하나였고 추가 권한 요청 없이 초기·실시간·로컬 실행 알림의 목적지를 각 소스에서 한 번 전달했다.

Fable Apex 후속 감사와 추가 재현

사용자의 Apex·Fable 활용 요청에 따라 claude-fable-5-1/high가 전체 재시도 연결을 읽기 전용으로 감사했다. 조정자는 실제 실행 모델과 제한된 도구, 작업 완료 정산을 확인했다. 감사는 제품 소스를 대조한 결과이며 테스트나 네이티브 실행 결과가 아니다.

경로확인한 연결실행 증거의 한계
최초 실패와 UI 재시도MainInitializer.retrySdkInitialization()의 실패 결과를 App이 받아 오류 화면을 표시한다. 재시도는 실패한 SDK 단계를 다시 실행하고, 성공 뒤 AppInitializer.initializeApp()으로 이어진다.기존 widget 테스트의 startupAttempt는 SDK 대기와 AppInitializer 호출을 포함한 시도 전체를 대체한다. 실제 static 체인을 실행한 증거가 아니다.
준비 후 푸시 시작모바일 AppInitializer의 백그라운드 작업이 PushTokenService.initialize()을 호출한다.호스트 테스트에서는 모바일 조건을 통과하지 않는다. 격리 네이티브 테스트도 전체 앱 연결을 실행하지 않았다.
앱 복귀오류 화면과 재시도 중에도 App의 lifecycle observer가 PushTokenService.resume()을 호출한다.기존 주입 지점으로 실제 App 복귀 콜백과 준비 전후의 푸시 가드를 검증하는 widget 회귀를 추가했다. SDK 시도와 외부 푸시 입력은 제어값이다.

재현된 추가 경계: Firebase 준비, Supabase 미준비

조정자는 격리된 호스트 테스트에서 Firebase [DEFAULT] 앱만 생성한 뒤 실제 PushTokenService.resume()을 호출했다. Supabase 클라이언트·coordinator 팩토리·메시지 소스는 대체하지 않았다. 테스트는 exit 1로 실패했고 다음 스택을 확인했다.

PushTokenService.resume()
  → _ensureCoordinator()
  → _createCoordinator()
  → authChanges: supabase.auth.onAuthStateChange
  → StateError: Supabase가 초기화되지 않았습니다.

후속 보완 전의 Firebase 가드는 이 상태에서 실제 coordinator 생성으로 진입했다. Supabase getter의 실패를 App의 unawaited 복귀 호출이 받는 경계를 재현했다. 이는 새로 재현한 준비 상태 결함이며, 기존 Sentry 두 이슈의 원인이 이 Supabase 오류라는 증거는 아니다.

설치된 supabase_flutter 2.12.0은 클라이언트를 만든 뒤 인증 복원을 기다린다. 따라서 모든 Supabase 초기화 timeout이 클라이언트 부재를 뜻하지는 않는다. 이번 재현은 클라이언트가 아직 없는 경우에 한정한다.

보완 구현과 다음 확인

Opus/high가 기존 서비스 안에서 실제 coordinator 생성에 필요한 Firebase 기본 앱과 Supabase 클라이언트를 확인하도록 수정했다. 클라이언트가 없으면 생성을 미루고 다음 호출에서 다시 확인한다. 로그인 여부를 준비 조건으로 사용하지 않는다. 확인한 클라이언트를 실제 auth stream 연결에 전달한다. 기존 제어용 팩토리, 알림 목적지 전달, 예상 밖의 팩토리 오류 보고는 유지한다. 다른 공급자의 Sol/high가 변경 3파일과 관련 의존성·회귀 테스트를 검토해 APPROVE로 판정했다. 차단 지적은 없었고 완료 정산과 검토 해시 일치를 확인했다. 이 승인은 코드 범위에 한정한다.

네트워크 차단만으로 Firebase Core 초기화 실패나 10초 timeout을 확실하게 만들 수 있다는 근거는 없다. 전체 앱 검증은 관측된 실패 또는 재현이 확인된 오류 주입 조건을 먼저 정해야 한다. 잘못된 iOS API 키 형식은 네이티브 종료를 일으키므로 Dart 재시도 검증에 사용하지 않는다.

배포 전 남은 기기 검증

iOS와 Android 테스트 빌드에서 아래 항목을 확인해야 한다. 사용자 ID·FCM/APNs 토큰 원문 없이 단계 기록과 등록 성공 응답을 남긴다.

  1. Firebase 최초 초기화를 지연하거나 실패시킨 상태에서 앱을 복귀시켜 core/no-app이 발생하지 않는지 확인한다.
  2. 실제 앱 재시도로 Firebase를 준비시킨 뒤 MainInitializer → App → AppInitializer → PushTokenService 연결에서 FCM 등록 성공을 확인한다.
  3. 권한 창 중 연속 resume가 한 작업에 합류하고, dispose 뒤 늦은 완료가 이전 owner를 갱신하지 않는지 확인한다.
  4. Firebase 준비 전후의 cold remote 알림과 local launch 알림 목적지가 각 소스에서 한 번 전달되는지 확인한다.

배포 후보·버전·OTA 호환성과 승인 절차는 T8에서 다룬다. 현재 코드의 검증 결과를 구 SDK 바이너리나 이미 설치된 앱의 해결 증거로 사용하지 않는다.
