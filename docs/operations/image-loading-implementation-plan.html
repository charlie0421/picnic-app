A2. 크기·키 계산 규칙

  1. 기본 위젯의 배치 크기는 각 축에서 유효한 명시 width/height → 유한 max constraint → 100 순서로 구하고 부모 min/max로 constrain한다. 0 크기 영역은 요청하지 않는다. NaN/무한/음수는 유효 크기가 아니다. 100 fallback은 무한 공간의 현행 safe layout을 보존한다. CDN 요청은 명시한 한 축만 있는 호출의 기존 width-only/height-only 계약을 유지한다. 양 축 모두 미지정이면 cover에서 두 실제 축을 추론하고, contain/fitWidth 등에서는 너비 한 축만 요청하여 서버 crop 가능성을 피한다. decode는 별도로 비율을 보존하는 양 축 상한을 적용한다.
  2. factory는 nullable 축을 유지한다. 주어진 양수 유한값만 URL에 사용한다. 양 축 null은 q-only를 허용하며 decode는400×400 bound. home hero는 실제 width만 전달해 h-auto로 요청한다.
  3. 현행 배율 Android min(DPR×1.1,2.5), iPad min(DPR×1.3,4), 기타 min(DPR×1.2,2.5)를 유지한다. 유한 양수 cap에만 min 적용. DPR이 비유한/0이하면1로 대체하고 비정상 cap은 무시한다. quality는 현행 면적50,000 미만85, 그 외80, GIF80, 기존 low 이미지 override를 유지한다. GIF 판단은 Uri.path로 해 .gif?token도 인식한다.
  4. 물리 목표는 round(논리×배율), 최소1. 한 축 최대2000px, 두 축 면적 최대2,000,000px로 비례 축소 후 floor한다. 한 축뿐이면 그 축만2000 cap. 이 값을 resolver의 width/height에, multiplier1로 전달한다. 외부 URL에는 resize query를 적용하지 않는다.
  5. decode bound는 명시 memCache 우선(DPR 미적용), 없으면 요청 물리 목표. width-only면 decodeWidth를 우선 보존하고 decodeHeight를 min(2000,2000000 ~/ decodeWidth)로 보충한다(height-only는 반대). 양 축 모두 자동/명시면 2000/2MP 초과 때만 함께 비례 축소한다. 한 축만 명시하면 그 값을 먼저 보존하고 자동 축에 나머지 면적 cap을 적용한다. 상세 목록78×78은 DPR1/2/3 모두78×78이다.
  6. CachedNetworkImageProvider(url, cacheKey: url)에 disk maxWidth/maxHeight를 주지 않는다. ResizeImage(..., width: decodeWidth, height: decodeHeight, policy: ResizeImagePolicy.fit, allowUpscaling: false)로 한 번 감싼다. 실제 decode는 bound 이하이며 원본 비율 유지. fit/clip은 Image/부모 담당. 2MP는 프레임당 약8MB이며 GIF 전체 메모리 상한이라는 뜻은 아니다.
  7. 최종 URL+decode 크기/정책이 같으면 같은 키다. DPR/constraints/옵션으로 키가 바뀌면 새 세대, 동일 rebuild는 같은 세대. request는 context를 보관하지 않는다. 제공된 imageRequest가 같으면 UI 높이 변화만으로 키를 바꾸지 않는다.

A3. 단일 표시 경로·생명주기

Image(
  key: ValueKey((request.url, request.decodeWidth,
      request.decodeHeight, reloadToken)),
  image: request.provider,

  errorBuilder: (context, error, stack) =>

세 함수는 공통 State의 private 메서드로 구현한다. markFirstFrame은 기존 _onImageLoadSuccess 진입점, placeholder는 사용자 placeholder/showLoadingOverlay/clip 재사용, error는 현행 retry 분류/backoff/오류 위젯으로 연결한다. 추가 progress UI나 stream widget을 만들지 않는다.

  • 첫 프레임에 timeout/retry를 취소하고 상태를 한 번만 갱신한다. GIF 매 프레임 성공 로그/setState 금지. 예약 postFrame도 mounted+generation+attempt를 다시 확인한다. URL 변경/dispose 뒤 이전 성공·오류 무시.
  • 요청 세대와 retry attempt를 구분한다. retry는 같은 provider 키와 reloadToken에 의한 Image Element 재생성. URL/cacheKey에 token을 붙이지 않는다. 실패해 남은 정확한 메모리 키만 필요 시 evict한다. live/pending 성공 작업과 disk 파일을 매 retry마다 제거하지 않는다.
  • timeout은 실제 로딩 가능한 시점부터 시작한다. cold resolve가 fast scroll로 보류되면 timer를 시작하지 않고 기존 다음 프레임 재평가를 timer 시작에만 사용한다. 이미 시작한 pending 요청은 감시 유지. reset/dispose는 모든 Timer 취소.
  • Image는 SDK 내부 ScrollAwareImageProvider를 적용하므로 이중 wrapper가 필요 없다. deferDuringFastScroll 필드는 유지하지만 이미지 트리를 제거하지 않는다. viewport lazy gate는 유지한다. 성공 URL 힌트만으로 eviction 이후 로딩 UI를 숨기지 않는다.
  • 기존 상한 모바일200MB/500개, 웹150MB/300개를 늘리지 않는다. 공통 GIF 전용 임시 축소/복구를 제거하고 LRU에 맡긴다. B가 페이지 진입50% 축소를 제거한다. telemetry map 상한/정리는 보존한다.

A4. 사전 로딩 scope

  • private Queue/Map/activeCount만 사용한다. scope들이 scheduler 하나를 공유하며 speculative active 최대2. display Image는 scheduler를 참조하지 않는다.
  • replace는 우선순위순 첫2개의 서로 다른 provider 키만 유지한다. createLocalImageConfiguration(context)로 obtain한다. generation은 갱신하되 동일 후보 rebuild가 진행 중 작업을 다시 시작하지 않는다.
  • 시작 직전 scope 생존/generation/context.mounted 확인. 오래된 queued 작업 폐기. 동일 in-flight key는 관심 scope를 합친다. 한 scope dispose가 다른 살아 있는 scope의 작업을 지우지 않는다.
  • 표준 precacheImage(request.provider, context, onError: ...)로 시작한다. 첫 프레임 뒤 표준 listener가 해제되게 프레임을 진행하고 별도 pin하지 않는다. 에러는 소비, finally에서 슬롯/in-flight 제거. background retry 없음.
  • 이미 시작된 HTTP/decode는 precacheImage로 강제 취소할 수 없다. replace/dispose는 새 시작과 stale 결과 사용을 취소한다. 시작 작업은 실제 완료까지 슬롯 점유. 가짜 timeout으로 슬롯만 반환해 실제 동시성을 초과시키지 않는다. speculative 두 작업이 느려도 display는 기다리지 않는다.
  • 영구 completed-key Set 금지. 준비된 정확한 key는 cache-hit, eviction 후 재진입은 다시 준비 가능해야 한다. 화면은 의미 있는 페이지/데이터/크기 변화 후 postFrame에서 replace, dispose에서 scope.dispose 호출.
