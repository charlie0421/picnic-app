결론: 스테이징 생략 방향 유지, 운영 적용은 보완 전 보류

핵심 기능 테스트는 통과했지만, 운영 권한에서의 마이그레이션 실패·권한 회수 누락이 확인됐고 운영 활성화 준비 상태도 미충족이다. 단순히 플래그를 꺼 둔 채 원본 6개 파일을 순서대로 실행하는 것으로는 준비가 끝나지 않는다. 실제 지급을 막는 기존 쓰기 가드는 정상 동작함을 재확인했다.

운영 DB 변경·배포·플래그 활성화·실결제·커밋·푸시는 하지 않았다. 기존 로컬 DB도 초기화하거나 변경하지 않았다. 이번 작업은 실행 승인 전 검증이며, 아래 보완 구현과 실제 운영 적용은 별도 단계다.

1. 차단 항목과 실제 지급 보호 검증

① 마이그레이션 소유권 변경 실패와 CREATE 권한 회수 누락

운영의 wallet_command_owner는 wallet_private 스키마에 CREATE 권한이 없다. 20260821103000…:56의 첫 ALTER FUNCTION … OWNER TO wallet_command_owner는 해당 권한을 준비하지 않는다. 103000:94, 110000:65도 같은 형태다.

운영과 같은 PostgreSQL 15.8에서 비슈퍼유저 postgres로 함수 생성은 성공했지만 소유권 이전은 permission denied for schema wallet_private로 실패했다. 제한된 CREATE 부여 → 소유권 변경 → CREATE 회수는 통과했고, 전체 검증 트랜잭션은 롤백했다. 새 소유자에게 해당 스키마 CREATE 권한이 필요하다는 규칙은 PostgreSQL 15 공식 문서와도 일치한다.

또한 20260821120000…:534/541와 20260821123000…:33/891은 두 스키마에 부여한 CREATE 중 public만 회수한다. 따라서 단순 선행 GRANT만 추가하면 권한이 남는다. 실제 배포 번들은 각 구간의 권한과 최종 ACL을 함께 검증해야 한다. 이미 main에 병합된 과거 마이그레이션을 무단으로 다시 쓰지 않는다.

② V2 표시·판정과 실제 지급은 별도 게이트 — 실제 지급 보호는 정상

promotion_schedule_v2_settlement_enabled()는 두 V2 표면·판정 플래그를 본다(20260821123000…:155). 그러나 실제 credit 호출 전에 promotion_write_enabled()를 추가 검사한다(같은 파일:540). 이 함수는 운영에서도 candy_boost_write_enabled를 검사하며, OFF이면 지급하지 않고 PROMOTION_WRITE_PAUSED로 재처리를 예약한다.

격리 DB에서 직접 UPDATE나 트리거 우회 없이 정상 public.set_wallet_runtime_flag API만 호출한 재현 결과:

이어 정상 API로 candy_boost_write_enabled=true를 시도하자 기존 준비 검사가 WALLET_RELEASE_GATE_BLOCKED로 올바르게 거부했다. 이미 통과한 grant snapshot 테스트의 776–811행도 쓰기 OFF에서 financial operation이 생기지 않고 지급 보류·재시도가 유지됨을 단언한다. 실험 전체는 ROLLBACK했다.

정정: V2 helper가 true라는 첫 관찰만으로 실제 금전 지급 검사 우회라고 판단할 수 없다. 추가 코드·실행 검증 결과 그 결함은 확인되지 않았다. 이 근거만으로 새 금융 가드를 추가하지 않는다. 필요한 것은 운영 workers·routes·coverage를 실제로 준비한 뒤 기존 지급 가드를 통과시키는 활성화 절차와, 표시·판정만 켜진 상태에서의 사용자 안내 검증이다.

③ 활성화 전 UI 일관성과 검증 도구 보완

상품 배지는 V2 우선 resolver를 쓰지만 구매 확인창은 V1 캠페인 provider를 사용한다. V2-only 일정·배수 변경 때 표시가 달라질 수 있으므로 동일한 표시 스냅샷을 사용하도록 맞추거나 승인된 표시 계약을 검증해야 한다. 서버 지급액을 클라이언트에서 재계산하는 문제는 확인되지 않았다.

백엔드 safety suite 4건은 삭제된 picnic-app-cotton-candy-policy 체크아웃의 절대경로를 하드코딩해 실패한다. 운영 데이터 문제가 아니라 재현 가능한 배포 검증 도구의 결함이며, 무시 처리 대신 fixture 경로를 이식 가능하게 고쳐야 한다.

격리 환경 구성과 테스트 증거의 정확한 범위

기존 공유 로컬 DB는 PostgreSQL 17.6이며 운영 URL을 향하는 웹훅 트리거 2개가 있었다. 그 DB에서는 SQL 테스트를 실행하지 않았다. 읽기 전용으로 얻은 로컬 논리 덤프를 별도의 public.ecr.aws/supabase/postgres:15.8.1.038 컨테이너에 복원했다. 운영 고객 데이터를 복사하지 않았다.

컨테이너는 network=none, 공개 포트 없음, Unix socket만 사용, cron 실행 OFF였다. 복제본에만 로컬 seed를 적용해 웹훅을 제거했고 트리거 수 0을 확인했다. 결정적인 실패를 숨기지 않도록 모든 restore/test는 ON_ERROR_STOP으로 실행했다.

PG17 덤프를 PG15에 옮기기 위한 테스트 전용 기계적 변환: transaction_timeout·psql restrict 제거, PG16+ 역할 membership 문법 변환, PG17 MAINTAIN 권한 제거, 버전별 pg_stat_statements/GraphQL/Vault 확장 ACL 차이 보정, Vault pgsodium 의존성 설치. 지갑/V2 함수 본문과 테스트 assertion은 바꾸지 않았다.

복제본 DB owner와 postgres의 CREATE 권한을 관찰된 운영 형태에 맞췄다. fixture 트리거 제어용 session_replication_role 권한도 복제본에만 부여했다. 기존 로컬 DB의 get_artist_paid_votes 2-인자 manifest와 4-인자 실제 함수 불일치는 복제본에서만 수정했다. 운영 manifest는 별도 읽기 전용 검사에서 unclassified=[] / not_callable=[]였다.

따라서 11개 SQL 통과는 보정된 격리 fixture에서의 기능 회귀 증거다. 운영 데이터 규모·락 경합·실제 6개 마이그레이션 전체 적용 리허설 또는 실결제 검증으로 확대 해석하지 않는다. dblink 별도 커밋형 동시성 테스트는 이번 범위에서 실행하지 않았다.

5. 다음 구현 계획 — 승인 후 진행할 범위

  1. 백엔드 권한·배포 번들: 최신 main 기준의 격리 작업공간에서 기존 6개 migration을 보존하며, 생산 환경 적용 순서의 선행 CREATE/소유권 변경/회수와 최종 ACL 검사를 구현한다. 부분 V2 설치·함수 지문 변경·예상 외 기존 권한이면 중지한다. 비슈퍼유저 PG15에서 전체 적용과 실패 시 원복을 검증한다.
  2. 활성화 절차·게이트 통합 검증: 기존 V2 판정과 실제 지급 가드를 유지하고 정상 플래그 API를 통한 통합 테스트를 추가한다. 쓰기 OFF에서 지급 없음, 미준비 상태의 쓰기 ON 거부, 준비 후 재처리, V2 OFF 후 기존 결정 유지가 대상이다. 운영 workers·coverage·routes·환불 준비는 사실에 기반한 증거를 확보하며, ready 값을 임의로 기록하거나 새로운 금융 가드를 불필요하게 추가하지 않는다.
  3. 앱 표시·테스트 도구: V2 일정만 활성화된 경우와 서로 다른 V1/V2 이름·배수의 확인창 테스트를 추가한다. 동일 resolver snapshot을 사용하도록 표시 계약을 맞춘다. 백엔드 safety fixture의 절대경로 의존을 없애고 전체 검증을 녹색으로 만든다.
  4. 독립 재검토: 수정 diff와 실행 증거만으로 반대 공급자의 Frontier 리뷰를 받고, 지적을 코드·테스트로 확인한 뒤 원 리뷰어가 재검증한다.
  5. 운영 비활성 배포 승인: 대상 project, immutable SHA/hash, 정확한 SQL/권한 변화, timeout·중지 조건을 제시해 확인받는다. 원래 V1 스테이징 gate를 허위로 통과시키거나 기존 cotton flags를 일괄 OFF하지 않는다.
  6. 실제 활성화는 별도 승인: 운영 workers/coverage/routes/admin 권한과 캠페인 일정·클라이언트 배포를 증거로 확인한 뒤 ON한다. 현재 flag는 환경 전체에 적용되므로 내부 계정 한정 canary라고 부르지 않는다.

6. 중지·복구 원칙

활성화 전 실패는 한정된 적용 단위의 실패 원복과 정확한 이전 함수/ACL 복구로 다룬다. 활성화 후에는 promotion_schedule_v2_enabled=false로 신규 V2 판정을 중지하되, 이미 확정된 grant snapshot·allocation·감사 기록을 삭제하지 않는다. snapshot이 고정됐지만 지급은 대기 중인 건도 기존 V2 경로로 재처리될 수 있으므로 V2 OFF를 대기 지급 취소로 해석하지 않는다. V2 재처리·환불에 필요한 새 schema/code를 곧바로 제거하지 않는다.
