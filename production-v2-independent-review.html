잔류가 영구인가 — 롤아웃 시나리오에 의존 [소스]

레포의 후속 마이그레이션들은 파일 끝에서 revoke create on schema wallet_private from wallet_command_owner 를 수행합니다 (20260824051000:343, 20260824060000:379, 20260831120000:579, 20260902093000:841).

  • 클린 전체 리플레이라면 20260824051000 이 뒤따르며 잔류가 부수적으로 해소됩니다.
  • 선택적 V2 적용은 다릅니다. 현재 검토 후보는 V2 6개 파일만이며, 위 후속 마이그레이션들을 자동 재실행하지 않습니다. 따라서 별도의 권한 회수가 없으면 해당 적용 단위 종료 후 CREATE 권한이 남습니다. 운영의 개별 migration ID 적용 여부는 이력 번호 차이 때문에 별도 확인 대상입니다. [root 통합 시 증거 범위 보정]
왜 통과 테스트로는 검증되지 않는가

F1 은 fail-closed(즉시 오류)라 실행 즉시 드러납니다. F2 는 fail-open 입니다 — 권한이 남아 있어서 이후 문장이 오히려 성공합니다. 따라서 "SQL 파일이 전부 통과했다"는 사실은 F2 의 해소 근거가 되지 못합니다. 검증은 적용 후 has_schema_privilege('wallet_command_owner','wallet_private','CREATE') 직접 조회로만 가능합니다.

영향 범위 (과장 없이)

원격에서 악용 가능한 취약점이 아닙니다. 이미 wallet_command_owner 로 실행 중인 코드에만 의미가 있으며, 해당 역할이 wallet_private 에 객체를 생성·교체할 수 있게 되는 방어심층(defense-in-depth) 경계 침식입니다. 전제된 CREATE=false 불변식과 레포 자체 규율을 위반한다는 점이 핵심입니다.

  • "123000 은 120000 의 권한 잔류에 의존해서만 성공한다" — 거짓. 자체 대여가 있어 독립적입니다.

정정된 사실

123000 은 120000 과 동일한 형태의 결함을 독립적으로 한 번 더 저지릅니다: 33행에서 두 스키마를 빌리고 891행에서 public 만 반납합니다. 즉 F3 은 "결합(coupling) 결함"이 아니라 "F2 의 두 번째 사이트" 입니다. 두 파일은 각각 독립적으로 수정 가능하며, 둘 다 수정해야 잔류가 사라집니다.

이 정정은 위험도를 낮추지 않습니다 — 잔류 사이트가 1개에서 2개로 늘었고, "함께 고쳐야 한다"는 잘못된 결합 제약만 제거됐습니다.

2. 플래그 OFF 교체 안전성 · V1 호환성 · 매니페스트 [소스]

3. 활성화 술어 vs 준비도 — 실질 정정

정정됨LOW F5. 준비도는 돈이 움직이는 플래그를 정확히 게이팅하고 있음 production-release-gate.sql:9-12, 53-68 · production-functions.sql:136-143 · 123000:540

1판은 "게이트가 준비도를 전혀 강제하지 않는다"고 서술했습니다. 이는 절반만 맞고, 가장 중요한 부분을 놓쳤습니다. 프로덕션 실제 정의를 읽고 정정합니다.

① 준비도는 네 개의 write 플래그에 묶여 있다 [소스]

  or  ... wallet_credit_source_coverage where coverage_percent<>100                            -- 크레딧 소스 커버리지

따라서 코디네이터가 제시한 준비도 관측치(미마이그레이션 라우트 2, 크레딧 소스 1건 미완, 워커 2건 미준비, 감사 커버리지)는 버려진 검사가 아니라 candy_boost_write_enabled 등 쓰기 플래그를 켜려 할 때 정확히 차단합니다.

[root 통합 주석] admin cutover evidence는 admin_financial_commands_enabled의 별도 게이트다. 모든 쓰기 플래그에 동일한 admin cutover 조건이 적용된다고 일반화하지 않는다.

② V2 라우팅 플래그는 준비도 검사 대상이 아니다 [소스]

promotion_surfaces_enabled 와 promotion_schedule_v2_enabled 는 write_requested 집합에 포함되지 않습니다. 그래서 [루트 증언] 의 로컬 게이트 프로브(public.set_wallet_runtime_flag 경유, 리플리카 우회 없음)에서 네 쓰기 플래그를 false, surfaces/V2 를 true 로 두었을 때 promotion_schedule_v2_settlement_enabled() 가 TRUE 를 반환한 것은 이 소스가 예측하는 그대로입니다. (해당 트랜잭션은 ROLLBACK 됨.)

③ ★ 결정적 — 술어 TRUE 는 실제 지급을 의미하지 않는다 [소스]

settlement_enabled() 는 V1/V2 라우팅만 결정합니다. 실제 크레딧은 별도의 하류 쓰기 게이트가 막고 있으며, 이 게이트는 V1·V2 양쪽 모두에 존재합니다.

정정된 결론

프로덕션 현재 candy_boost_write_enabled = false 이므로, V2 라우팅 플래그를 켜더라도 실제 구매에서 보너스가 지급되지 않습니다. 평가 후 enqueue_promotion_award 로 적재되고 인박스 이벤트는 5분 재시도로 일시정지되며, 결의(resolution)는 GRANTED 로 전이되지 않습니다. 그리고 그 candy_boost_write_enabled 를 켜려면 ①의 준비도 검사를 통과해야 합니다 — 준비도 → 돈 이동의 인과 사슬은 온전합니다.

증거의 한계 (명시): 위는 술어와 코드 경로에 대한 증거입니다. 실제 구매는 시도되지 않았습니다(루트·나 모두). 따라서 "실구매 시 지급되지 않는다"는 코드 경로 판독에 근거한 결론이며 실거래로 실증된 것이 아닙니다.

[root 후속 실행 증거] 같은 격리 트랜잭션에서 실제 promotion_write_enabled()는 false였다. 정상 API로 candy 쓰기 ON을 시도하자 WALLET_RELEASE_GATE_BLOCKED로 거부됨을 단언했고 ROLLBACK했다. 통과한 grant snapshot 테스트 776–811행도 쓰기 OFF에서 financial operation 없음, 고정된 결정과 지급 보류·재시도 유지를 검증한다. 이는 로컬 fixture 증거이며 실제 운영 결제는 수행하지 않았다.

잔여 위험 (결함 아님, 운영 주의)

V2 라우팅 ON + candy_boost_write_enabled OFF 상태를 오래 유지하면, 적격 구매마다 지급 큐가 쌓이고 인박스 이벤트가 5분 주기로 재시도됩니다. 이 조합은 단기 전환 상태로만 유지하십시오.

7. 권고 — 역사 재작성 없는 전진 보정

병합된 과거 마이그레이션 파일을 수정하지 않는다는 전제에서, 두 가지 방식을 권합니다.

[root 통합 주석] 아래는 미구현·미실행 설계 후보의 의사코드이며 운영 실행용 완성 스크립트가 아니다. 정확한 파일 hash·대상·기존 함수 지문·부분 적용 부재·ACL 전후 동일성·실패 시 원복·마이그레이션 이력 기록을 구현하고 전체 적용 테스트와 독립 재검토 후 사용자 승인을 받아야 한다.

  1. 고정 대상 적용 래퍼(pinned targeted application wrapper) — 권장. 6개 파일을 있는 그대로 적용하되, 앞뒤에 대여/반납을 감싸는 래퍼 스크립트를 하나 만들어 한 트랜잭션으로 실행합니다. F1·F2·F3·F4 를 동시에 해소합니다. 
    begin;
  grant usage, create on schema wallet_private to wallet_command_owner;   -- F1 해소
  \i 20260821100000_...sql
  \i 20260821103000_...sql
  \i 20260821110000_...sql
  \i 20260821113000_...sql
  \i 20260821120000_...sql
  \i 20260821123000_...sql
  revoke create on schema wallet_private from wallet_command_owner;       -- F2·F3 잔류 반납
commit;                                                                   -- F4 원자성 확보

    래퍼의 마지막 revoke 가 120000:541·123000:891 이 빠뜨린 반납을 대신 수행합니다. 과거 파일은 한 글자도 건드리지 않습니다.

  2. 전진 보정 마이그레이션 — 래퍼를 쓸 수 없다면, V2 6종 뒤에 놓일 신규 마이그레이션 1개를 추가해 revoke create on schema wallet_private from wallet_command_owner; 를 수행합니다. 단 이 방식만으로는 F1(적용 자체가 중단됨)이 해소되지 않으므로, F1 을 위한 선행 대여가 별도로 필요합니다.

적용 후 필수 검증 — select has_schema_privilege('wallet_command_owner','wallet_private','CREATE'); 가 false 인지 직접 확인하십시오. F2/F3 는 fail-open 이라 테스트 통과로는 확인되지 않습니다.

활성화 순서 — ① 다크 배포 완료 및 ACL 검증 → ② 앱 F7(가능하면 F6) 수정 → ③ promotion_surfaces_enabled + promotion_schedule_v2_enabled ON(라우팅만) → ④ 준비도 통과 후 candy_boost_write_enabled ON(실지급). ③↔④ 간격은 짧게 유지(F5 잔여 위험).
