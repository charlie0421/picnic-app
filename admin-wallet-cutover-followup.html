관리자 웹 코드·의존성·배포·역할·운영 지갑은 변경하지 않았다. 운영 지갑 이관 완료 또는 ADMIN_ONLY 활성화 승인이 아니다. 실제 사용자로 조정·복구 요청을 보내지 않았다.

2. 확인한 호출 경로와 남은 계약 차이

대상배포 코드의 경로판단
admin_adjustmentCandyAdjustModal → submitCandyAdjust → /api/wallet/candy-adjust → 서버 session user.id + service-role → admin_adjust_star_bonusRPC 경로가 존재한다. 단, 별도 진입점이며 아래 canonical handler와 응답 형식도 다르다. raw table writer라고 단정하는 것은 부정확하다.
projection_repairUserProfileDetail/WalletRepairDialog → WalletCommandExecutor → /api/wallet-ops/commands → admin_preview_wallet_repair 및 admin_execute_wallet_repair서버가 session actor를 결합하고 허용 action을 매핑하는 경로가 존재한다. 실제 운영 권한·preview/execute 동작과 감사 증거는 아직 미실행이다.
단일 진입점 계약backend docs/wallet/admin-command-handoff.md는 하나의 인증된 Next Route Handler와 7-key envelope, transport/decode 실패의 별도 감사 기록을 요구한다.두 진입점이 현재 배포돼 있다. candy-adjust는 성공 응답을 3개 key로 재구성하며, canonical command handler의 transport/decode 실패도 별도 record_wallet_command_failure 호출 없이 error 응답을 만든다. 코드·문서 계약을 정리하고 검증하기 전 이관 완료를 선언하지 않는다.
  • 별도 조정 API — 서버 session actor 사용, 직접 RPC 호출 및 응답 재구성
  • canonical command handler — closed mapping과 서버 actor, 성공 envelope 검증, 실패 처리
  • command API · 브라우저 command transport
  • 기존 backend handoff 계약

이 차이는 프로덕션 취약점 악용 재현이나 금전 손실 확인을 뜻하지 않는다. DB가 별도 actor 권한·입력 검증을 수행한다는 구조와, 운영 호출자 전환 전체 증거가 미완료라는 판단을 구분한다.

3. 테스트 시도와 한계

관련 Jest 6개 파일의 mock 테스트를 네트워크 EPERM 차단, 실제 .env 파일 읽기 차단, 가짜 자격증명, --no-cache, default reporter로 실행하려 했다. 그러나 node_modules/jest-cli/build/index.js가 없어 테스트 실행 전에 exit1로 종료됐다. 테스트 assertion 실패가 아니며 통과한 테스트는 0개다.

실행 조건·결과 · 원시 오류. 기존 package.json 수정과 .nvmrc/service-role-key-rotation.html은 그대로 보존했다. 의존성 설치·수정은 하지 않았다. 실제 배포 UI E2E와 운영 지갑 쓰기 테스트도 수행하지 않았다.

4. 플래그 설정 위치 — 사용자 추가 질문

저장 위치는 Supabase의 public.wallet_runtime_flags이고 변경 명령은 public.set_wallet_runtime_flag(flag_key, value_json, expected_version, reason)이다. 현재 version 및 변경 사유를 요구하며 활성화 안전 조건을 검사한다. 일반 앱 사용자의 authenticated 역할에는 EXECUTE 권한이 없다. 테스트 대상 사용자 여부와 설정 권한은 다르다.

promotion_v2_rollout_mode는 OFF / ADMIN_ONLY / ALL이며 ADMIN_ONLY 대상 판정은 is_admin OR is_super_admin이다. V2 스케줄·표시·실제 적립의 boolean 플래그도 별도 조건이다. 앱이 값을 직접 설정하지 않고 서버 RPC 결과를 읽는다.

앱의 V2 repository가 로그인 세션으로 get_active_promotion_campaigns_v2(HOME 또는 PAYMENT_BADGE)를 호출한다. 서버가 표시·스케줄 flag, 사용자 대상, 이벤트 시간 조건을 평가해 대상이면 배너·배율 데이터를, 제외되면 빈 V2 목록을 반환한다. 앱이 DB 플래그 테이블을 직접 읽거나 관리자 여부만 보고 적립을 결정하지 않는다. 해당 코드가 배포 앱에 포함됐다면 플래그 변경은 재배포 없이 다음 RPC 조회에 반영되지만 실시간 push 보장은 없다. 홈의 당겨서 새로고침은 V1/V2 source 캐시를 함께 무효화해 다시 조회한다. V1 fallback은 별도 서버 계약이며 빈 V2가 앱의 모든 기존 이벤트 제거를 뜻하지 않는다.

현재 /wallet-ops의 긴급 런타임 플래그 UI에는 boolean 및 기존 광고 enum 조작만 구현되어 있고, promotion_v2_rollout_mode enum 선택은 없다. 이번 ADMIN_ONLY 활성화는 승인된 서버 명령 절차이며, 별도의 관리자 UI를 이번 작업에서 추가하지 않았다. 서버 설정 명령·대상 판정 근거.

5. 다음 범위 — 아직 구현·승인하지 않음

  1. 별도 관리자 worktree에서 단일 명령 진입점과 현재 조정 UI를 연결하는 최소 변경을 설계한다. 기존 한도 UX·사용자 메시지·재시도 idempotency를 보존하고 transport/decode 실패의 정해진 감사 처리를 검증한다. 먼저 범위 확인을 받는다.
  2. 해당 isolated worktree의 의존성을 정상 준비한 뒤 관련 mock/integration 테스트와 금융·권한 교차 리뷰를 수행한다. UI/API main merge 전 Vercel Preview 확인 절차를 따른다.
  3. 실제 배포 호출자 SHA·파일·RPC·검증 결과를 근거로 미이관 두 경로 및 promotion-ops 적립 source를 처리할 승인된 migration/운영 절차를 정리한다. 검증 없이 migrated 값을 바꾸지 않는다.
  4. worker 패치 운영 OFF 설치와 이관 조건 해소 후 안전 게이트를 재검증하고, 계정·배율·기간과 활성화 승인을 확정해 ADMIN_ONLY로 테스트한다.

마지막 운영 DB 확인(12:35 KST)의 미이관 두 경로/75% 값은 이번 Vercel 메타데이터 조회로 새로 확인한 값이 아니다. 앱 대상 is_admin OR is_super_admin과 관리자 금융 명령 RBAC를 혼동하지 않는다. 별도 금융 기능을 켜거나 역할을 추가하지 않았다.
