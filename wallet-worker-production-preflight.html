Worker 패치 — 프로덕션 사전점검 중단

후속 상태: 사용자 승인에 따라 운영 권한을 보존하는 배포 도구·테스트·문서 보완과 독립 검증을 완료했다. 최신 수정·검증·PR 결과. 아래는 15:46–15:48 KST의 사전점검 기록이며, 이 후속 작업은 운영 DB를 변경하지 않았다.

2026-09-09 15:46–15:48 KST, PICNIC-PROD xtijtefcycoeqludlngc, PG15.8.1.038. 사용자 “진행”은 머지된 단일 패치의 OFF 상태 운영 적용 승인으로 해석했다. 대상 main은 dc1edda2d0d2cb7868ce2d1ec1298a0cabda0c11, PR #140이다.

배포 중단: 운영 권한이 배포 도구의 고정 기준과 다르다. 단일 migration과 적용 번들은 실행하지 않았다. 운영 함수·권한·플래그·이력 변경 0건, 앱 변경 0건이다. 기준을 맞추려고 운영 권한을 부여하거나 검사를 우회하지 않았다.

1. 정확한 불일치

대상은 public.reconcile_wallet_batch(integer,uuid). 함수 본문 MD5 ac4af4b21c3cd18eac4cc79da7bbfe6c, owner wallet_command_owner 및 security shape는 같다. 차이는 직접·유효 EXECUTE 권한이다.

원본 preflight SQL을 수정 없이 BEGIN; SET LOCAL statement_timeout='10s'; SET LOCAL lock_timeout='1s'; … ROLLBACK; 경계에서 실행해 다음 거부를 확인했다. 이 gate는 metadata 조회와 transaction-local 설정만 수행한다. gate가 read-only transaction 자체를 거부하기 때문에 BEGIN READ ONLY로 실행했다고 표현하지 않는다.

2. 확인된 현재 상태

  • 프로젝트 이름 PICNIC-PROD, 상태 ACTIVE_HEALTHY, 서울 리전. 연결 tool의 project ID와 프로젝트 메타데이터를 대조.
  • 해당 migration 20260909030430 이력 0건. 거부 뒤 15:48:07 재조회도 0건.
  • promotion_v2_rollout_mode=OFF. schedule/surfaces 및 네 write flag 모두 false, version=1. 거부 뒤 재조회도 동일.
  • 두 worker 존재, scan_had_skips=false. 15:46 조회에서 expiry 마지막 성공 15:45:03, reconciliation 15:34:00·clean_scans=19. 이 값은 cron의 동적 상태이며 작업자가 수동 실행한 결과가 아님.
  • 나머지 세 함수 본문·권한, worker CHECK/owner/RLS 및 schema CREATE 조건은 최초 metadata 비교에서 기대값과 일치. 전체 gate는 wrapper에서 중단됐으므로 모든 gate를 통과했다고 주장하지 않음.

3. 원인과 검증 한계

배포물의 manifest·builder·pre/postflight·테스트는 wrapper의 service_role 실행을 true로 고정했고, 격리 fixture도 그 기준이었다. 실제 운영은 더 제한적이어서, 격리 테스트 통과만으로 운영 권한 기준의 일치를 보장하지 못했다. 이 운영 대조 누락은 배포 검증물의 보완 대상이다.

현재 저장소의 20260721095500 원본 migration에는 wrapper의 service_role grant가 있으나, 제한된 소스 조사에서는 실제 운영에서 이를 회수한 변경의 시점·행위자·승인 근거를 찾지 못했다. 따라서 임의 권한 축소의 원인이나 보안 설계의 의도를 확정하지 않는다. 운영을 원본 migration의 더 넓은 권한으로 되돌리는 것도 금지한다.

추가 문서 오류: 실제 checkpoint 본문은 public.reconcile_wallet_batch_release_unguarded를 호출한다. 배포물의 “checkpoint가 public.reconcile_wallet_batch wrapper를 거친다”는 설명도 그 호출 경로와 맞지 않는다. 이 패치는 어느 대사 함수도 교체하지 않으며, 후속 문서·검증 기준에서 두 대상을 구분해야 한다.

실제 백업/PITR 복구 지점과 이번 실행의 쓰기 중단 창은 아직 새로 확인하지 않았다. 기준 불일치가 확인되어 이후 배포 단계에 진입하지 않았다. 이전 백업 기록이나 다른 세션의 과거 동결을 이번 실행 근거로 재사용하지 않는다.

4. 필요한 후속 승인

  1. 운영 권한을 보존하는 방향으로 배포 도구 기준을 재검토·보완한다. 관련 운영 변경 이력·호출 경로 조사도 포함한다.
  2. 운영과 같은 ACL fixture에서 사전검사·원자성·롤백·postflight를 다시 검증하고, service_role 실행 추가·grant option·unknown role·membership 확대를 반드시 거부하는 반례를 유지한다.
  3. 반대 공급자 보안 리뷰 및 새 PR·머지 후 적용물을 재생성한다. migration 본문이나 운영 권한을 임의 수정하지 않는다.
  4. 새 복구 지점과 쓰기 중단 창 확인 후 재승인된 적용을 진행한다. ADMIN_ONLY 활성화는 여전히 별도 승인이다.

현재 승인 범위는 운영 적용이므로, 안전 기준을 바꾸는 추가 코드 보완은 사용자 확인을 받은 뒤 진행한다. Superpowers의 실행 중단·원인 조사 절차와 Supabase 사전/사후 확인 원칙을 적용했다. 독립 작업자와 추가 운영 쓰기 작업은 시작하지 않았다.
